# 99L Mission Board 故障分離・回収優先仕様

## 1. 目的

本仕様は、飛行中の一部機能の故障や性能不足を、減速機構・パラシュート開放まで連鎖させないための上位方針を定める。

基本原則は、**故障した機能だけを縮退させ、回収に不要な故障をflight-wide fatal errorへ昇格させない**ことである。

特に離床検知成立後は、通信、AirData、動翼制御、ADC、logging等の故障によってパラシュートの時刻fallbackを停止、延期、resetしてはならない。

## 2. 機能の優先度と故障domain

### 2.1. Recovery critical

以下は回収系として最優先で扱う。

- current flight epochと離床時刻の安全latch
- monotonic elapsed timer
- `SafetyTask`の+17 s deployment fallbackと+25 s absolute power cutoff
- パラシュートOpenのflight snapshot
- Para power arbiter / GPIO44
- `ParachuteTask` / STS3215 UART / servo actuation

これら自身の故障は回収能力を失わせ得るため、他のdiagnostic errorと同列に扱わない。

### 2.2. Control critical but not Recovery critical

以下は動翼制御には必要になり得るが、パラシュート時刻fallbackの依存先にしてはならない。

- ICM42688姿勢推定
- AS5047D / Fin Velocity Estimator
- TB67H450 / motor / fin zero / fin overtravel
- LPS25HB / SSCDRRN005PD2A5 / airspeed
- Roll Controller / Control coordinator
- 1 kHz Mission/Control周期のdeadline遵守

これらが故障した場合はControlを停止し、必要ならEngineBurn相当の非Control状態へ縮退してよい。ただしdeployment clock、+17 s fallback、Para Open要求、+25 s cutoffへ影響させてはならない。

### 2.3. Housekeeping / telemetry / logging

以下は原則としてflight sequenceを止めない。

- logic voltage ADC / motor voltage ADC
- CAN telemetry
- 通信基板およびLoRa link
- microSD logging
- internal Flash backup logging
- LED、diagnostic、低rate housekeeping

ADC等、審査・飛行安全上の必須判定に実際には使用しないものは、初期化失敗、read失敗、値invalidをtelemetry/logへ残すだけとし、`StartSequence`、離床後sequence、Control以外の回収処理を拒否する理由にしない。

将来ある値を安全判定へ昇格する場合は、その依存関係をVaultで明示してから実装する。暗黙にfatal化しない。

## 3. 離床後のdeployment invariant

current flight epochで離床検知が成立した時点で、離床時刻に基づく回収clockを確定する。

- 離床+10 s以降にLPS25HBの頂点条件が成立した場合は早期deploymentしてよい。
- LPS25HBが故障、stale、Unavailable、I2C timeoutとなった場合は気圧triggerだけを失効させる。
- **離床+17 sのdeployment fallbackは無条件で残す。**
- +17 s deadlineをsensor recovery待ち、CAN/LoRa reconnect待ち、Control復帰待ち、logging完了待ち等の理由で延長しない。
- 動翼が0 degへ到達していないことをPara Openの前提条件にしない。
- 離床+25 sの絶対電源遮断も同じ回収clockから独立して実行する。

`CancelSequence`は離床前のLiftoffDetectionでのみ扱う。離床後の通常のsensor/control/communication faultは離床時刻をinvalid化しない。

`LiftoffDetectionEmergencyStop`のように仕様で明示されたoperator要求によるrollbackだけは例外として新epochへ巻き戻してよい。単なる通信断やsensor faultをrollbackとして扱わない。

## 4. 通信断の扱い

Mission Boardから見たCAN、およびその先の通信基板/LoRa/地上局は、離床後の自律回収に必須ではない。

- CAN bus-off、通信基板reset、LoRa link loss、地上局停止をdeployment inhibit条件にしない。
- commandを受信できないことを理由にflight timerを停止しない。
- telemetry送信、CAN recovery、ACK待ち等は`SafetyTask`およびPara Open処理をblockingしない。
- 通信が復旧した場合は現在状態を再送してよいが、回収clockを再初期化しない。

## 5. AirData故障の扱い

LPS25HB / SSCはControl判定には使用してよいが、回収fallbackとは分離する。

- LPS/SSC故障でControl entryを拒否またはControlを停止してよい。
- LPS故障時はpressure apex detectorをUnavailableとする。
- LPS/SSCの再初期化やI2C timeout処理はbest effortとし、+17 s timerを待たせない。
- AirDataが後から復旧しても、既に失効したControl re-entryを復活させる必要はない。
- recovery側はAirDataの復旧有無にかかわらず既定deadlineで進む。

## 6. Control周期超過の扱い

Control/PWM updateの目標周期は1 kHzとするが、**1周期の処理時間が1 msを超えたこと自体をfatal error、Control即停止、deployment inhibitの理由にしない。**

productionでは以下とする。

- late tickでも利用可能なlatest complete sampleを用いてControl計算を継続する。
- estimator/integrationは固定1 msを盲目的に仮定せず、可能な限りsensor timestamp / measured dtを使用する。
- deadline miss / overrun / repeated block / coalescingはcounterと最大遅延をlog/telemetryへ残す。
- 遅れを取り戻すために古いcontrol outputを複数回まとめて再生しない。
- future sampleを待つためにControl taskをblockingしない。

ただし、実際のsensor sample invalid、FIFO破損、許容不能なdata loss、fin actuator fault、数値異常などによりControl入力そのものが信頼できない場合はControlを停止してよい。この場合も回収系は独立して継続する。

## 7. SafetyTaskの独立性

`SafetyTask`は最優先のnon-blocking taskとし、deployment timing判定にMission/Control/AirData/CAN/ADC/storageの正常動作を要求しない。

離床検知成立時には、少なくとも以下を一方向のsafety latchへpublishする。

- `flight_epoch`
- `liftoff_time_us`
- `liftoff_time_valid`

+17 s / +25 s判定はこのlatchとmonotonic timerだけで実行可能にする。離床後のfallback判定を`MissionState` mutexの取得成功に依存させない。

`safety_authorized`なPara Open要求は、通常のMissionState遷移確認を待たずに回収系へ渡せるようにする。epoch整合性が必要な場合は上記safety latchで検証し、MissionRealtimeTaskが保持し得るmutexへ依存しない。

queue full等でSafety eventを一回捨てて終わりにしない。成功するまで再試行するか、atomic latch / overwrite型のsingle latest request等で要求を保持する。

## 8. ParachuteTaskの境界

「timerだけで開く」とは、**deployment判断が非回収subsystemへ依存しない**という意味である。物理的な開放にはPara電源、STS UART、servo、Open snapshot等の回収系自身は必要である。

- `ParachuteTask`のUART処理はbounded timeoutとglobal retry deadlineを持つ。
- Open snapshotがvalidなら、通信、AirData、Control、ADC、storageの状態にかかわらずOpenを試行する。
- Open snapshot missing/corrupt、current angle取得不能、servo failure等は専用failure reasonとして記録し、他domainのerrorと混同しない。
- +25 s absolute cutoffは`ParachuteTask`のhangやUART failureから独立してGPIO40/GPIO44を遮断できる構成を維持する。

## 9. Error propagation規則

errorは原因domainから必要最小限だけ伝播させる。

- Housekeeping error → telemetry/log invalid。MissionStateへ伝播しない。
- Communication error → telemetry/command unavailable。MissionState/deploymentへ伝播しない。
- AirData/attitude/fin error → Control unavailable。deploymentへ伝播しない。
- Control deadline miss → timing quality低下の記録。単独ではControl unavailableへ伝播しない。
- Recovery critical error → parachute failure reason / safety statusへ明示する。

単一のglobal `fatal` flagで全actuator、timer、state machineを一括停止する設計は禁止する。必要な停止範囲をerrorごとに明示する。

## 10. 検証条件

少なくとも以下をHIL/benchまたはhost testで確認する。

1. 離床検知後にCANを停止しても離床+17 sでOpen要求が出る。
2. 離床検知後にLPS25HBを切断しても離床+17 sでOpen要求が出る。
3. LPS故障中でも+25 s absolute cutoffが実行される。
4. ADC initialize/readを失敗させてもflight sequenceとrecovery clockが継続する。
5. SD/Flash loggingを失敗させてもflight sequenceとrecovery clockが継続する。
6. Mission/Control tickへ1 ms超の人工負荷を入れてdeadline missを発生させても、deadline miss単独ではControlを停止せず、回収clockにも影響しない。
7. Control inputを意図的にinvalid化してControlを停止させても、+17 s Openと+25 s cutoffは継続する。
8. MissionState mutexを長時間競合させても、既にlatchedされた離床時刻からSafetyTaskが+17 s/+25 s判定を継続できる。
9. Para request queueを一時的にfullにしてもSafety Open要求が失われない。
10. CAN/LoRa復旧後もflight epochと離床時刻がresetされない。

本仕様は回収成功を保証するものではないが、**回収に不要な機能の故障が回収機能を道連れにする構造を禁止する**ための受入条件とする。
