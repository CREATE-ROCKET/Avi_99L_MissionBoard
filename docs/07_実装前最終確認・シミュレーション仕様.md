# 99L Mission Board 実装前最終確認・シミュレーション仕様

## 1. 位置付け

本書は、Mission Board本番実装へ進む直前のcross-cuttingな最終確認事項と、実機計測→Spica→firmware定数確定の順序をまとめる。

機能別要求は00〜05、bring-up手順は06を正とし、本書はそれらを実装へ落とす際の統合条件、検証順序、Spicaとの接続条件を定義する。

Spica側は`Natsu-B/Spica_v3.1`を使用する。2026-08-12時点で監査したHEADは`99a3bf295fa1b65fa0f47ba607f4ebf0d6b9d2dd`で、Phase 1〜5相当まで実装済みである。

## 2. 飛行用動翼の絶対制約とstopper

動翼hardware/mechanical limitは**±15 deg**であり、`|theta| > 15 deg`は絶対FAILとする。

mechanical stopperへの接触自体は直ちにFAILとはしない。構造系審査書の現行実機・構造評価値を以下の基準として使用する。

- backlash全幅: **0.344 deg = 0.00600 rad**
- 回転方向支持剛性: **269.43 N·m/rad**
- stopper構造評価torque: **7.10328 N·m**
- stopper FM相当静的確認: **10.65 N·mを30 s保持**
- 通常制御時必要保持torqueの構造側上限: **2.66526 N·m**
- stopperなし駆動系構造評価torque: **1.21208 N·m**

10.65 N·m試験は静的保持試験であり、高速衝突時の運動energy許容値を直接保証しない。Spicaではstopper contactを以下の3値で区別する。

- `PASS`: `|theta| <= 15 deg`かつ構造確認済みstatic範囲内
- `FAIL`: `|theta| > 15 deg`またはstatic contact torqueが構造評価範囲を超える
- `NEEDS_HW_VALIDATION`: 未実機確認のdynamic impactが発生

stopper contact時には最低限、contact count、first contact time、`theta_dot` at contact、max static contact torque、total contact duration、max absolute fin angleを記録する。

motorを用いた意図的なstopper衝突試験はPhase 6開始条件にしない。High-authority candidateがstopper dynamic contactを必要とする場合にのみ、simulationが要求する最大接触速度まで低速から段階的にqualification testを行う。試験後はbacklash、歯車異音/損傷、AS5047D基準、stopper変形、ガタ増加を確認し、GP22Aを破損させる条件まで上げない。

飛行用software limitは±15 degそのものではなく、fin/stopper組付後にBrake停止角、encoder error、backlash、sensor/estimator/scheduler delay等を実測し、15 degから必要marginを差し引いて決定する。

## 3. CommandReceiveからLiftoffDetectionへのmemory freeze

`CommandReceive -> LiftoffDetection`をdynamic initialization可能期間からflight deterministic runtimeへの境界として扱う。

LiftoffDetectionへ遷移する前に少なくとも以下を完了する。

- 全FreeRTOS Task生成
- 全Task stack確保
- queue/semaphore/event生成
- ICM42688 / AS5047D / I2C / CAN / STS等のdriver `begin()`
- SDMMC mount
- flight log file open
- file I/O buffer設定
- gyro rolling ring buffer確保
- control/estimator/logging/event buffer確保
- ADC calibration handle生成
- timer生成
- internal Flash backup用buffer確保
- flight中に使用するinternal Flash領域の事前erase
- Deep Sleep recovery用RTC state領域準備
- driver/APIのflight中に通るlazy initialization pathの事前実行

StartSequence受理直前にheap integrity、free internal heap、minimum free heap、largest free blockを記録する。

LiftoffDetection以降、application codeでは`new/delete/malloc/calloc/realloc/free`、container capacity growth、Task/queue/semaphore/event新規生成、filesystem mount、未準備file open、大規模local automatic array確保を行わない。

integration testではheap tracingとtask stack high-water markを使い、LiftoffDetection→EngineBurn→Control→Descent、CAN recovery、sensor error、SD/Flash error等を通して予期しないallocation/stack不足がないことを確認する。

## 4. Taskとhardware ownership

最終priority numberとstack sizeは実機計測後に決定するが、責務は以下を基本とする。

| Task | 主責務 | owner |
|---|---|---|
| `SafetyTask` | deployment条件、+17/+25監視、cutoff latch | power safety arbiter |
| `ParachuteTask` | STS3215通信、Open/progress/retry | STS UART |
| `MissionRealtimeTask` | 1 kHz FSM、ICM、AS5047D、fin controller | MissionState、SPI、TB67 output |
| `AirDataTask` | SSC/LPS、filter、airspeed | I2C |
| `CanTask` | CAN RX/TX、bus-off/recovery | CAN/TWAI |
| `CommandWorkerTask` | command dispatch、Calibration、長時間command管理 | device直接ownerにしない |
| `HousekeepingTask` | ADC、LED、低rate Health/時刻 | ADC/LED |
| `InternalFlashTask` | NVS + internal Flash backup | internal Flash |
| `SdLogTask` | Mission microSD | SDMMC |

`MissionState`を書き換えるのは`MissionRealtimeTask`のみとする。

`SafetyTask`はdeployment request/latchを立て、MissionRealtimeTaskが次の1 ms tickでDescentへ遷移する。STS UARTはParachuteTaskのみが操作する。

GPIO40/GPIO44等のpower enableは単一arbiterを通し、`deployment_power_cutoff_latched=true`後は他TaskのON要求で再投入できない構造とする。

## 5. NVS / internal Flashの非critical化

NVS checkpointはreset recoveryの成功率を上げる補助系であり、飛行critical pathのtransaction journalとは扱わない。

飛行中のSequence/liftoff/Open/cutoff等では、まずRAM/RTC上のstateとMission動作を即更新し、NVS保存はbounded queueへnon-blockingで要求する。

NVS queue full、write failure、CRC failure等があっても離床検知、Control、パラシュートOpen、+25秒cutoffを待たせない。失敗時は`persistence_healthy=false`とevent/logを残す。

CommandReceive中のpara Open/Close設定やMotorProfileのように永続化そのものがcommand目的である操作は、保存成功後にactive configを更新してよい。

internal Flash backupは飛行前に必要領域をeraseし、飛行中はpre-erased領域へのappend writeのみとする。eraseは飛行中に行わない。

## 6. 姿勢・fin estimator runtime方針

ICM42688 raw gyro rolling bufferはICM初期化後のCommandReceiveから常時1秒以上保持する。保存対象はsensor timestamp、raw gyro XYZ、validity等とし、liftoff検知時に最新valid gyro biasを適用してreplayする。

replay後の`roll_estimate_liftoff_relative_unwrapped_rad`は離床時刻を0 radとする連続な姿勢推定値であり、Control開始時にresetしない。Mission/Control coordinatorはEngineBurn→Controlのrising edgeで最新valid/fresh sampleを一度だけ`control_roll_reference_unwrapped_rad`へcaptureし、同じsampleによる最初のControl演算より前に`control_roll_reference_valid`を確立する。LQR第1状態は`roll_deviation_unwrapped_rad = roll_estimate_liftoff_relative_unwrapped_rad - control_roll_reference_unwrapped_rad`とし、shortest-path wrapを使用しない。

Control中の再captureは禁止する。reset、新flight epoch、`CancelSequence`、`LiftoffDetectionEmergencyStop`、rollbackではreferenceをinvalidにする。capture tick、estimator timestamp、unwrapped estimate/reference/deviationをsimulation/runtime共通のsource contractへ含める。

1 sample欠落時は1 kHz Control tickを未来sample待ちで停止しない。欠落tickでは直前rateで1 ms積分し、次valid tickではそのrateで1 ms積分することで2 ms全体を前後sampleの台形積分と等価にする。連続欠落許容数1は`TODO(SIMULATION)`とする。

Fin Velocity EstimatorのPhase 5 **1 kHz single + quadratic regression N=3**はhistorical candidateとして保持する。Phase 6/7 revision 3では、1 kHz single、2 kHz 2-point block arithmetic mean、5 kHz 5-point block arithmetic meanの各quadratic N=3/alpha-beta、ideal/empirical capture-order noise・jitter・release delayを再比較する。alpha-beta .40/.35をfinalとせず、必要ならpipelineごとにgrid sweepする。10 kHzはdynamic logがないためstatic sensitivityに限る。

multi-rate blockではraw compensated angleをsampleごとにunwrapしてから平均し、capture timestampをvalid subsample timestampの算術平均、release timestampを最後のsubsample SPI完了時刻とする。estimator/control updateは1 kHzとし、block sizeは1/2/5/10 sampleとする。rawで既存1 kHz estimatorをhigh-rate更新する方式は係数をretuneしないnoise rejection comparatorに限り、production候補にしない。

production estimatorは新結果だけで自動切替せずprovisional candidateとして残す。2 kHzと5 kHzをnoise、delay、steady-state reliability、dynamic error、implementation costのPareto比較で選び、5 kHzを事前採用しない。capture producerと1 kHz deterministic consumerを分離するか、同等にdeadlineを証明し、capture interval、release delay、block group delay、deadline miss/repeated block/coalescingをartifactへ保存する。

現V4 characterization firmwareはAS5047D timer/high-priority producerとrecord assemblerをtask分離しているが、1 kHz assembler wakeをN個のraw sample enqueue完了後に発行している。このためconsumer cadenceはcapture完了へ従属しており、production deadline gateは**FAIL / not proven**とする。static logで再計算したblock cadenceは約999.9996 / 994.6029 / 984.7575 Hz、`encoder_burst_missed_ticks`合計は0 / 270 / 1525、5/10 kHzのmean block group delayは約395.6 / 447.5 usである。これらは現task構成の値でAS5047D sensor limitではない。actual SPI completionと独立controller release timestampは現V4にないため、startup warm-upを許容しても`production_timing_proven=false`を維持し、firmware修正・再測定を`TODO(HW_TEST)`とする。

AS5047D producerはCommandReceive中から開始してよい。`EncoderPipelineState` は`Uninitialized / WarmingUp / Ready / Faulted`とし、complete block、strict monotonic timestamp、filtered angle valid、estimator history、freshnessを満たすまで`Ready`にしない。StartSequence/Control entry時に未Readyならfuture sampleを待たずinput unavailableとする。startup warm-up durationとReady後のsteady-state deadline missを別gateにする。

## 7. AirDataとControl gate

Control用availability判定は一箇所へ集約し、少なくともinitialized、latest valid、freshness、Health、power、必要calibrationをANDする。

初期freshness候補はICM 3 ms、AS5047D 3 ms、SSC 20 ms、LPS25HB 120 msとし、`TODO(SIMULATION)`とする。

LPS25HB/SSCがControlに必要な時点でUnavailableになった場合、そのflightでは復旧後もControlへ再entryしない。

60 m/s gateにはdebounceを持つ。初期候補はentry `>60 m/s` 50 ms連続、stop `<=60 m/s` 20 ms連続とし、Spicaで決定する。

LPS25HB internal averagingはdriver default任せにせず、初期候補pressure/temperatureとも8 samples。Mission側5 sample meanと合わせたdelayをSpicaで評価する。

coefficient robustness simulationではpressure plantの`pitot_coefficient_true`とMission変換の`pitot_coefficient_assumed`を分離する。primary firmware assumptionは`K_assumed=0.92`へ固定し、`K_true=[0.60, 0.70, 0.80, 0.92, 1.00, 1.10, 1.20]`をsweepする。同一係数で生成・復元してmismatchをcancelしてはならない。`K_true=1.00, K_assumed=0.92`はmandatory case、0.60 / 0.92 / 1.00 / 1.20のmatched pairはnoise/delayなしのround-trip consistency testとする。

gain lookupはraw推定速度を保存したまま60..180 m/sのendpointへclampし、low/high diagnostic flagを出す。table外extrapolationは禁止し、coefficient mismatchによるrange外をexceptionにしない。Control gateとgain lookup clampは別責務である。

次のgate policyを同一inputでoffline比較するが、本follow-upでflight policyを自動変更しない。

- current nominal policy: nominal推定airspeedでentry/stop debounce
- coefficient-interval candidate: K=0.60 / 0.92 / 1.20から求めたairspeed min/maxを用いるconservative/hysteretic候補

true / nominal / interval lower / interval upperの60 m/s crossing、Control entry/stop、false early entry、false late/no entry、false early stop、uncertainty-straddling duration、再entry countを保存する。一度しかControlできない契約を維持し、係数uncertaintyを理由に再entryを許可しない。

## 8. パラシュートOpenとDescent fin

Open retryは最初から動かない場合だけでなく途中stallも扱う。

初期候補:

- Open開始0.5 s後の進行量が2 deg未満: retry
- target未到達かつ直近0.5 sの進行量が2 deg未満: retry
- 全体deadlineは最初のOpen commandから5.0 s、retryで延長しない

2 deg/0.5 sは`TODO(HW_TEST)`。

Descent後、finが利用可能なら離床+25 sまでZeroHoldを継続し、+25 sでBrake、Recovery Deep Sleep直前にはStop/Hi-Zへ安全化する。

## 9. Recovery

Recoveryは**Deep Sleepのみ対応**し、Light Sleep fallbackを実装しない。

RecoveryEnter後はSD/Flash flush、安全output、RTC Recovery marker/version/check情報保存を行いDeep Sleepへ入る。

Deep Sleep wakeでは通常flight boot pathへ戻らず、wake causeとRTC markerを確認してRecovery専用boot pathへ入る。Recovery pathでは必要最小限のCAN、ADC、storage/log transfer機能のみ初期化する。

初期候補として10 s periodic wakeを使用し、wake後にbattery ADC、CAN/Recovery statusを更新して短時間command待機後に再Deep Sleepする。wake周期/command window/CAN再initializationは`TODO(HW_TEST)`。

標準remote log dumpはInternal Flash backup。Mission microSD full-rate logはoffset/length指定の部分dumpとする。

Mission→ComBoardは可能ならrequested rangeをCANでComBoard microSDへ先にspoolし、その後Mission BoardをDeep Sleepへ戻してComBoardだけでLoRa送信を継続する。

A6の初期候補をdata 16 byte、5 Hzとすると有効payloadは約80 byte/sで、100 kBの送信に約21分かかる。この程度の時間を前提にInternal Flashを標準remote dumpとする。

### Phase 7: ZeroHold tuning

現Phase 7の`Kp=37.12 N·m/rad`、`Kd=4.736 N·m·s/rad`、torque limit 0.80 N·m、valid `1.5 deg / 2 deg/s / 200 ms`はhistorical provisionalとして削除せず、revisionで同一条件を再評価する。新encoder pipelineとchatter評価に基づき再選定し、結果を自動維持しない。

pipeline comparatorは最低以下を含める。

- 1 kHz single + quadratic N=3 / alpha-beta
- 2 kHz 2-point block arithmetic mean + quadratic N=3 / alpha-beta
- 5 kHz block arithmetic mean + quadratic N=3
- 5 kHz block arithmetic mean + alpha-beta
- 5 kHz block median + quadratic N=3 / alpha-beta
- ideal sensor/timing
- empirical capture-order noise/jitter/release delay

10 kHzはstatic sensitivityに限り、dynamic 10 kHz logがないことを明示する。alpha-beta .40/.35を固定finalとせず、必要ならpipelineごとにgrid sweepする。新結果はprovisional candidateでありproduction estimatorを自動切替しない。

continuous dead-zoneは`dz(x,d)=sign(x)*max(abs(x)-d,0)`とし、angle `[0, 0.002, 0.005, 0.01, 0.02] deg`、rate `[0, 0.1, 0.25, 0.5, 1.0] deg/s`、requested torque dead-zone/hysteresisを比較する。0.01 degを事前採用せず、angle dead-zoneだけで残るD項noiseも評価する。

pure PDとlower-gain PD + direction-dependent TorqueMapper compensation/hysteresisを比較する。mapperはPhase 6のrun-to-run threshold rangeを扱い、単一thresholdやactual torqueを真値としない。torque command zero、mechanical zero、TB67 Stop/Standbyを区別し、Phase 6 same-tick reversal semanticsを維持する。

Phase 7 revisionでは少なくとも以下を保存する。

- max/p95/p99 absolute raw requested torque
- clamped torque RMS/mean absolute value
- valid window raw/clamped torque RMS
- torque saturation fraction、episode count、maximum contiguous duration、valid window saturation duration
- valid成立後の無外乱区間metric
- raw torque / effective duty / bridge direction / mechanical reversalのsign flips per second
- zero crossings/s、same-tick reversals/s
- active duty fraction、stiction dwell fraction
- flip duty regime: below breakaway / intermittent / sustained
- post-valid nonzero-duty fraction、post-valid sub-breakaway-duty fraction
- maximum contiguous nonzero-duty duration、maximum contiguous subthreshold-drive duration
- mean/RMS absolute duty、duty direction dwell
- stiction中nonzero dutyの継続時間
- kinematic holding headroom
- `current_thermal_margin_identified=false`

浮動小数点のraw torque zero crossingをbridge reversalと数えない。angle/rate valid内でもvalid window全体の連続saturation、またはvalid後無外乱区間の継続bridge reversalがあるcaseを良好としない。

raw torque sign flip、clamped torque sign flip、raw duty sign flip、effective duty sign flip、bridge direction flip、mechanical reversal、zero crossing、same-tick reversalを別metricとする。raw torqueが揺れていてもbridge/mechanicalが動かなければ同じchatterと数えない。一方、active duty fractionが高くstiction dwell=1.0ならcurrent/thermal/creepの`TODO(HW_TEST)`を必須とする。

requested-torque dead-zone/hysteresisが100 % saturationになる理由を独立監査する。zero input→zero output、dead-zoneが`|output|`を増加させない、continuous boundary、対称性または明示的方向非対称、hysteresis stateのtick間保持、stateを毎tick初期化しない、rad/deg混在なし、N·mのまま処理、clamp前後の順序、常にtorque limit以内、noise-only入力で常時limitに張り付かないことをunit testする。bugなら修正し、構造上の結果なら最小reproductionと理由を残す。

ZeroHold plant/controller自体はControl roll reference訂正に依存しない。ただしsource contractとControl entry handoffを訂正し、valid tupleは修正referenceでControl entryしたPhase 9評価待ちとする。ZeroHold単体で達成可能という理由だけでflight用確定値にしない。

既存`docs/phase7`と`control_design/99L_zero_hold_candidate.json`は上書きしない。revisionは`docs/phase7_revision2/...`と`control_design/99L_zero_hold_candidate_v2.json`等へ出力し、旧candidateとの定量比較、filter/dead-zone/mapper選択、holding margin、unresolved `TODO(HW_TEST)`を記録する。Phase 7 revisionはPhase 8ではない。

follow-upではrevision 2をbyte-preserveし、`docs/phase7_revision3/...`と`control_design/99L_zero_hold_candidate_revision3.json`へのみ出力する。現Kp/Kd/limit/valid tupleはhistorical/provisional comparatorとし、full-turn Control closed-loopとtiming/fin-installed validation前にflight selectableにしない。Phase 7 revision 3はPhase 8ではない。

### Phase 9: LQR retune + robustness + finalization

#### Coefficient robustness prework（system-ID非依存）

Phase 8開始やPhase 9 final retuneとは別のpreworkとして、現provisional actuator/profileを外部pathから受け取れるdeterministic runnerを用意する。結果は`status=provisional_pre_system_identification`、`phase9_final_retune_performed=false`、`production_selectable=false`、`requires_actuator_reidentification_rerun=true`とする。飛行中のonline coefficient identification、adaptation、gain learning、ARE、case別retuneは禁止し、全caseで同じfixed gain table、fixed `K_assumed=0.92`、fixed gate policyを使う。

最低grid:

- `K_true`: 0.60 / 0.70 / 0.80 / 0.92 / 1.00 / 1.10 / 1.20
- `moving_fin_CN_a_scale_true`: 0.50 / 0.75 / 1.00 / 1.25 / 1.50
- true airspeed: 60 / 80 / 100 / 120 / 140 / 160 / 180 m/s
- authority: Roll Gentle 1.21208 N·m / Roll High-authority 3.0 N·m / Control OFF
- separate comparator: ZeroHold authority 0.80 N·m。Roll Gentleとして扱わない

moving-fin scaleはactual plantのbody roll momentとcommon shaft hinge/aero loadにだけ共通適用し、fixed fins、whole-vehicle `CNalpha_per_rad`、controller nominal Clda/gain/source artifactを変更しない。scale=1でbaseline一致、0以下reject、actual body authority/hinge loadのscale整合をtestする。この0.50..1.50は`TODO(SIMULATION/AERO_VALIDATION)`付きprovisional rangeである。

linear screeningではactual true speed、K mismatch推定speed、endpoint-clamped lookup speed、scheduled gain、`A_true/B_true`、`eig(A_true-B_true*K_scheduled)`、maximum real pole、damping/settling proxyを保存する。K=1.0とCN scale 0.5 / 1.0 / 1.5のrowを必須とし、non-finite、zero/positive pole、range exceptionをrejectする。resultは`pre_system_identification=true`とする。

nonlinear scenarioはEngineBurn→Control entry transient、entry後追加外乱なし、local roll disturbance、full-turn `±180 / ±380 / ±720 deg`、Control OFFを含む。entry transientとpost-entry disturbanceを別caseとして評価し、full-turnだけをrobust gain選択根拠にしない。各caseでentry/stop/reentry count、true/estimated/lookup airspeed、roll deviation/rate、settling/first-valid、raw/clamped torque、saturation、fin angle/rate、motor/gear speedとexceed duration、stopper、Control OFF差、component/overall classificationを保存する。

mandatory acceptanceは、K true 0.60..1.20 × CN scale 0.50..1.50の全gridでexception/NaN/Infなし、K=1.0・CN scale 0.5/1.0/1.5のmandatory row、reference一度だけcapture、意図しないreentryなし、gain range外でcrashなし、hard FAILをcandidate PASSにしないこととする。全cornerがmission性能を満たさない場合は範囲を削らず`SAFE_DEGRADED`または`FAIL`を報告する。

## 13. Simulation判定方針

絶対条件:

- NaN / Inf / solver exceptionは`numeric_classification=FAIL`
- `|theta| > 15 deg`はFAIL
- motor speed > 9800 rpmは`motor_speed_classification=FAIL`
- static stopper contact torqueが構造評価範囲を超えるcaseはFAIL
- 未実機確認のdynamic impactは`NEEDS_HW_VALIDATION`
- GP22A continuous input speed > 6000 rpmはexceed durationを保存し、少なくとも`MISSION_PASS`にしない

各caseへ`stopper_classification`、`motor_speed_classification`、`gearbox_speed_classification`、`numeric_classification`、`control_performance_classification`、`overall_classification`を保存する。`overall_classification`は`FAIL > NEEDS_HW_VALIDATION > SAFE_DEGRADED > MISSION_PASS`のworst-ofであり、post-disturbance windowだけの良好値でwhole-run failureを上書きしない。hard limit違反がなくてもControl no-entry、false early stop、未settleは`SAFE_DEGRADED`とする。

それ以外のroll error、roll-rate、settling、saturation、ZeroHold応答、dropout許容等は事前に根拠なく一値へ固定せず、Codex/解析側が以下を比較して候補と根拠を報告する。

- MotorProfile差
- parameter sensitivity
