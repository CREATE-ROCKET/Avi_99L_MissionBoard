# 99L Mission Board 実装前最終確認・シミュレーション仕様

## 1. 位置付け

本書は、Mission Board本番実装へ進む直前のcross-cuttingな最終確認事項と、実機計測→Spica→firmware定数確定の順序をまとめる。

機能別要求は00〜05、bring-up手順は06を正とし、本書はそれらを実装へ落とす際の統合条件、検証順序、Spicaとの接続条件を定義する。

Spica側は`Natsu-B/Spica_v3.1`を使用する。2026-08-12時点で監査したHEADは`99a3bf295fa1b65fa0f47ba607f4ebf0d6b9d2dd`で、Phase 1〜5相当まで実装済みである。

## 2. 飛行用動翼の絶対制約とstopper

動翼hardware/mechanical limitは**±15 deg**であり、`|theta| > 15 deg`は絶対FAILとする。

mechanical stopperへの接触自体は直ちにFAILとはしない。構造系審査書の現行実機・構造評価値を以下の基準として使用する。

- backlash全幅: **0.344 deg = 0.00600 rad**
- 回転方向支持剛性: **269.43 N·m/rad**
- stopper構造評価torque: **7.10328 N·m**
- stopper FM相当静的確認: **10.65 N·mを30 s保持**
- 通常制御時必要保持torqueの構造側上限: **2.66526 N·m**
- stopperなし駆動系構造評価torque: **1.21208 N·m**

10.65 N·m試験は静的保持試験であり、高速衝突時の運動energy許容値を直接保証しない。Spicaではstopper contactを以下の3値で区別する。

- `PASS`: `|theta| <= 15 deg`かつ構造確認済みstatic範囲内
- `FAIL`: `|theta| > 15 deg`またはstatic contact torqueが構造評価範囲を超える
- `NEEDS_HW_VALIDATION`: 未実機確認のdynamic impactが発生

stopper contact時には最低限、contact count、first contact time、`theta_dot` at contact、max static contact torque、total contact duration、max absolute fin angleを記録する。

motorを用いた意図的なstopper衝突試験はPhase 6開始条件にしない。High-authority candidateがstopper dynamic contactを必要とする場合にのみ、simulationが要求する最大接触速度まで低速から段階的にqualification testを行う。試験後はbacklash、歯車異音/損傷、AS5047D基準、stopper変形、ガタ増加を確認し、GP22Aを破損させる条件まで上げない。

飛行用software limitは±15 degそのものではなく、fin/stopper組付後にBrake停止角、encoder error、backlash、sensor/estimator/scheduler delay等を実測し、15 degから必要marginを差し引いて決定する。

## 3. CommandReceiveからLiftoffDetectionへのmemory freeze

`CommandReceive -> LiftoffDetection`をdynamic initialization可能期間からflight deterministic runtimeへの境界として扱う。

LiftoffDetectionへ遷移する前に少なくとも以下を完了する。

- 全FreeRTOS Task生成
- 全Task stack確保
- queue/semaphore/event生成
- ICM42688 / AS5047D / I2C / CAN / STS等のdriver `begin()`
- SDMMC mount
- flight log file open
- file I/O buffer設定
- gyro rolling ring buffer確保
- control/estimator/logging/event buffer確保
- ADC calibration handle生成
- timer生成
- internal Flash backup用buffer確保
- flight中に使用するinternal Flash領域の事前erase
- Deep Sleep recovery用RTC state領域準備
- driver/APIのflight中に通るlazy initialization pathの事前実行

StartSequence受理直前にheap integrity、free internal heap、minimum free heap、largest free blockを記録する。

LiftoffDetection以降、application codeでは`new/delete/malloc/calloc/realloc/free`、container capacity growth、Task/queue/semaphore/event新規生成、filesystem mount、未準備file open、大規模local automatic array確保を行わない。

integration testではheap tracingとtask stack high-water markを使い、LiftoffDetection→EngineBurn→Control→Descent、CAN recovery、sensor error、SD/Flash error等を通して予期しないallocation/stack不足がないことを確認する。

## 4. Taskとhardware ownership

最終priority numberとstack sizeは実機計測後に決定するが、責務は以下を基本とする。

| Task | 主責務 | owner |
|---|---|---|
| `SafetyTask` | deployment条件、+17/+25監視、cutoff latch | power safety arbiter |
| `ParachuteTask` | STS3215通信、Open/progress/retry | STS UART |
| `MissionRealtimeTask` | 1 kHz FSM、ICM、AS5047D、fin controller | MissionState、SPI、TB67 output |
| `AirDataTask` | SSC/LPS、filter、airspeed | I2C |
| `CanTask` | CAN RX/TX、bus-off/recovery | CAN/TWAI |
| `CommandWorkerTask` | command dispatch、Calibration、長時間command管理 | device直接ownerにしない |
| `HousekeepingTask` | ADC、LED、低rate Health/時刻 | ADC/LED |
| `InternalFlashTask` | NVS + internal Flash backup | internal Flash |
| `SdLogTask` | Mission microSD | SDMMC |

`MissionState`を書き換えるのは`MissionRealtimeTask`のみとする。

`SafetyTask`はdeployment request/latchを立て、MissionRealtimeTaskが次の1 ms tickでDescentへ遷移する。STS UARTはParachuteTaskのみが操作する。

GPIO40/GPIO44等のpower enableは単一arbiterを通し、`deployment_power_cutoff_latched=true`後は他TaskのON要求で再投入できない構造とする。

## 5. NVS / internal Flashの非critical化

NVS checkpointはreset recoveryの成功率を上げる補助系であり、飛行critical pathのtransaction journalとは扱わない。

飛行中のSequence/liftoff/Open/cutoff等では、まずRAM/RTC上のstateとMission動作を即更新し、NVS保存はbounded queueへnon-blockingで要求する。

NVS queue full、write failure、CRC failure等があっても離床検知、Control、パラシュートOpen、+25秒cutoffを待たせない。失敗時は`persistence_healthy=false`とevent/logを残す。

CommandReceive中のpara Open/Close設定やMotorProfileのように永続化そのものがcommand目的である操作は、保存成功後にactive configを更新してよい。

internal Flash backupは飛行前に必要領域をeraseし、飛行中はpre-erased領域へのappend writeのみとする。eraseは飛行中に行わない。

## 6. 姿勢・fin estimator runtime方針

ICM42688 raw gyro rolling bufferはICM初期化後のCommandReceiveから常時1秒以上保持する。保存対象はsensor timestamp、raw gyro XYZ、validity等とし、liftoff検知時に最新valid gyro biasを適用してreplayする。

1 sample欠落時は1 kHz Control tickを未来sample待ちで停止しない。欠落tickでは直前rateで1 ms積分し、次valid tickではそのrateで1 ms積分することで2 ms全体を前後sampleの台形積分と等価にする。連続欠落許容数1は`TODO(SIMULATION)`とする。

Fin Velocity Estimatorは、Spica Phase 5で選ばれた**quadratic regression N=3**を初期production candidateとしてよい。Phase 5の選択はactive motionのRMSE/peak/phase delayではalpha-betaより優位だったが、noiseは実測値ではない。

したがってPhase 6で実機AS5047D/motor noise・vibrationを取り込み、quadratic N=3とalpha-betaを再比較して最終方式を決める。estimator interfaceは差替可能にするがflight中runtime切替は行わない。

## 7. AirDataとControl gate

Control用availability判定は一箇所へ集約し、少なくともinitialized、latest valid、freshness、Health、power、必要calibrationをANDする。

初期freshness候補はICM 3 ms、AS5047D 3 ms、SSC 20 ms、LPS25HB 120 msとし、`TODO(SIMULATION)`とする。

LPS25HB/SSCがControlに必要な時点でUnavailableになった場合、そのflightでは復旧後もControlへ再entryしない。

60 m/s gateにはdebounceを持つ。初期候補はentry `>60 m/s` 50 ms連続、stop `<=60 m/s` 20 ms連続とし、Spicaで決定する。

LPS25HB internal averagingはdriver default任せにせず、初期候補pressure/temperatureとも8 samples。Mission側5 sample meanと合わせたdelayをSpicaで評価する。

## 8. パラシュートOpenとDescent fin

Open retryは最初から動かない場合だけでなく途中stallも扱う。

初期候補:

- Open開始0.5 s後の進行量が2 deg未満: retry
- target未到達かつ直近0.5 sの進行量が2 deg未満: retry
- 全体deadlineは最初のOpen commandから5.0 s、retryで延長しない

2 deg/0.5 sは`TODO(HW_TEST)`。

Descent後、finが利用可能なら離床+25 sまでZeroHoldを継続し、+25 sでBrake、Recovery Deep Sleep直前にはStop/Hi-Zへ安全化する。

## 9. Recovery

Recoveryは**Deep Sleepのみ対応**し、Light Sleep fallbackを実装しない。

RecoveryEnter後はSD/Flash flush、安全output、RTC Recovery marker/version/check情報保存を行いDeep Sleepへ入る。

Deep Sleep wakeでは通常flight boot pathへ戻らず、wake causeとRTC markerを確認してRecovery専用boot pathへ入る。Recovery pathでは必要最小限のCAN、ADC、storage/log transfer機能のみ初期化する。

初期候補として10 s periodic wakeを使用し、wake後にbattery ADC、CAN/Recovery statusを更新して短時間command待機後に再Deep Sleepする。wake周期/command window/CAN再initializationは`TODO(HW_TEST)`。

標準remote log dumpはInternal Flash backup。Mission microSD full-rate logはoffset/length指定の部分dumpとする。

Mission→ComBoardは可能ならrequested rangeをCANでComBoard microSDへ先にspoolし、その後Mission BoardをDeep Sleepへ戻してComBoardだけでLoRa送信を継続する。

A6の初期候補をdata 16 byte、5 Hzとすると有効payloadは約80 byte/sで、100 kBの送信に約21分かかる。この程度の時間を前提にInternal Flashを標準remote dumpとする。

## 10. 実機characterizationからSpicaへの入力

Spicaの最終係数決定前に、Avi_ESP_Libs `refactor`を使用するMission Board実機firmwareで少なくとも以下を記録する。

### 10.1. fin/stopper未装着状態で実施可能

- 5分以上の静置log
- motor ±5/10/15% duty step
- fixed-seed PRBS ±5/10%、必要なら±15%
- coast response
- Brake response
- motor駆動中ICM/AS5047D同時1 kHz log
- logic/motor Vbus
- ICM FIFO lost/full/fault、sensor timestamp
- 1 kHz scheduler/logging jitter
- SD queue drop/最大write latency

このデータからgyro bias/noise/drift、encoder noise、motor dead-zone、voltage-speed response、command→motion delay、effective inertia候補、Coulomb/viscous friction候補、Brake response、motor vibrationのIMU影響を求める。

### 10.2. 構造系審査書から既に使用可能

- backlash全幅 0.344 deg
- support stiffness 269.43 N·m/rad
- hardware limit ±15 deg
- stopper structural eval 7.10328 N·m
- stopper static proof 10.65 N·m / 30 s

これらはPhase 6初期modelへ導入可能である。

### 10.3. fin/stopper組付後に追加で必要

- final software limit用停止margin
- fin/output inertiaを含むresponse
- 最大fin rateからのBrake停止角
- stopper dynamic impact qualification（必要な場合のみ）
- 組立後backlash/compliance再確認
- fin装着時encoder/IMU vibration

### Phase 8: timing/dropout/freshness/AirData

最終的にestimator、ZeroHold、LQR、freshness/debounce/filter、torque/current/PWM saturation、telemetry torque scale、software fin limit等をmachine-readable artifactとして確定し、C++ headerへ自動exportする。MATLABからC++へ手作業転記しない。

Spica/Mission C++で同一test vectorを使用し、gain interpolation、angle wrap、estimator update、TorqueMapper、AirData式、limit処理のparityを確認する。

**独立したPhase 10は設けず、final constants export / firmware parityはPhase 9に含める。**

## 13. Simulation判定方針

絶対条件:

- `|theta| > 15 deg`はFAIL
- static stopper contact torqueが構造評価範囲を超えるcaseはFAIL
- 未実機確認のdynamic impactは`NEEDS_HW_VALIDATION`

それ以外のroll error、roll-rate、settling、saturation、ZeroHold応答、dropout許容等は事前に根拠なく一値へ固定せず、Codex/解析側が以下を比較して候補と根拠を報告する。

- Control ON/OFF同一条件比較
- nominal / worst-case
- Gentle / High-authority
- MotorProfile差
- parameter sensitivity
- Monte Carlo percentile
- maximum/RMS roll angle・rate
- fin angle/rate
- requested/delivered torque
- current/voltage/PWM saturation
- continuous saturation time
- ZeroHold settling/overshoot
- estimator error/lag
- dropout時の安全state遷移
- stopper contact count/speed/torque/duration

simulation終了時は採用候補、棄却候補、margin、Hard Constraint violation、`NEEDS_HW_VALIDATION`、未同定parameter依存性をmachine-readable artifactと人間向けsummaryで残す。
