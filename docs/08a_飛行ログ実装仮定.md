# 99L Mission Board 飛行ログ実装仮定

更新日: 2026-08-16

本書は`05_実装仕様.md`の飛行ログ・Recovery dump実装に対し、既存仕様だけでは一意に決まらない値を固定する。既存仕様と矛盾する場合は既存仕様を優先し、本書を更新する。

## MISSION-LOG-001 Internal Flash backup rate

- microSD primary flight logはMissionRealtimeTaskの1 kHz tickごとに1 recordを生成する。
- Internal Flash backupは同一record streamを20分周し、50 Hzで保存する。
- recordは128 byte固定長とする。
- `flightlog` partitionは2 MiBなので、50 Hzでは最大327.68 s分を保持できる。
- partition満杯時にflight中eraseやwrap-aroundは行わない。以後のbackup recordをdropし、drop counterを増加させる。
- 50 Hzは`00_共通仕様.md`の初期rate指定に従う。最終rateは`TODO(HW_TEST)`として実機storage latencyと必要保持時間から確定する。

## MISSION-LOG-002 RecoveryControl length=0

`0x008 RecoveryControl / StartLogDump`で`length=0`が指定された場合、`offset`からsource末尾までを要求したものとして扱う。

- `offset > source_size`は`InvalidArgument`。
- `offset == source_size`またはsourceが空の場合は直ちに`Complete`。
- `length>0`でsource末尾を越える場合はsource末尾で切り詰める。

これは現行wire仕様が`length=0`の意味を定義していないための仮定である。

## MISSION-LOG-003 microSD latest-flight path

production runtimeは`/sdcard/avi_99l_latest.bin`をlatest flight logとして使用する。

- normal bootではCommandReceive中にmount/openし、`StartSequence`前にtruncateして新flight用に準備する。
- Recovery wake bootではtruncateせずread-onlyでopenする。
- normal bootでSD openが完了していない場合、通常`StartSequence`/`ForceStartSequence`はresource未準備として拒否する。
- SD failureはMission state machineやRecovery entryを永久停止させず、error event/drop counterへ残す。

複数flight履歴の保存規則を別途定義した場合、この固定latest path方式を置換する。

## MISSION-LOG-004 fixed record schema v1

v1 recordは128 byte、explicit little-endian、CRC32付きとする。native struct paddingをwire/storage formatとして使用しない。

現時点でproduction runtimeから観測可能な次の値を保存する。

- monotonic timestamp、flight elapsed、flight epoch、MissionState
- flight/config status、Fin/Parachute mode
- roll、roll rate、fin angle/rate、requested torque
- liftoff-relative roll、control roll reference/deviation
- reference capture tick/timestamp/event sequence、control-roll flags
- LPS pressure/temperature、SSC由来temperature、airspeed、static pressure
- `K_assumed`およびdiagnostic用`K_min/K_max`
- gain table端へのclamp flag
- SD/Internal Flash drop counter

### 未取得値の扱い

`05_実装仕様.md`が要求するFin zeroの詳細値のうち、現在のproduction producerが保持していない値は推定しない。

- encoder zero count: `0xFFFF` sentinel
- measured bidirectional span: IEEE-754 NaN

これらは「測定済み」を意味しない。producer側で実測値を保持できるようになった時点でschema versionを上げるか、reserved fieldの正式利用規則を定義して追加する。

## MISSION-LOG-005 queue/backpressure

- SD log queueとInternal Flash log queueへの投入はMissionRealtimeTaskからnon-blockingで行う。
- queue full時にRealtimeTaskを待たせない。
- drop数は単調増加counterに残し、その後のrecordにも格納する。
- Recovery entry要求後は新規flight record生成を停止し、既存queueをdrainしてからflush完了とする。

この方針によりstorage遅延が1 kHz制御loopを直接blockしないことを優先する。

## MISSION-LOG-006 ExportFlashLogToSdAndErase raw export

`ExportFlashLogToSdAndErase`はInternal Flash backupのrecord解釈結果ではなく、`flightlog` partition全体のraw byte列を保存対象とする。

- record magic/schema/CRCが正常か、途中recordが破損しているか、全領域がerasedかにかかわらず、2 MiB partition全体をそのままmicroSDへ書き出す。
- microSD側はraw export専用fileへtruncate/writeし、`fflush`/`fsync`後に先頭から再読出しする。
- 再読出したfile lengthと全byteがInternal Flash raw内容と一致した場合だけexport成功とする。
- export途中のwrite/read/flush/比較が1つでも失敗した場合はInternal Flashをeraseしない。
- export成功後にのみ`flightlog` partition全体をeraseし、次flightのpre-erased状態とする。
- normal bootそのものをerase条件にしない。前flightのraw dataが残っている場合は自動eraseせず保持し、export完了まで通常`StartSequence`/`ForceStartSequence`をresource未準備として拒否する。
- Recovery wake bootではraw dataを保持し、bootを理由にeraseしない。

この方針により、CRC破損や部分書込みが発生した場合も原因調査に必要なraw evidenceを消去前に保存する。
