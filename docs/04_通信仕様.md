# 99L Mission Board 通信仕様

## 1. 目的

Mission Boardおよび通信基板のmicroSDログが利用できない場合でも、地上局の通信ログのみから、少なくとも以下を事後評価できる通信内容を確保する。

- 離床検知が適切に行われたか
- ロール制御が開始・継続され、要求トルクに応じて動翼が動作したか
- 対気速度・気圧等のControl条件が成立していたか
- パラシュート制御および開傘後の挙動が適切であったか
- 着水等の飛行終了後も、回収に必要なGNSS位置を可能な限り長時間送信できること

## 2. 状態ごとの通信形式

コマンド受信モードの通信形式は、コマンド実装方式への依存が大きいため現時点では未定義とする。

離床検知モード、エンジン燃焼モード、制御モードでは、各状態に異なるHeaderを割り当てる。

これら3状態は基本となるFlightTelemetry形式を共有してよい。状態ごとに必要性の異なる一部フィールドについては、Headerによって解釈が一意に決まるunion領域として共有してよい。

降下モードではFlightTelemetryとは別のDescentTelemetry形式を使用し、開傘条件、パラシュート状態、LPS25HB、GNSS位置等を送信する。

着水等の飛行終了後は、通信基板側の省電力送信モードとしてRecoveryBeaconを使用する。RecoveryBeaconはMission BoardのMissionStateを追加するものではない。

FlightTelemetryおよびDescentTelemetryのLoRa送信は約0.5秒間隔を前提とする。RecoveryBeaconは約10秒間隔を基本とする。

## 3. フレーム長と誤り検出

通信基板からE220へ書き込む送信データは、E220固定アドレス・チャンネルの3 byteを含めて39 byte以下とする。

アプリケーションフレームの誤り検出にはCRC16を使用する。従来のXOR checksumをアプリケーションフレームの誤り検出としては使用しない。

CRC16のvariant、多項式、初期値、反転条件、送信byte orderは実装時に固定する。

0.5秒周期で確実に送信する前提のため、FlightTelemetryにはpacket sequence numberを必須としない。

## 4. FlightTelemetry

離床検知モード、エンジン燃焼モード、制御モードで使用する。

### 4.1. bit幅

FlightTelemetryのbit幅は以下で固定する。byte offsetおよびbit offsetの具体的な並び順は実装時に決定する。

| 項目 | bit数 | 備考 |
|---|---:|---|
| E220固定アドレス・チャンネル | 24 | 現行と同様に3 byte |
| State Header | 8 | LiftoffDetection / EngineBurn / Controlで別Header |
| Status field | 16 | 9 bit使用、残りは予約 |
| ロール角 `φ` | 16 | error用予約値を持てる形式 |
| ロール角速度 `φdot` | 16 | error用予約値を持てる形式 |
| 動翼角 `θ` | 8 | ±15度の物理範囲を利用して圧縮 |
| 動翼角速度 `θdot` | 16 | error用予約値を持てる形式 |
| LPS25HB気圧 | 11 | 800 hPa基準、0.2 hPa/LSB |
| LPS25HB温度 | 8 | errorを予約値で表現可能にする |
| 対気速度 | 8 | errorを予約値で表現可能にする |
| 要求出力軸トルク | 12 | Controller出力 |
| 離床後経過時間 | 8 | 離床前/invalid用予約値を持つ |
| GNSS latitude | 32 | 現行通信基板形式を維持 |
| GNSS longitude | 32 | 現行通信基板形式を維持 |
| GNSS height | 16 | 現行通信基板形式を維持 |
| CRC16 | 16 | アプリケーションフレームCRC |

bit packingした場合の合計は247 bitであり、31 byteに収まる。E220固定アドレス・チャンネル3 byteを含めても39 byte以下とする条件を満たす。

### 4.2. Status field

FlightTelemetryのStatus fieldは16 bitとし、少なくとも以下の9 bitを使用する。

- LPS25HBによる離床検知: 1 bit
- ICM42688による離床検知: 1 bit
- ICM42688生存: 1 bit
- STS3215生存: 1 bit
- ロール制御実行中: 1 bit
- 電池1が接続されていると判定: 1 bit
- 電池2が接続されていると判定: 1 bit
- 通信基板microSD正常: 1 bit
- Mission Boardと通信基板間のCAN通信正常: 1 bit

残り7 bitは予約とする。

電池状態bitは電圧値そのものではなく、Mission Board側で行う電池抜け判定の結果を表す。

SD正常bitは通信基板側microSDの記録状態を示す。

CAN正常bitは、通信基板がMission Boardから継続して有効なCANデータを受信できていることを示す。

### 4.3. ロール・動翼制御値

姿勢はpitch/yawを含むXYZ姿勢ではなく、ロール制御の事後評価に必要なロール角 `φ` およびロール角速度 `φdot` を送信する。

動翼角 `θ` は機構上おおむね±15度に制限されるため、8 bitで表現する。正常範囲外の予約値をAS5047D異常、値無効等のerror codeとして利用できる形式とする。

ロール角、ロール角速度、動翼角速度についても、正常な値として使用しない予約値をerror codeへ使用できる形式とする。

要求出力軸トルクは12 bitとし、Controllerが出力した要求値を送信する。actual PWM値はFlightTelemetry必須項目としない。

各角度・角速度および要求出力軸トルクの具体的な量子化幅、正常値範囲、error codeは別途定義する。

### 4.4. AirData

LPS25HBから算出した高度そのものはFlightTelemetryへ送信せず、気圧と温度を送信する。これにより通信ログから必要に応じて気圧高度を再計算できるようにする。

LPS25HB温度は外気温そのものと同一とはみなさず、LPS25HBが出力した温度として扱う。

LPS25HB気圧は11 bitとし、800 hPaを基準として0.2 hPa/LSBで表現する。シミュレーション上の飛行範囲では800 hPaを下回らない前提とする。上端側の一部コードをerror等に予約する。

LPS25HB温度は8 bitとする。具体的なscale、正常範囲、error codeは別途定義する。

対気速度は8 bitとする。正常飛行範囲外の予約値を利用し、LPS25HB異常、差圧計異常、AirData無効等のerror codeを表現できる形式とする。具体的なscaleおよびerror codeは別途定義する。

### 4.5. 時刻

離床後経過時間は8 bitとする。

離床前には離床後経過時間が未確定であることを表現できる予約値を設ける。具体的な時間分解能と予約値は別途定義する。

### 4.6. 通信基板由来GNSS

GNSS latitude、longitude、heightは現行通信基板の形式を維持する。

- GNSS latitude: 32 bit
- GNSS longitude: 32 bit
- GNSS height: 16 bit

## 5. DescentTelemetry

降下モードではFlightTelemetryとは別のDescentTelemetryへ切り替える。

DescentTelemetryは、どの条件で開傘へ移行したか、パラシュート機構がどの状態にあるか、実際の開傘を示す衝撃を確認できたか、および降下位置を通信ログだけでも追跡できることを目的とする。

### 5.1. bit幅

| 項目 | bit数 | 備考 |
|---|---:|---|
| E220固定アドレス・チャンネル | 24 | 3 byte |
| Descent Header | 8 | 専用Header |
| Status field | 8 | 下記8 bitを使用 |
| LPS25HB気圧 | 11 | 800 hPa基準、0.2 hPa/LSB |
| LPS25HB温度 | 8 | errorおよび電源断を予約値で扱う |
| パラシュートサーボ角度 | 8 | 1 deg/LSB程度を基本とする |
| 離床後経過時間 | 16 | Descent以降の長い時間を扱う |
| GNSS latitude | 32 | 現行形式 |
| GNSS longitude | 32 | 現行形式 |
| GNSS height | 16 | 現行形式 |
| CRC16 | 16 | 必須 |

bit packingした場合の合計は179 bitであり、23 byteに収まる。

### 5.2. Status field

DescentTelemetryのStatus fieldは8 bitとし、以下で使用する。

- LPS25HBによる開傘条件成立: 1 bit
- 経過時間による開傘条件成立: 1 bit
- パラシュートstate: 2 bit
- パラシュート電源遮断済み: 1 bit
- 通信基板microSD正常: 1 bit
- Mission Boardと通信基板間のCAN通信正常: 1 bit
- `DeploymentShockConfirmed`: 1 bit

LPS条件bitと経過時間条件bitは独立して保持し、両条件が成立した場合は両方を1にできる形式とする。

パラシュートstateの2 bitが表す具体的な状態割り当ては別途定義する。

`DeploymentShockConfirmed`はテレメトリ用であり、MissionState遷移、Open retry、電源遮断等の制御条件には使用しない。

### 5.3. LPS25HB

LPS25HB気圧はFlightTelemetryと同じ11 bit、800 hPa基準、0.2 hPa/LSBを使用する。

LPS25HB温度は8 bitとする。LPS25HBの値が取得不能な場合およびLPS25HB側の電源が遮断された場合を、正常温度として使用しない予約値で区別できる形式とする。具体的なcode割り当ては別途定義する。

### 5.4. パラシュート角度

パラシュートサーボ角度は8 bitとし、1 deg/LSB程度を基本とする。具体的な正常角度範囲およびerror codeは別途定義する。

### 5.5. 離床後経過時間

DescentTelemetryの離床後経過時間は16 bitとする。FlightTelemetryとは異なり、Descent後も十分長い時間を表現できるようにする。

具体的な時間分解能は別途定義する。

## 6. RecoveryBeacon

着水等の飛行終了後は、回収に必要な位置情報を可能な限り長時間送信するため、通信基板側でRecoveryBeaconへ移行できる構成とする。

RecoveryBeaconはMission BoardのMissionStateとは独立した通信基板側の省電力送信モードとする。

RecoveryBeaconの送信周期は約10秒を基本とする。

少なくとも以下を送信する。

- 電池電圧
- GNSS latitude
- GNSS longitude
- 離床後経過時間
- CRC16

離床後経過時間は2 byte、すなわち16 bitで送信する。

電池電圧は1系統あたり8 bitで送信する。対象となる電池電圧は12 V以下であることが保証されるものとし、8 bitの正常値領域で0 Vから12 Vまでを表現できる形式とする。具体的なscaleとerror code割り当ては別途定義する。

RecoveryBeaconでは飛行中の詳細テレメトリより回収位置および残電力の把握を優先する。

電池電圧の対象系統数、およびRecoveryBeaconへ移行する具体的な条件は別途定義する。

## 7. bit削減方針

通信テレメトリは39 byte以下に収めることを前提として、以下の方法でbit数を削減する。

- boolean状態はbit fieldへまとめる。
- 動翼角は物理制限±15度を利用して圧縮する。
- LPS25HB気圧は800 hPaからの差分として表現する。
- 正常な物理値として使用しない上端・下端コードをerror codeや電源断状態へ使用する。
- 必要に応じてstate-specific union領域として同じbit位置を再利用してよい。

制御内部の計算精度を通信量子化に合わせて低下させてはならない。bit削減は地上局向けテレメトリ表現にのみ適用する。

## 8. 未定義事項

以下は現時点では未定義とする。

- 各Headerの具体値
- 各フレームの最終byte offset / bit offset
- ロール角、ロール角速度、動翼角、動翼角速度の具体的なscale
- 要求出力軸トルクの通信上の最大値およびscale
- LPS25HB温度のscaleと表現範囲
- 対気速度のscale
- FlightTelemetry離床後経過時間の時間分解能
- DescentTelemetry離床後経過時間の時間分解能
- 各error codeの具体値
- パラシュートstate 2 bitの具体的な状態割り当て
- CRC16 variant、多項式、初期値、反転条件、byte order
- state-specific union領域の具体的な割り当て
- RecoveryBeaconの電池電圧対象系統数およびscale
- RecoveryBeaconへの移行条件
- コマンド受信モードの通信形式
- CAN IDおよびMission Boardと通信基板間のpayload layout
