# 99L Mission Board 通信仕様

## 1. 目的

Mission Boardおよび通信基板のmicroSDログが利用できない場合でも、地上局の通信ログのみから、少なくとも以下を事後評価できる通信内容を確保する。

- 離床検知が適切に行われたか
- ロール制御が開始・継続され、要求torqueに応じて動翼が動作したか
- 対気速度・気圧等のControl条件が成立していたか
- Controlを停止・禁止した理由
- 機軸が鉛直からどちらへどの程度傾いていたか
- パラシュート制御および開傘後の挙動
- 飛行終了後の回収位置

Mission Board由来の物理量およびsemantic errorは**Mission Board側で量子化してからCANへ送信**する。通信基板はMission Board由来値を別scaleへ再量子化しない。

## 2. 通信階層

1. Mission Board内部のSI単位値・semantic error
2. Mission Board→通信基板のClassic CAN量子化済みtelemetry
3. 通信基板→地上局のcompact LoRa telemetry

Mission Board→通信基板の周期telemetryは、生成元と更新周期に合わせて分離する。Kinematics、Control、差圧系由来のairspeedは**100 Hz**、LPS25HBのpressure/temperatureは**25 Hz**、MissionStatus、PowerTime、AttitudeTiltは**10 Hz**を基本とする。

異なる更新周期の値を一つのCAN frameへ集約するためだけに、同じsensor値を高rateで再送しない。通信基板はCAN IDごとに最新値と受信時刻を保持し、LoRa送信時に必要な最新値をsnapshotしてpacketへまとめる。

実機でCAN、task scheduling、通信基板処理、SD logging等に問題が確認された場合は、100 Hz系telemetryを**10 Hz程度**へ変更してよい。runtime adaptive switchingは行わない。LPS25HB telemetryはsensor更新周期に合わせた25 Hzを基本とする。

通信基板はCAN受信telemetryをLoRaへ間引く前にmicroSDへ記録し、少なくとも受信時刻、CAN ID、DLC、raw payloadを保持する。

FlightTelemetry / DescentTelemetry / CommandReceiveTelemetryのLoRa送信は約0.5秒周期を基本とし、RecoveryBeaconは約10秒周期を基本とする。command result、重大event、時刻要求等は通常周期を待たず送信可能とする。

## 3. 共通error表現

通信上のerror codeにはESP-IDFの`esp_err_t`をそのまま格納しない。

`Avi_ESP_Libs/refactor`の`esp_err_t`、driver固有Status、Mission側推定器状態等からsubsystem固有semantic errorへ変換し、その後telemetry予約値へencodeする。

`driver esp_err_t + driver status -> semantic error -> telemetry reserved code`

現在値がvalidなら、一時errorが起きたという理由だけでnumeric値をerror codeへ置換しない。interval event等を併用する。

## 4. Mission Boardと通信基板間CAN

### 4.1. 基本設定

- Classic CAN
- Standard 11-bit ID
- 125 kbit/s
- 8 byte以下
- 新protocolのmulti-byte integerは**little-endian**
- 周期telemetryはmessage種別ごとに8 bit sequence counterを持ち、0→255でwrap
- LoRaにはこのCAN sequenceを必須fieldとして載せない

Emergency、generic command/result、MissionEvent、Recovery control等のevent-driven frameは周期telemetry待ちにしない。

125 kbit/sでの帯域には十分な余裕を持たせる。Control相当で`Kinematics 100 Hz + Control 100 Hz + Airspeed 100 Hz + LPS 25 Hz + Status 10 Hz + Power 10 Hz + Tilt 10 Hz = 355 frame/s`となる。全frameを保守的に8 byte、bit stuffing込み135 bit/frameとして見積もっても47,925 bit/s、bus占有率約38.3 %である。実際にはLPS、Airspeed、Control等は8 byte未満となるため占有率はさらに低い。低IDのEmergency/commandを優先できる余裕を維持する。

### 4.3. 周期telemetry

`KinematicsTelemetry 0x100`は100 Hz基本で、sequence、roll、roll rate、fin angle、fin rateを送る。rollは離床時刻を0 radとする`roll_estimate_liftoff_relative_unwrapped_rad`であり、Control targetを差し引いた値、ランチャー0へresetした値、または表示用wrapped orientationではない。

`ControlTelemetry 0x101`は100 Hz基本で、sequence、requested torque、Flight elapsedを送る。LPS/SSC由来値は本frameへ含めない。

CAN compact telemetryのrollだけからControl referenceを推測しない。Mission Board full-rate logには`control_roll_reference_unwrapped_rad`、valid、capture tick、captureに使用したestimator timestamp、`roll_deviation_unwrapped_rad`を保存し、Control entry orderingとfull-turn偏差を事後検証可能にする。

現行protocol v1のrollは16 bit signed、0.5 deg/LSBで、reserved codeを除くnumeric rangeは-16376.0〜+16383.5 degである。+380 deg、+720 deg、-720 degはそれぞれraw 760、1440、-1440で表現可能である。ただしv1にはControl reference、full-turn deviation、reference capture eventが無いため、Groundがrollだけからこれらを再構成してはならない。

cross-repository follow-upのprotocol v2ではoption Aの**signed accumulated deviation**を採用し、v1 fieldを再解釈せず`ControlRollTelemetryV2 0x10A`を追加する。10 Hz基本とし、reference captureとrange/error変化時は即時送信する。DLC=8のbyte layoutは以下とする。

| byte | 内容 |
|---:|---|
| 0 | sequence u8 |
| 1 | schema version u8 = 2 |
| 2..3 | `control_roll_reference_unwrapped` signed16 LE、0.5 deg/LSB |
| 4..5 | `roll_deviation_unwrapped` signed16 LE、0.5 deg/LSB |
| 6 | flags |
| 7 | reference capture event sequence u8 |

flagsはbit0=`reference_valid`、bit1=`reference_captured_since_previous_frame`、bit2=`control_active`、bit3=`reference_out_of_range`、bit4=`deviation_out_of_range`、bit5..7=0 reservedとする。signed fieldは04aのrollと同じnumeric range/error codeを使用する。range超過時は最大/最小へclampせず、wrapせず、`OUT_OF_RANGE`と対応flagを送る。Mission SDにはwire量子化前のfull-precision SI値を保持する。Mission SDを失った場合、range超過中の正確な値はcompact telemetryから復元不能であることを解析statusに明示する。

`MissionStatusTelemetry 0x102`は10 Hz基本かつ重要状態変更時即時送信とし、MissionState、Flight Status、config flags、FinMode、ParaMode、para angleを送る。

`PowerTimeTelemetry 0x103`は10 Hz基本で、logic/motor voltage、Descent/Recovery elapsed、persistence/storage statusを送る。

`DescentCoreTelemetry 0x104`はDescent中100 Hz基本で、Descent status、para angleを送る。LPS pressure/temperatureは本frameへ重複掲載しない。

`AttitudeTiltTelemetry 0x107`は10 Hz基本で3D表示用tiltを送る。Roll Controllerの制御入力には使用しない。

`LpsTelemetry 0x108`は25 Hz基本で、sequence、LPS pressure、LPS temperatureを送る。LPS25HBの新しいsample周期に合わせ、100 Hz系frameへ同じ値を繰り返し掲載しない。

`AirspeedTelemetry 0x109`は100 Hz基本で、sequence、SSCDRRN005PD2A5の差圧系から算出したairspeedを送る。SSC自体の400 Hz acquisition/filter処理とCAN送信周期は分離し、CANへは100 Hzでpublishする。

### 4.4. MissionState別送信方針

| MissionState | 100 Hz基本 | 25 Hz基本 | 10 Hz基本 | event-driven |
|---|---|---|---|---|
| CommandReceive | 必要時Kinematics / Airspeed | LPS | Status / Power / Tilt | CommandResult / MissionEvent |
| LiftoffDetection | Kinematics / Control / Airspeed | LPS | Status / Power / Tilt | MissionEvent |
| EngineBurn | Kinematics / Control / Airspeed | LPS | Status / Power / Tilt | MissionEvent |
| Control | Kinematics / Control / Airspeed | LPS | Status / Power / Tilt | MissionEvent |
| Descent | Kinematics / DescentCore / Airspeed（AirData電源ON中） | LPS（AirData電源ON中） | Status / Power / Tilt | MissionEvent |
| Recovery Deep Sleep | 通常停止 | 通常停止 | wake時Power/Status | Recovery protocol |

通信基板は各周期telemetryをCAN IDごとに独立してcacheし、最新値と受信時刻を保持する。LoRa packet生成時は必要fieldのlatest valueを組み合わせるため、LPS 25 HzとAirspeed 100 HzをMission Board側で同期させる必要はない。

DescentでもKinematicsを通信基板microSDへ残し、開傘前後のroll/fin挙動を高rateで解析可能にする。AirData電源遮断後はLPS/Airspeedの周期送信を停止し、power/status/eventから停止理由を追跡可能にする。

## 5. Generic command

### 5.1. GenericCommandRequest `0x010`

DLC=8。

| byte | 内容 |
|---:|---|
| 0 | transaction ID |
| 1 | command code |
| 2..7 | args[6] |

transaction IDは`uint8_t`、0を予約、1..255を使用する。pending transactionのIDは再利用しない。

unused argsは必ず0とし、非0なら`InvalidArgument`として拒否する。

Mission Boardは直近のtransaction結果を少なくとも16件cacheし、同一IDかつ同一requestを再受信した場合はcommandを再実行せず結果をreplayする。同一IDで異なるpayloadを再受信した場合は`ProtocolError`とする。

### 5.2. command code

| code | command |
|---:|---|
| `0x01` | `StartSequence` |
| `0x02` | `CancelSequence` |
| `0x03` | `DisableFinControl` |
| `0x10` | `FinFree` |
| `0x11` | `SetFinZero` |
| `0x12` | `StartFinZeroHold` |
| `0x13` | `FinMoveRelative` |
| `0x20` | `ParaFree` |
| `0x21` | `ParaHold` |
| `0x22` | `ParaMoveRelative` |
| `0x23` | `SetParaOpen` |
| `0x24` | `SetParaClose` |
| `0x25` | `ParaOpen` |
| `0x26` | `ParaClose` |
| `0x30` | `RunPreflightCalibration` |
| `0x31` | `ExportFlashLogToSdAndErase` |
| `0x32` | `SelectMotorProfile` |
| `0x33` | `EnterRecovery` |
| `0xF0` | result上の`ActuatorEmergencyStop`識別 |
| `0xF1` | result上の`LiftoffDetectionEmergencyStop`識別 |

`FinMoveRelative`はargs0..1をsigned int16 LE、0.1 deg/LSBとする。

`ParaMoveRelative`はargs0..1をsigned int16 LE、0.1 deg/LSBとし、絶対移動量180 deg未満のみ許可する。

`SetParaOpen` / `SetParaClose`は現在servo位置を保存対象位置とし、args0を方向指定として`1=CW`, `0xFF=CCW`とする。

`SelectMotorProfile`はargs0をprofile IDとする。

`EnterRecovery`はunused argsをすべて0とし、**Descentかつ`DeploymentPowerCutoffDone=true`の場合だけ受理**する。受理時はMission Board自身がRecoveryBeacon移行を決定し、9.1のRecovery移行手順を開始する。地上局または通信基板が本commandを経由せず通信基板だけをRecoveryBeaconへ直接遷移させてはならない。

### 5.3. CommandResult `0x011`

DLC=8。

| byte | 内容 |
|---:|---|
| 0 | transaction ID |
| 1 | command code |
| 2 | phase |
| 3 | reason |
| 4..7 | detail u32 LE |

phaseは`Accepted`, `Completed`, `Rejected`, `Failed`を区別する。reasonは少なくとも`None`, `Busy`, `InvalidState`, `InvalidArgument`, `NotConfigured`, `DeviceUnavailable`, `Timeout`, `Stall`, `ProtocolError`, `InterruptedByEmergency`, `PersistenceError`, `InternalError`, `NotSupported`, `SafetyInterlock`, `AlreadySatisfied`を持つ。

## 6. Emergency command

Emergencyはgeneric requestへ含めない。

### 6.1. ActuatorEmergencyStop `0x001`

DLC=1、byte0=transaction ID。

CommandReceiveのみで受理し、動翼とパラシュートを手で動かせる状態へ移行する。専用解除commandは設けない。

### 6.2. LiftoffDetectionEmergencyStop `0x002`

DLC=1、byte0=transaction ID。

**EngineBurnのみで受理**し、LiftoffDetectionへ巻き戻す。Controlでは受理しない。

受理不能stateでは実行せず、`CommandResult(Rejected, InvalidState)`を返す。

## 7. Time protocol

`TimeRequest 0x012`はDLC1、byte0=request ID。

`TimeResponse/TimeSync 0x013`はrequest ID、source、Unix seconds u32 LE、milliseconds u16 LEを送る。sourceは`0=Invalid`, `1=GNSS`, `2=Ground`。request ID 0はunsolicited GNSS TimeSync用に予約する。

## 8. MissionEventとinterval latch

`MissionEvent 0x020`はevent sequence、flags、MissionState、elapsed、detailを持つ。

flagsは少なくともICM error/data loss、AS5047D error、AirData error、fin motor saturation、reset/recovery、MissionState changed、liftoff detected、parachute Open started、`DeploymentPowerCutoffDone`、persistence error、Mission microSD error、CAN recovery、LiftoffDetectionEmergency rollback、ActuatorEmergencyStop、FinControlDisabledByGround、`ControlRollReferenceCaptured`を表す。

通信基板はevent sequenceでduplicateを排除し、LoRa interval eventへOR latchする。

## 9. Recovery protocol

### 9.1. RecoveryBeacon移行責務

RecoveryBeaconはMissionStateではなく通信基板のPower/communication modeであるが、**移行判断はMission Boardのみが行う**。通信基板はDescent経過時間、last-known MissionState、MissionStatus/CAN timeout、GNSS状態等からRecoveryBeaconへ自律移行してはならない。

Mission Boardの自動移行初期条件はDescentかつ離床後経過時間120秒以上とする。地上局から早期移行を要求する場合も`EnterRecovery 0x33`をMission Boardへ送り、Mission BoardがState/Safety条件を検証して受理した場合だけ移行する。

Mission BoardはRecovery移行を決定した後、安全output、電源遮断、bounded best-effort flush、RTC Recovery marker設定を行い、`RecoveryModeCommand::EnterRecoveryBeacon 0x014`を通信基板へ送る。初期候補として最大1秒のbounded retryを許可するが、CAN不通でRecovery safety処理やDeep Sleepを無期限に待たせない。送信できなかった場合はRecovery専用periodic wakeで再送する。

通信基板は有効な`EnterRecoveryBeacon`を受信した時点でRecoveryBeacon modeをlatchedし、A5を約10秒周期で送信する。Mission Boardから明示的な指示を受信する前にMission linkが失われた場合は`MissionLinkFallback A8`を継続し、120秒等の経過時間だけでA5へ切り替えない。

### 9.2. RecoveryModeCommand `0x014`

Mission→Com、DLC=3。Mission Boardが通信基板のRecoveryBeacon modeを指示するためのidempotent commandとする。

| byte | 内容 |
|---:|---|
| 0 | sequence u8、wrap可 |
| 1 | mode |
| 2 | reason |

modeは`1=EnterRecoveryBeacon`のみを定義し、0および2..255はreservedとする。

reasonは次を定義する。

- 0 `AutoElapsed120`
- 1 `GroundRequested`
- 2 `RecoveryWakeRetry`
- 3 `ResetRecovery`
- 4..255 reserved

同一modeの再受信は副作用なくidempotentに扱い、すでにRecoveryBeacon中なら状態を維持する。通信基板は本frameの受信をMissionState変更として扱わない。

### 9.3. RecoveryControl `0x008`

Com→Mission。Recovery logは部分転送・resumeを明確にするためoffsetとlengthを持つ。DLC=8で以下を基本とする。

| byte | 内容 |
|---:|---|
| 0 | low4=opcode, bit4=source, bit5..7=flags |
| 1 | transfer ID |
| 2..4 | offset u24 LE |
| 5..7 | length u24 LE、0=EOFまで |

opcode:

- 0 reserved（旧`EnterRecovery`。新実装では受理せず`NotSupported`）
- 1 `Wake`
- 2 `StartLogDump`
- 3 `StopLogDump`

source:

- 0 Internal Flash backup
- 1 Mission microSD latest flight

RecoveryBeaconへの移行に本frameを使用しない。

### 9.4. RecoveryStatus `0x105`

transfer ID、status、source、total sizeを返す。Recovery専用bootがCANを再初期化した後、通信基板はこの応答を確認してRecovery log commandを送る。

### 9.5. RecoveryLogData `0x106`

CAN上のlog dataはtransfer ID、sequence、data payloadを持つ。通信基板はsequence/offsetを使用して欠落を検出し、必要offsetから再requestできるようにする。

標準remote dump sourceはInternal Flash backupとする。Mission microSD full-rate logはoffset/length指定の部分dumpを基本とする。

可能ならMission→通信基板はrequested rangeをCANで通信基板microSDへ先にspoolし、Mission Boardは再Deep Sleepして、通信基板だけで時間をかけてLoRa送信する。

A6 log packet初期候補は約32 byte、data 16 byte程度、約5 Hzとする。この場合有効payloadは約80 byte/sなので、100 kBで約21分を要する。packet size/rate/idle timeoutは`TODO(HW_TEST)`とする。

## 10. LoRa compact packing

E220へ書き込むpacketは39 byte以下に収めるが、39 byteを使い切ることを目的にせず、可能な範囲でpacketを小さく保つ。

非byte境界のcompact bit packingを使用する。

- E220固定address/channel 3 byteは先頭の通常byte
- Header以降を本仕様のfield順にpack
- 各fieldはLSB側からpack
- output byte内もbit0→bit7の順
- signed値は指定bit幅のtwo's complement
- checksum直前の最終byte余りbitは0 padding
- XOR対象はHeaderからpaddingを含むchecksum直前byteまで
- E220先頭3 byteとchecksum自身はXOR対象外

Headerは`A0 CommandReceive`, `A1 LiftoffDetection`, `A2 EngineBurn`, `A3 Control`, `A4 Descent`, `A5 RecoveryBeacon`, `A6 RecoveryLogData`, `B0 CommandResult`, `B1 GroundTimeRequest`を使用する。versioned follow-upは`A7 ControlRollTelemetryV2`をadditive packetとして使用し、Mission link fallbackには`A8 MissionLinkFallbackTelemetry`を使用する。旧A3/A5のfield意味や長さを変更しない。

## 11. FlightTelemetry

FlightTelemetryはLiftoffDetection / EngineBurn / Controlで共通fieldを使用し、Headerだけを状態ごとに変える。

主要fieldはStatus 16 bit、roll 16 bit 0.5 deg/LSB、roll rate 16 bit 0.1 deg/s/LSB、tilt magnitude/direction、fin angle 8 bit 0.125 deg/LSB、fin rate 16 bit 0.02 deg/s/LSB、LPS pressure 11 bit、temperature 8 bit、airspeed 8 bit、requested torque 12 bit、elapsed 8 bit、GNSS East/North/height、XORとする。

通信基板はLPS 25 Hz、Airspeed 100 Hz、Control 100 Hz等の独立CAN telemetryから各fieldの最新値を取得してFlightTelemetryを構成する。各CAN frameの受信時刻は独立して管理し、Mission Board側で同一timestampへ揃えるための再送は行わない。

既存の量子化値・semantic error codeは維持する。fin angleはraw0..240を`-15 + raw*0.125 deg`とし、241..255をerror領域とする。`|theta| > 15 deg`は正常値としてencodeしない。

requested torque scaleは`TODO(SIMULATION)`とする。

### 11.1. ControlRollTelemetryV2 follow-up

`A7 ControlRollTelemetryV2`はapplication packet 9 byteとし、Header `A7`、schema version `02`、reference raw16、deviation raw16、flags u8、capture event sequence u8、XOR u8の順に格納する。multi-byte値はLSB-firstとする。A3 Control packetは従来どおり送信し、A7は約0.5 s周期とreference capture/range status変化時に追加送信する。

Groundはwrapped orientationとaccumulated Control deviationを別表示する。表示用orientationは受信したliftoff-relative rollを画面上だけでwrapしてよいが、deviationはA7値をそのまま表示し、ComBoard/Groundが最短角へ再計算しない。`corrective_roll_error_unwrapped` が必要な場合はdeviationの符号反転とし、最短路変換は行わない。

## 12. DescentTelemetry

Descent Statusは13 bitとし、LPS/elapsedによる開傘条件、parachute state、`DeploymentPowerCutoffDone`、通信基板microSD/CAN、DeploymentShockConfirmed、STS3215 faultを含む。

DescentTelemetryのLPS pressure/temperatureは最新の`LpsTelemetry 0x108`から取得し、`DescentCoreTelemetry 0x104`へ重複掲載しない。

`DeploymentPowerCutoffDone`はパラシュートサーボ**および差圧系基板の両方**の電源遮断完了を意味する。

Descent elapsedは16 bit、0.1 s/LSBとする。

## 13. RecoveryBeacon

RecoveryBeaconはMissionStateではなく通信基板側Power/communication modeである。**mode entryの所有者はMission Board**とし、通信基板は`RecoveryModeCommand::EnterRecoveryBeacon 0x014`を有効受信した場合にのみA5送信へ移行する。Mission link timeoutや経過時間を理由に通信基板だけでA5へ遷移しない。

Battery1=logic、Battery2=motor。battery voltageは0.05 V/LSB。GNSS East/North/absolute heightとelapsed 10 s/LSBを送る。

### 13.1. MissionLinkFallbackTelemetry `A8`

Mission Boardからのtelemetryが失われても通信基板、GNSS、LoRa、通信基板microSDが動作している状態を、MissionStateとは別の`MissionLinkFallback` communication modeとして定義する。MissionState `Unknown`をA0 CommandReceiveへ丸めない。

NormalからFallbackへの初期判定は次とする。

- validな`MissionStatusTelemetry`のageが300 msを超えたらA8へ切り替える。
- 300 ms以上1.0 s未満はGround上で`MISSION STATUS LATE`として扱う。
- 1.0 s以上MissionStatusが無い場合、他のMission periodic CANが1.0 s以内なら`MISSION_STATUS_TIMEOUT`、全Mission periodic CANが1.0 s以上無ければ`NO_MISSION_TRAFFIC`とする。
- ComBoard起動後にMissionStatusを一度も受信していない場合は`STARTUP_WAITING`とする。
- CAN bus-off/recovering/controller errorは時間条件を待たずA8理由へ反映してよい。

FallbackからNormalへは、ID、DLC、reserved bit、MissionState enumがvalidな`MissionStatusTelemetry`を**1回受信した時点で即復帰**する。Fallback中に受けたMission向けcommandを復帰後へqueueして実行してはならない。

すでにMission Boardの明示指示によりRecoveryBeacon modeがlatchedされている場合はA5を優先する。一方、Mission Boardが停止・通信断になるまでに明示的なRecoveryBeacon移行指示を受信していなければ、通信基板はA8を継続しRecoveryBeaconへ自律移行しない。

A8 application packet長は24 byteとする。E220 fixed prefix 3 byteとappend RSSIは含めない。

| byte | field | encoding |
|---:|---|---|
| 0 | Header | `0xA8` |
| 1 | schema version | `0x01` |
| 2 | sequence | u8 wrap |
| 3 | primary loss reason | enum |
| 4..5 | status flags | u16 LE |
| 6 | last valid MissionState | 0..4、未受信=`0xFF` |
| 7 | GNSS state | enum |
| 8..9 | MissionStatus age | 0.1 s/LSB、`0xFFFF=never/unavailable` |
| 10..11 | any Mission periodic CAN age | 0.1 s/LSB、`0xFFFF=never/unavailable` |
| 12..13 | last PowerTimeTelemetry age | 0.1 s/LSB、`0xFFFF=never/unavailable` |
| 14..15 | GNSS East | 既存signed16/error raw |
| 16..17 | GNSS North | 既存signed16/error raw |
| 18..19 | GNSS absolute height | 既存9 bit raw、upper 7 bit=0 |
| 20 | last logic voltage | 既存battery raw、liveではない |
| 21 | last motor voltage | 既存battery raw、liveではない |
| 22 | CAN health | enum |
| 23 | XOR | byte 0..22 |

primary loss reason:

- 0 `STARTUP_WAITING`
- 1 `MISSION_STATUS_TIMEOUT`
- 2 `NO_MISSION_TRAFFIC`
- 3 `CAN_BUS_OFF`
- 4 `CAN_RECOVERING`
- 5 `MISSION_STATUS_INVALID`
- 6 `FORCED_TEST`
- 7 `UNKNOWN`
- 8..255 reserved

status flags:

- bit0: valid MissionStatusをboot後に1回以上受信
- bit1: valid Mission periodic CANをboot後に1回以上受信
- bit2: MissionStatus age < 1.0 s
- bit3: any Mission periodic CAN age < 1.0 s
- bit4: ComBoard microSD healthy
- bit5: logging requested
- bit6: logging active
- bit7: unflushed dataあり
- bit8: GNSS enabled
- bit9: GNSS valid numeric fix
- bit10: GNSS stale
- bit11: last PowerTimeTelemetryあり
- bit12: last MissionState valid
- bit13: CAN controller active
- bit14: CAN runtime error
- bit15: reserved=0

GNSS stateは`0=OFF, 1=STARTING, 2=RECEIVER_DETECTED, 3=CONFIGURATION_FAILED, 4=RECEIVER_ERROR, 5=NO_FIX, 6=VALID_FIX, 7=INVALID_SAMPLE, 8=STALE`、9..255 reservedとする。

CAN healthは`0=UNKNOWN, 1=ACTIVE, 2=WARNING, 3=PASSIVE, 4=BUS_OFF, 5=RECOVERING, 6=CONTROLLER_ERROR`、7..255 reservedとする。

A8中のlogic/motor voltageは最後にMission Boardから受信した値でありlive値ではない。Groundは`PowerTime age`を併記し、A8中はbattery remaining-time推定へこのstale値を使用しない。

A8はmode entry、reason/GNSS/CAN health変化時に即時送信し、その後は約0.5秒周期を基本とする。

## 14. CommandReceiveTelemetry

Statusは24 bitとし、ICM/LPS/SSC/AS5047D/STS Health、Fin/Para設定、logic/motor battery、Mission/ComBoard SD、CAN、persistence、fin/para busy、gyro bias、gravity reference、SSC zero、Flash backup、MotorProfile、FinControlDisabled、Calibration busy等を地上で確認できるようにする。

## 15. Ground→通信基板uplink

旧3 byte command形式ではparameterを運べないため、新application uplinkを固定11 byteとする。kindでMissionGeneric、ActuatorEmergency、LiftoffDetectionEmergency、ComBoardLocal、GroundTimeResponseを区別する。

ComBoardLocal commandから通信基板を直接RecoveryBeaconへ遷移させる操作は定義しない。旧実装の`ForceRecoveryBeacon`相当codeは`NotSupported`として扱い、手動Recovery移行が必要な場合はMissionGeneric `EnterRecovery 0x33`を使用してMission Boardに判断させる。

## 16. Protocol golden vectors

compact bit packing、XOR、signed量子化について、Mission C++、通信基板Rust、地上局で共通のgolden vectorを持つ。

各vectorは少なくとも入力物理量、量子化raw値、期待bit列、期待byte列、期待XORを含む。codec変更時は3実装すべてで同じvectorを通す。
