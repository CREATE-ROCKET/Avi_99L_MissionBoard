# 99L Mission Board 通信仕様

## 1. 目的

Mission Boardおよび通信基板のmicroSDログが利用できない場合でも、地上局の通信ログのみから、少なくとも以下を事後評価できる通信内容を確保する。

- 離床検知が適切に行われたか
- ロール制御が開始・継続され、要求torqueに応じて動翼が動作したか
- 対気速度・気圧等のControl条件が成立していたか
- Controlを停止・禁止した理由
- 機軸が鉛直からどちらへどの程度傾いていたか
- パラシュート制御および開傘後の挙動
- 飛行終了後の回収位置

Mission Board由来の物理量およびsemantic errorは**Mission Board側で量子化してからCANへ送信**する。通信基板はMission Board由来値を別scaleへ再量子化しない。

## 2. 通信階層

1. Mission Board内部のSI単位値・semantic error
2. Mission Board→通信基板のClassic CAN量子化済みtelemetry
3. 通信基板→地上局のcompact LoRa telemetry

Mission Board→通信基板の周期telemetryは、生成元と更新周期に合わせて分離する。Kinematics、Control、差圧系由来のairspeedは**100 Hz**、LPS25HBのpressure/temperatureは**25 Hz**、MissionStatus、PowerTime、AttitudeTiltは**10 Hz**を基本とする。

異なる更新周期の値を一つのCAN frameへ集約するためだけに、同じsensor値を高rateで再送しない。通信基板はCAN IDごとに最新値と受信時刻を保持し、LoRa送信時に必要な最新値をsnapshotしてpacketへまとめる。

実機でCAN、task scheduling、通信基板処理、SD logging等に問題が確認された場合は、100 Hz系telemetryを**10 Hz程度**へ変更してよい。runtime adaptive switchingは行わない。LPS25HB telemetryはsensor更新周期に合わせた25 Hzを基本とする。

通信基板はCAN受信telemetryをLoRaへ間引く前にmicroSDへ記録し、少なくとも受信時刻、CAN ID、DLC、raw payloadを保持する。

FlightTelemetry / DescentTelemetry / CommandReceiveTelemetryのLoRa送信は約0.5秒周期を基本とし、RecoveryBeaconは約10秒周期を基本とする。command result、重大event、時刻要求等は通常周期を待たず送信可能とする。

## 3. 共通error表現

通信上のerror codeにはESP-IDFの`esp_err_t`をそのまま格納しない。

`Avi_ESP_Libs/refactor`の`esp_err_t`、driver固有Status、Mission側推定器状態等からsubsystem固有semantic errorへ変換し、その後telemetry予約値へencodeする。

`driver esp_err_t + driver status -> semantic error -> telemetry reserved code`

現在値がvalidなら、一時errorが起きたという理由だけでnumeric値をerror codeへ置換しない。interval event等を併用する。

## 4. Mission Boardと通信基板間CAN

### 4.1. 基本設定

- Classic CAN
- Standard 11-bit ID
- 125 kbit/s
- 8 byte以下
- 新protocolのmulti-byte integerは**little-endian**
- 周期telemetryはmessage種別ごとに8 bit sequence counterを持ち、0→255でwrap
- LoRaにはこのCAN sequenceを必須fieldとして載せない

Emergency、generic command/result、MissionEvent、Recovery control等のevent-driven frameは周期telemetry待ちにしない。

125 kbit/sでの帯域には十分な余裕を持たせる。Control相当で`Kinematics 100 Hz + Control 100 Hz + Airspeed 100 Hz + LPS 25 Hz + Status 10 Hz + Power 10 Hz + Tilt 10 Hz = 355 frame/s`となる。全frameを保守的に8 byte、bit stuffing込み135 bit/frameとして見積もっても47,925 bit/s、bus占有率約38.3 %である。実際にはLPS、Airspeed、Control等は8 byte未満となるため占有率はさらに低い。低IDのEmergency/commandを優先できる余裕を維持する。

| `0x010` | Com→Mission | `GenericCommandRequest` |
| `0x011` | Mission→Com | `CommandResult` |
| `0x012` | Mission→Com | `TimeRequest` |
| `0x013` | Com→Mission | `TimeResponse` / periodic TimeSync |
| `0x020` | Mission→Com | `MissionEvent` |
| `0x100` | Mission→Com | `KinematicsTelemetry` |
| `0x101` | Mission→Com | `ControlTelemetry` |
| `0x102` | Mission→Com | `MissionStatusTelemetry` |
| `0x103` | Mission→Com | `PowerTimeTelemetry` |
| `0x104` | Mission→Com | `DescentCoreTelemetry` |

### 4.3. 周期telemetry

`KinematicsTelemetry 0x100`は100 Hz基本で、sequence、roll、roll rate、fin angle、fin rateを送る。

`ControlTelemetry 0x101`は100 Hz基本で、sequence、requested torque、Flight elapsedを送る。LPS/SSC由来値は本frameへ含めない。

`MissionStatusTelemetry 0x102`は10 Hz基本かつ重要状態変更時即時送信とし、MissionState、Flight Status、config flags、FinMode、ParaMode、para angleを送る。

`PowerTimeTelemetry 0x103`は10 Hz基本で、logic/motor voltage、Descent/Recovery elapsed、persistence/storage statusを送る。

`DescentCoreTelemetry 0x104`はDescent中100 Hz基本で、Descent status、para angleを送る。LPS pressure/temperatureは本frameへ重複掲載しない。

`AttitudeTiltTelemetry 0x107`は10 Hz基本で3D表示用tiltを送る。Roll Controllerの制御入力には使用しない。

`LpsTelemetry 0x108`は25 Hz基本で、sequence、LPS pressure、LPS temperatureを送る。LPS25HBの新しいsample周期に合わせ、100 Hz系frameへ同じ値を繰り返し掲載しない。

`AirspeedTelemetry 0x109`は100 Hz基本で、sequence、SSCDRRN005PD2A5の差圧系から算出したairspeedを送る。SSC自体の400 Hz acquisition/filter処理とCAN送信周期は分離し、CANへは100 Hzでpublishする。

### 4.4. MissionState別送信方針

| MissionState | 100 Hz基本 | 25 Hz基本 | 10 Hz基本 | event-driven |
|---|---|---|---|---|
| CommandReceive | 必要時Kinematics / Airspeed | LPS | Status / Power / Tilt | CommandResult / MissionEvent |
| LiftoffDetection | Kinematics / Control / Airspeed | LPS | Status / Power / Tilt | MissionEvent |
| EngineBurn | Kinematics / Control / Airspeed | LPS | Status / Power / Tilt | MissionEvent |
| Control | Kinematics / Control / Airspeed | LPS | Status / Power / Tilt | MissionEvent |
| Descent | Kinematics / DescentCore / Airspeed（AirData電源ON中） | LPS（AirData電源ON中） | Status / Power / Tilt | MissionEvent |
| Recovery Deep Sleep | 通常停止 | 通常停止 | wake時Power/Status | Recovery protocol |

通信基板は各周期telemetryをCAN IDごとに独立してcacheし、最新値と受信時刻を保持する。LoRa packet生成時は必要fieldのlatest valueを組み合わせるため、LPS 25 HzとAirspeed 100 HzをMission Board側で同期させる必要はない。

DescentでもKinematicsを通信基板microSDへ残し、開傘前後のroll/fin挙動を高rateで解析可能にする。AirData電源遮断後はLPS/Airspeedの周期送信を停止し、power/status/eventから停止理由を追跡可能にする。

## 5. Generic command

### 5.1. GenericCommandRequest `0x010`

DLC=8。

| byte | 内容 |
|---:|---|
| 0 | transaction ID |
| 1 | command code |
| 2..7 | args[6] |

transaction IDは`uint8_t`、0を予約、1..255を使用する。pending transactionのIDは再利用しない。

unused argsは必ず0とし、非0なら`InvalidArgument`として拒否する。

Mission Boardは直近のtransaction結果を少なくとも16件cacheし、同一IDかつ同一requestを再受信した場合はcommandを再実行せず結果をreplayする。同一IDで異なるpayloadを再受信した場合は`ProtocolError`とする。

### 5.2. command code

| code | command |
|---:|---|
| `0x01` | `StartSequence` |
| `0x02` | `CancelSequence` |
| `0x03` | `DisableFinControl` |
| `0x10` | `FinFree` |
| `0x11` | `SetFinZero` |
| `0x12` | `StartFinZeroHold` |
| `0x13` | `FinMoveRelative` |
| `0x20` | `ParaFree` |
| `0x21` | `ParaHold` |
| `0x22` | `ParaMoveRelative` |
| `0x23` | `SetParaOpen` |
| `0x24` | `SetParaClose` |
| `0x25` | `ParaOpen` |
| `0x26` | `ParaClose` |
| `0x30` | `RunPreflightCalibration` |
| `0x31` | `ExportFlashLogToSdAndErase` |
| `0x32` | `SelectMotorProfile` |
| `0xF0` | result上の`ActuatorEmergencyStop`識別 |
| `0xF1` | result上の`LiftoffDetectionEmergencyStop`識別 |

`FinMoveRelative`はargs0..1をsigned int16 LE、0.1 deg/LSBとする。

`ParaMoveRelative`はargs0..1をsigned int16 LE、0.1 deg/LSBとし、絶対移動量180 deg未満のみ許可する。

`SetParaOpen` / `SetParaClose`は現在servo位置を保存対象位置とし、args0を方向指定として`1=CW`, `0xFF=CCW`とする。

`SelectMotorProfile`はargs0をprofile IDとする。

### 5.3. CommandResult `0x011`

DLC=8。

| byte | 内容 |
|---:|---|
| 0 | transaction ID |
| 1 | command code |
| 2 | phase |
| 3 | reason |
| 4..7 | detail u32 LE |

phaseは`Accepted`, `Completed`, `Rejected`, `Failed`を区別する。reasonは少なくとも`None`, `Busy`, `InvalidState`, `InvalidArgument`, `NotConfigured`, `DeviceUnavailable`, `Timeout`, `Stall`, `ProtocolError`, `InterruptedByEmergency`, `PersistenceError`, `InternalError`, `NotSupported`, `SafetyInterlock`, `AlreadySatisfied`を持つ。

## 6. Emergency command

Emergencyはgeneric requestへ含めない。

### 6.1. ActuatorEmergencyStop `0x001`

DLC=1、byte0=transaction ID。

CommandReceiveのみで受理し、動翼とパラシュートを手で動かせる状態へ移行する。専用解除commandは設けない。

### 6.2. LiftoffDetectionEmergencyStop `0x002`

DLC=1、byte0=transaction ID。

**EngineBurnのみで受理**し、LiftoffDetectionへ巻き戻す。Controlでは受理しない。

受理不能stateでは実行せず、`CommandResult(Rejected, InvalidState)`を返す。

## 7. Time protocol

`TimeRequest 0x012`はDLC1、byte0=request ID。
`TimeResponse/TimeSync 0x013`はrequest ID、source、Unix seconds u32 LE、milliseconds u16 LEを送る。sourceは`0=Invalid`, `1=GNSS`, `2=Ground`。request ID 0はunsolicited GNSS TimeSync用に予約する。

## 8. MissionEventとinterval latch

`MissionEvent 0x020`はevent sequence、flags、MissionState、elapsed、detailを持つ。

flagsは少なくともICM error/data loss、AS5047D error、AirData error、fin motor saturation、reset/recovery、MissionState changed、liftoff detected、parachute Open started、`DeploymentPowerCutoffDone`、persistence error、Mission microSD error、CAN recovery、LiftoffDetectionEmergency rollback、ActuatorEmergencyStop、FinControlDisabledByGroundを表す。

通信基板はevent sequenceでduplicateを排除し、LoRa interval eventへOR latchする。

## 9. Recovery protocol

### 9.1. RecoveryBeacon移行

通信基板はDescentかつ離床後経過時間が120秒以上である場合を自動RecoveryBeacon移行の初期条件とする。elapsedを確定できない場合は自動移行しない。通信基板local commandによる`ForceRecoveryBeacon`は許可する。

RecoveryBeaconへ移行する際、通信基板はMission Boardへ`RecoveryControl::EnterRecovery`を送る。Mission Boardは可能なら`RecoveryStatus`を返し、必要なSD/Flash flushと安全化後に**Deep Sleep**へ入る。Light Sleep fallbackは持たない。Mission BoardからACKを得られなくても通信基板自身のRecoveryBeacon移行を妨げない。

Deep Sleepからの復帰は通常flight boot pathと分離し、RTC Recovery markerとwake causeを確認してRecovery専用boot pathへ入る。初期候補として10秒periodic wakeを使用する。

### 9.2. RecoveryControl `0x008`

Recovery logは部分転送・resumeを明確にするためoffsetとlengthを持つ。DLC=8で以下を基本とする。

| byte | 内容 |
|---:|---|
| 0 | low4=opcode, bit4=source, bit5..7=flags |
| 1 | transfer ID |
| 2..4 | offset u24 LE |
| 5..7 | length u24 LE、0=EOFまで |

opcode:

- 0 `EnterRecovery`
- 1 `Wake`
- 2 `StartLogDump`
- 3 `StopLogDump`

source:

- 0 Internal Flash backup
- 1 Mission microSD latest flight

### 9.3. RecoveryStatus `0x105`

transfer ID、status、source、total sizeを返す。Recovery専用bootがCANを再初期化した後、通信基板はこの応答を確認して本commandを送る。

### 9.4. RecoveryLogData `0x106`

CAN上のlog dataはtransfer ID、sequence、data payloadを持つ。通信基板はsequence/offsetを使用して欠落を検出し、必要offsetから再requestできるようにする。

標準remote dump sourceはInternal Flash backupとする。Mission microSD full-rate logはoffset/length指定の部分dumpを基本とする。

可能ならMission→通信基板はrequested rangeをCANで通信基板microSDへ先にspoolし、Mission Boardは再Deep Sleepして、通信基板だけで時間をかけてLoRa送信する。

A6 log packet初期候補は約32 byte、data 16 byte程度、約5 Hzとする。この場合有効payloadは約80 byte/sなので、100 kBで約21分を要する。packet size/rate/idle timeoutは`TODO(HW_TEST)`とする。

## 10. LoRa compact packing

E220へ書き込むpacketは39 byte以下に収めるが、39 byteを使い切ることを目的にせず、可能な範囲でpacketを小さく保つ。

非byte境界のcompact bit packingを使用する。

- E220固定address/channel 3 byteは先頭の通常byte
- Header以降を本仕様のfield順にpack
- 各fieldはLSB側からpack
- output byte内もbit0→bit7の順
- signed値は指定bit幅のtwo's complement
- checksum直前の最終byte余りbitは0 padding
- XOR対象はHeaderからpaddingを含むchecksum直前byteまで
- E220先頭3 byteとchecksum自身はXOR対象外

Headerは`A0 CommandReceive`, `A1 LiftoffDetection`, `A2 EngineBurn`, `A3 Control`, `A4 Descent`, `A5 RecoveryBeacon`, `A6 RecoveryLogData`, `B0 CommandResult`, `B1 GroundTimeRequest`を使用する。

## 11. FlightTelemetry

FlightTelemetryはLiftoffDetection / EngineBurn / Controlで共通fieldを使用し、Headerだけを状態ごとに変える。

主要fieldはStatus 16 bit、roll 16 bit 0.5 deg/LSB、roll rate 16 bit 0.1 deg/s/LSB、tilt magnitude/direction、fin angle 8 bit 0.125 deg/LSB、fin rate 16 bit 0.02 deg/s/LSB、LPS pressure 11 bit、temperature 8 bit、airspeed 8 bit、requested torque 12 bit、elapsed 8 bit、GNSS East/North/height、XORとする。

通信基板はLPS 25 Hz、Airspeed 100 Hz、Control 100 Hz等の独立CAN telemetryから各fieldの最新値を取得してFlightTelemetryを構成する。各CAN frameの受信時刻は独立して管理し、Mission Board側で同一timestampへ揃えるための再送は行わない。

既存の量子化値・semantic error codeは維持する。fin angleはraw0..240を`-15 + raw*0.125 deg`とし、241..255をerror領域とする。`|theta| > 15 deg`は正常値としてencodeしない。

## 12. DescentTelemetry

Descent Statusは13 bitとし、LPS/elapsedによる開傘条件、parachute state、`DeploymentPowerCutoffDone`、通信基板microSD/CAN、DeploymentShockConfirmed、STS3215 faultを含む。

DescentTelemetryのLPS pressure/temperatureは最新の`LpsTelemetry 0x108`から取得し、`DescentCoreTelemetry 0x104`へ重複掲載しない。

`DeploymentPowerCutoffDone`はパラシュートサーボ**および差圧系基板の両方**の電源遮断完了を意味する。

Descent elapsedは16 bit、0.1 s/LSBとする。

## 13. RecoveryBeacon
RecoveryBeaconはMissionStateではなく通信基板側Power/communication modeである。

Battery1=logic、Battery2=motor。battery voltageは0.05 V/LSB。GNSS East/North/absolute heightとelapsed 10 s/LSBを送る。

## 14. CommandReceiveTelemetry

Statusは24 bitとし、ICM/LPS/SSC/AS5047D/STS Health、Fin/Para設定、logic/motor battery、Mission/ComBoard SD、CAN、persistence、fin/para busy、gyro bias、gravity reference、SSC zero、Flash backup、MotorProfile、FinControlDisabled、Calibration busy等を地上で確認できるようにする。

## 15. Ground→通信基板uplink

旧3 byte command形式ではparameterを運べないため、新application uplinkを固定11 byteとする。kindでMissionGeneric、ActuatorEmergency、LiftoffDetectionEmergency、ComBoardLocal、GroundTimeResponseを区別する。

## 16. Protocol golden vectors

compact bit packing、XOR、signed量子化について、Mission C++、通信基板Rust、地上局で共通のgolden vectorを持つ。

各vectorは少なくとも入力物理量、量子化raw値、期待bit列、期待byte列、期待XORを含む。codec変更時は3実装すべてで同じvectorを通す。
