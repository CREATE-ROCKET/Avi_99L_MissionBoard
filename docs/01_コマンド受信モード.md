# 99L Mission Board コマンド受信モード仕様

> **2026-08-16更新:** パラシュートのOpen/Close、STS3215 Hold、NVS、readiness、廃止commandについては[[08e_20260816_パラシュート簡素化|08e パラシュート簡素化仕様]]を優先する。本書に残る絶対角endpoint、NVS、Free、Open retryの旧記述は当該範囲では廃止。


## 1. 前提

コマンド受信モードは電源投入直後の準備状態である。

この時点では以下が未接続でも許容する。

- 動翼モータ系統
- パラシュートサーボ
- 気圧計・差圧計系統

デバイスが未接続または正常動作していないこと自体を理由にMission Boardの起動を禁止しない。

通常の`StartSequence`は飛行準備条件を確認する。protocol/state/Busy/resource条件を通過すればまず`Accepted`とし、非同期preparationで必須設定・校正5項目の不足が判明した場合はterminal `Failed / NotConfigured`と5 bit missing maskを返す。競合処理中は`Busy`として受理しない。

一方、operatorが初期セットアップ不足のriskを認識した上でsequence開始を優先するため、`ForceStartSequence`を別commandとして設ける。`ForceStartSequence`は通常Startが確認する**5項目の初期セットアップNotConfigured gateだけをbypass**してLiftoffDetectionへの遷移を試みる非常用操作であり、Healthやruntime safetyを正常扱いにする機能ではない。詳細は[[04c_ForceStartSequence詳細|ForceStartSequence詳細]]に従う。

CommandReceiveでは各種driverのbring-up、校正、設定、Flash backup export等を何度でも実行可能にする。初期実装段階の検証方法は[[06_初期実装・検証仕様|初期実装・検証仕様]]に従う。

## 2. 起動直後のアクチュエータ安全化

driverやtaskの初期化より先に、アクチュエータへ意図しない出力が出ないGPIO状態を確立する。

最低限、起動直後は以下とする。

- TB67H450FNG IN1/IN2をLOWとしてStop / Hi-Z
- `+5V_short` EnableをLOW
- パラシュート系EnableをLOW

`+5V`常時ON系統とGPIO40で制御する`+5V_short`を混同しない。

その後に必要な電源・通信を段階的に有効化する。

通常のCommandReceive動作では、動翼とパラシュートを現在位置で固定することを試みる。

動翼はエンコーダから現在角度を取得できた場合はその位置で保持し、取得不能の場合はbest effortでBrakeとする。パラシュートサーボは現在角度を取得できた場合はその位置をHoldし、取得不能の場合はbest effortの安全化を行う。

bring-up用motor試験はboot時に自動実行せず、RAM-onlyの明示的なarm状態を経た場合だけ許可する。再起動時は必ずdisarmから開始する。

## 3. デバイス再接続

CommandReceive中は未接続または正常動作していないデバイスに対して1秒ごとに接続・動作確認を再試行する。

正常に動作するようになった場合はHealthおよび地上局telemetryを更新する。

actuatorの再接続時は現在の安全要求を維持する。動翼はrequested `FinMode`を維持する。パラシュートはFreeを使用せず、`ActuatorEmergencyStop`後を含め、電源遮断済みでなければ現在位置Holdをbest effortで再確立する。

`Avi_ESP_Libs/refactor`は本Mission Boardで十分に実機検証されていないため、Mission本実装より先に今回使用するAPIを個別に実機検証する。library側の責務に属する不具合をMission Board側のad-hoc workaroundで隠さない。

## 4. CANおよびLoRa通信

CommandReceiveではCANにより通信基板と通信できるか確認し、通信基板からLoRaを介した地上局との通信状態を取得する。

CANまたはLoRa通信が確立していない場合は通信回復を試みる。CANがbus-off等になった場合はCAN recoveryを行う。

すでに受理して実行を開始した通常コマンドは、CANまたはLoRa通信が途切れても中断しない。

Mission Board向け通常コマンドはgeneric command request/result形式を使用する。具体的なwire formatは[[04_通信仕様|通信仕様]]および[[04c_ForceStartSequence詳細|ForceStartSequence詳細]]に従う。

## 5. コマンド実行モデル

動翼系、パラシュート系、校正・storage系は互いに可能な範囲で並列実行可能とする。

同一系統で通常コマンド実行中に、その系統の別の通常コマンドを受信した場合はqueueに入れず`Busy`として拒否する。

通常のStop/Free系commandは別の通常commandを暗黙に割り込ませない。Emergencyのみ通常commandへ割込み可能とする。

`StartSequence`および`ForceStartSequence`受理時に競合する動翼、パラシュート、Calibration、Flash export/erase、bring-up motor試験等が実行中の場合は`Busy`として拒否する。Forceは5項目の初期セットアップgateだけをbypassする操作であり、同一deviceを複数ownerが同時操作するような実行時排他をbypassしない。

`RunPreflightCalibration`は静置状態を前提とするため、実行中は動翼・パラシュートを動かす通常command、bring-up用motor試験、`StartSequence`および`ForceStartSequence`を`Busy`として拒否する。CAN telemetry、sensor取得、通常loggingは継続してよい。

逆に動翼・パラシュート駆動commandまたはbring-up motor試験中も`RunPreflightCalibration`を`Busy`として拒否する。

長時間commandは`Accepted`と最終`Completed/Failed`を分離して通知する。`StartSequence`と`ForceStartSequence`もprotocol/state/Busy/resource条件を通過した時点で`Accepted`を返し、その後のpreparationはParachuteTask等で非同期に実行する。通常Startの5項目不足はterminal `Failed / NotConfigured / detail=missing mask`とし、Forceはその5項目だけをbypassする。

## 6. CommandReceiveで使用する主なgeneric command

少なくとも以下を用意する。

- `StartSequence`
- `ForceStartSequence`
- `FinFree`
- `SetFinZero`
- `StartFinZeroHold`
- `FinMoveRelative`
- `ParaOpen`
- `ParaClose`
- `RunPreflightCalibration`
- `ExportFlashLogToSdAndErase`

パラシュートの`0x20..0x24`は旧wire codeとして予約するが、Mission Boardは常に`Rejected / NotSupported`とし、副作用を発生させない。

`CancelSequence`および`DisableFinControl`もgeneric commandであるが、受理するMissionStateは飛行シーケンス側で定義する。

MotorProfileはruntime commandで変更しない。選択は9章のcompile-time設定だけで行う。

## 7. ActuatorEmergencyStop

`ActuatorEmergencyStop`は[[02_飛行シーケンス|飛行シーケンス]]の`LiftoffDetectionEmergencyStop`とは別commandであり、通常generic commandとは別の専用Emergency messageとする。

**CommandReceiveでのみ受理**する。

受理した場合は実行中の動翼・パラシュート操作へ割り込む。動翼は既定のEmergency安全状態であるFree/Coastへ移行する。パラシュートはFreeまたはpower-offへ移行せず、電源遮断済みでなければ現在位置Holdを要求する。

この操作は専用Emergency latchを追加するものではない。動翼はその後の通常commandでrequested modeを変更できる。パラシュートは`ParaOpen` / `ParaClose`を受理するまでHoldを維持し、飛行中は離床+25秒absolute cutoffまでHold/Torque ONを維持する。

割り込まれた通常commandは`InterruptedByEmergency`相当の失敗として結果を返す。

## 8. 動翼試験操作

CommandReceiveでは以下を操作できる。

- Free / Stop状態へ移行し、手で動かせるようにする
- 現在位置を論理上の動翼角0度として設定する
- 動翼角0度保持を開始する
- 相対角度を指定して移動する

動翼角0度設定と0度保持開始は別操作とする。

相対角度指定は0.1度単位とし、エンコーダが正常に利用できる場合のみ実行する。保持状態から相対移動した場合は移動完了後に新しい位置の保持状態へ戻る。

相対移動のtorque、stall判定、ZeroHold係数等は初期値を置いて実装してよいが、simulationまたは実機で最終決定する値には`TODO(SIMULATION)` / `TODO(HW_TEST)`を残す。

`SetFinZero`が正常に完了した場合のみ`FinZeroConfigured=true`とする。Mission Board reset時は必ず未設定へ戻す。

現在のbring-up状態では動翼本体・stopperがなくmotorは360度以上連続回転可能である。bring-up motor testへ飛行用±15度software limitを適用せず、test専用duty/speed/time limitを使用する。飛行用software limitは動翼・stopper取付後に決定する。

## 9. MotorProfile

動翼motorには予備個体があるため、motor依存値をcontrollerやTorqueMapperへ直接散在させず、profile IDごとの`MotorProfile`としてまとめる。

`MotorProfile`には少なくともprofile ID、motor電気定数、駆動系効率、current/torque limit、ZeroHold tuning、必要に応じたControl tuning/tableを持たせる。

飛行firmwareが使用するMotorProfileは**build時に固定**する。build systemからcompile definition `AVI_99L_MOTOR_PROFILE_ID`を必ず指定し、source側は次のfail-closed規則を持つ。

- `AVI_99L_MOTOR_PROFILE_ID`が未定義なら`#error`でbuildを失敗させる。
- 定義されたIDに対応するMotorProfileが存在しなければ`#error`でbuildを失敗させる。
- build後のfirmwareではactive MotorProfileをruntime変更しない。
- MotorProfile IDをNVS/Flashから選択・上書き・復元しない。
- 地上局/CAN/LoRaからMotorProfileを変更するcommandは定義しない。
- MotorProfileを変更する場合はbuild設定を変更してfirmwareを再build・再書込みする。

`MotorProfileValid`は、compile-timeで選択されたprofileが存在し、そのprofileの飛行に必要なparameters/qualification flagがvalidであることを表す。未qualification profileを明示的にbuild対象へ選択すること自体は許容できるが、その場合`MotorProfileValid=false`とし通常`StartSequence`を`NotConfigured`で拒否する。`ForceStartSequence`はこのgateだけをbypassできる。

profile変更はfirmware再書込みを伴うためresetが発生し、`FinZeroConfigured`は通常のreset規則により未設定へ戻る。runtime profile変更専用の追加無効化処理は設けない。

MotorPolarityもruntime変更しない。選択MotorProfileまたはcompile-time board configurationに属する静的値として扱い、実機低duty試験で確定する。

## 10. PreflightCalibration

`RunPreflightCalibration`を何度でも実行可能にする。

1回のattemptでは、利用可能なデバイスについて以下を同時に評価する。

- ICM42688 gyro bias
- 重力加速度vector
- 重力vectorから得られるlauncher tilt
- SSCDRRN005PD2A5差圧zero offset

校正中は機体がランチャー挿入後に静置されていることを前提とする。初期calibration時間は3秒としてよいが`TODO(HW_TEST)`を残す。

各校正量は最新attemptの結果だけを使用する。最新attemptで失敗した項目を以前の成功値へ自動rollbackしない。

重力vectorはlauncher tiltや取付異常の確認へ使用するが、重力軸まわりのroll zeroを決めるためには使用しない。roll zeroはliftoff基準とする。

差圧zeroはLiftoffDetection中に自動rolling更新せず、PreflightCalibrationで求めてfreezeする。差圧系が未接続の場合はSSC zeroのみinvalidとして、gyro bias/gravity calibrationを独立して成功させてよい。

通常のSequence Startでは`GyroBiasValid`、`GravityReferenceValid`、`SscZeroValid`を必須とする。通常は`RunPreflightCalibration`でこれらを確立する。最新attemptでいずれかがinvalidなら通常Startは`NotConfigured`で拒否する。`ForceStartSequence`ではこの3 validity gateを含む5項目だけをbypassできるが、invalid状態をvalidへ偽装してはならない。

## 11. パラシュート試験操作

CommandReceiveで使用できるパラシュート駆動commandは`ParaOpen`と`ParaClose`だけとする。

- `ParaOpen (0x25)`: 現在位置から物理的な反時計回りへ130度相対移動し、到達後は現在位置Holdへ戻る。
- `ParaClose (0x26)`: 現在位置から物理的な時計回りへ130度相対移動し、到達後は現在位置Holdへ戻る。
- args0..5はすべて0とし、角度・方向をwireから指定しない。
- `ParaFree`、`ParaHold`、`ParaMoveRelative`、`SetParaOpen`、`SetParaClose`は廃止し、常に`NotSupported`とする。
- Open/Close絶対角をNVSへ保存しない。Open/Close configured flagも持たない。
- relative move発行前にHold/Torque ONを確立し、move後もHoldを維持する。
- command実行有無が曖昧な場合、同じ130度moveを自動再送しない。

詳細は[[08e_20260816_パラシュート簡素化|08e パラシュート簡素化仕様]]に従う。
## 12. Flash backup log export

`ExportFlashLogToSdAndErase`はCommandReceiveのみで受理する長時間generic commandとする。

内部Flash backup log scan/CRC確認 → microSD書出し → flush/sync → SD再確認 → 完全保存確認後のみFlash erase、の順とする。失敗時はFlashを消去しない。

## 13. LiftoffDetectionへの遷移

地上局から`FinZeroConfigured`、`ParachuteOpenConfigured`、`ParachuteCloseConfigured`、`MotorProfileValid`、`GyroBiasValid`、`GravityReferenceValid`、`SscZeroValid`を個別に確認できるようにする。

### 13.1 通常のStartSequence

通常のSequence Start必須初期セットアップは以下5項目とする。

- `FinZeroConfigured`
- `ParachuteOpenConfigured`
- `ParachuteCloseConfigured`
- `MotorProfileValid`
- `GyroBiasValid`
- `GravityReferenceValid`
- `SscZeroValid`

いずれかがfalseなら`Rejected / NotConfigured`として拒否する。`CommandResult.detail`には[[04c_ForceStartSequence詳細|ForceStartSequence詳細]]で定義する不足項目bitmaskを設定し、複数不足時はORする。

さらにCalibration、Flash export/erase、bring-up motor試験、競合actuator command等の処理中は`Busy`として拒否する。

Sequence Start受理前に[[05_実装仕様|実装仕様]]のmemory freeze/preallocation条件を満たす。`resources_preallocated=false`は5項目のNotConfigured gateではなくexecution safety failureであり、Forceでもbypassしない。

### 13.2 ForceStartSequence

`ForceStartSequence`は通常のStartSequenceと同じCommandReceive→LiftoffDetection遷移を行うが、13.1の**5項目だけを開始拒否理由から除外**する。

Forceでも以下はbypassしない。

- current MissionStateが`CommandReceive`であること
- command frame、transaction ID、argument等のprotocol validity
- memory freeze / resource preallocationが完了していること
- command/actuator/Calibration/storage等の排他と`Busy`判定
- queue、mutex、Task、driver ownership等、実行そのものを成立させるruntime invariant
- 離床+17秒deployment fallback、離床+25秒絶対power cutoff等のSafety処理

Force時も5項目の値、Health、freshness、calibration、設定状態を正常値へ書き換えてはならない。Force command自身がprovisional fallback、暗黙の0、前flightのstale値を生成・注入してはならない。

例えば`SscZeroValid=false`のままForce開始した場合はLiftoffDetectionへの遷移を許可するが、SSC zeroを必要とするControl gateは通常どおり成立しない。`MotorProfileValid=false`、Para設定未完了等についても既存のunavailable/fail-safe handlingを維持する。

Ground GUIは通常Startを先に送信し、terminal `Rejected / NotConfigured`かつdetail bit0..6のいずれかが1の場合だけerror popup内へ`FORCE START SEQUENCE`と`CANCEL`を表示する。Forceは別transactionで送信し、通常Startから自動fallbackしてはならない。詳細は[[04c_ForceStartSequence詳細|ForceStartSequence詳細]]に従う。

`StartSequence`または`ForceStartSequence`を受理した時点で`fin_control_disabled=false`から新しいflight attemptを開始する。利用可能な範囲で動翼角0度保持を開始し、CommandReceive中にすでに0度保持中なら継続する。パラシュートは設定が利用可能なら遷移時点の現在位置Holdを維持し、未設定をForceした場合は設定済みと偽装せず既存の安全側handlingに従う。
