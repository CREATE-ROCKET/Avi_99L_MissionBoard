# 99L Mission Board 飛行シーケンス仕様

## 1. ミッション状態

Mission Boardは以下の5状態を持つ。

1. CommandReceive: 起動直後の準備状態
2. LiftoffDetection: ランチャに設置され、離床検知前の状態
3. EngineBurn: 離床検知後の非Control状態
4. Control: ロール角保持制御を行う状態
5. Descent: 減速機構作動条件を満たした状態

状態数は増やさず、Controlを停止した場合はEngineBurnへ戻る。

EngineBurnという名称は役割に合わせて今後変更してよいが、状態の意味は「離床後かつDescent前の非Control状態」とする。

Descentへ移行する条件は減速機構作動条件のみとする。Control停止、制御系故障、対気速度60 m/s以下、`DisableFinControl`等を理由としてDescentへ移行しない。

## 2. LiftoffDetection

CommandReceiveからLiftoffDetectionへ遷移する時点で、`fin_control_disabled=false`なら動翼角0度保持を開始する。CommandReceive中にすでに0度保持中なら継続する。

離床検知器は以下を使用する。

- ICM42688: 1 kHz評価。各軸直近20 sample=20 msの算術平均を求め、3軸平均加速度vectorのnorm二乗が4 (G^2)を50回=50 ms連続で上回った場合
- LPS25HB: 25 Hz。5 sample算術平均が前回平均より0.05 hPa以上低い状態を5回連続した場合

いずれかを満たした場合に離床検知とし、**検知時刻の1秒前を離床時刻**とする。

片方のセンサが故障した場合は正常な側のみで離床検知を継続する。離床検知した場合は他のerrorの有無にかかわらずEngineBurnへ進む。

ICM raw gyro rolling bufferはLiftoffDetectionへ入ってから作り始めず、ICM初期化後のCommandReceiveから常時1秒以上保持する。保存対象はsensor timestamp、raw gyro、validity等とし、離床検知時に最新valid gyro biasを適用して離床時刻から検知時刻までreplay積分する。

### 2.1. CancelSequence

`CancelSequence`はgeneric commandとし、**LiftoffDetectionでのみ受理**する。

受理した場合はCommandReceiveへ戻り、sequence/liftoff関連checkpoint、flight parachute snapshot、`forced_start` latch、Control roll referenceを無効化する。`FinZeroConfigured`およびパラシュートOpen/Close active設定は維持し、`fin_control_disabled`をclearする。次のSequence Startは新しいflight attemptとして開始する。

### 2.2. LiftoffDetectionEmergencyStop

`LiftoffDetectionEmergencyStop`は[[01_コマンド受信モード|コマンド受信モード]]の`ActuatorEmergencyStop`とは別の専用Emergency commandである。

受理可能MissionStateは**EngineBurnのみ**とする。Controlでは受理しない。

EngineBurnで受理した場合はLiftoffDetectionへ巻き戻す。巻き戻し時は前回離床に依存する離床時刻、離床検知counter、姿勢積分、Control roll reference、+8秒Control gate、deployment pressure counter等を無効化し、再び離床検知を待つ。

各flight attempt/liftoffにはepoch ID相当を持たせ、巻き戻し前epochに属する遅延Safety eventやtimer eventを現在flightへ適用しない。`LiftoffDetectionEmergencyStop`は同じflight attempt由来のrollbackとして`forced_start`とflight parachute snapshotを維持する。

raw gyro rolling bufferそのものは継続してよく、離床時刻/積分stateだけを新epochとして初期化する。

`fin_control_disabled`がすでにtrueの場合はこのEmergency Stopでclearしない。その場合、巻き戻し後のfinはBrakeを維持する。falseの場合は通常のLiftoffDetectionと同様にZeroHoldを行う。

### 2.3. Fin zeroの飛行sequence上の意味

`FinZeroConfigured`はencoder / motor-side zero referenceのconfiguration transactionが成功したことを表し、physical finの空力0 degを保証しない。ZeroHoldはAS5047Dから得る`theta_measured_rad`を0付近へ保持する。simulationでは`electrical_zero_hold_valid`と左右のphysical fin角および`false_zero_hold_valid`を別に記録する。flight runtimeは観測できないphysical errorをvalid条件に使用しない。

CommandReceiveで設定されたencoder zero error、左右fin中立offset、backlash initial flank、安全評価用残留角は、simulation上でLiftoffDetection、EngineBurn、Controlへ継続する。EngineBurnではactual fin offsetから生じる法線力、roll acceleration/rate/angle、hinge load、authority consumptionを評価する。Control entryでaccumulated roll angleはreferenceへcaptureされentry deviationは0となるが、roll rateは残るため最初のtickからrate feedbackの対象とする。Control中もphysical fin biasはconstant trim demand、saturation、motor/gear/stopperへの影響として継続する。

## 3. PreflightCalibrationと姿勢推定

Control用gyro biasはCommandReceiveの`RunPreflightCalibration`で求めた最新valid値を使用する。重力vectorからlauncher tiltを評価できるが、重力だけでは重力軸まわりのrollを決定できないためroll zeroには使用しない。

AS5047D producerはCommandReceive中から開始し、`Uninitialized -> WarmingUp -> Ready`を飛行前に完了させてよい。startupの避けられない遅延はControl開始が離床+8 s以降であることから直ちにflight rejection理由としない。ただし`StartSequence`またはControl entryの判定で`Ready`でなければ、将来sampleを待たずにencoder/Control input unavailableとする。

離床検知時は離床時刻を`検知時刻 - 1秒`とし、その離床時刻のroll角を0とする。CommandReceiveから保持していたgyro履歴を離床時刻から検知時刻まで積分し、その後もsensor timestampを使用して`roll_estimate_liftoff_relative_unwrapped_rad`の積分を連続して継続する。この姿勢推定値はEngineBurnからControlへ移行してもresetしない。

制御の目的は、エンジン燃焼終了後から頂点付近まで機体のロール角を一定に保つことである。実装上は、エンジン燃焼終了後であることを十分保証できる離床+8秒以降にEngineBurnからControlへ初めて遷移するaccepted tickで保持目標を取得する。Controlの保持目標はランチャー上の0 radではなく、そのtickの連続・unwrappedな機体ロール角である。最初のControl演算より前に最新のvalid/fresh `roll_estimate_liftoff_relative_unwrapped_rad`を一度だけ`control_roll_reference_unwrapped_rad`へcaptureする。captureと最初のControl演算には同じlatest-complete sampleを使用し、`roll_deviation_unwrapped_rad = roll_estimate_liftoff_relative_unwrapped_rad - control_roll_reference_unwrapped_rad`をRoll Controllerへ渡す。このためentry tickの角度偏差はexactly 0 radだが、roll rateはそのまま使用する。Control pathはこの差を最短路へwrapせず、360度を超えた回転も連続値として加減し続ける。

`control_roll_reference_valid`はControl entry前にfalseとし、reference未captureでRoll Controllerを実行しない。Control中は再captureしない。reset、新しいflight epoch、`CancelSequence`、`LiftoffDetectionEmergencyStop`でreferenceをinvalidにする。captureしたMission tickとestimator timestampを保存し、estimator timestampがcapture時刻より未来にならないことを保証する。

### 3.1. ICM42688 sample欠落

単一sample欠落だけで直ちに姿勢を永久invalidにしない。

初期実装では連続欠落許容数を1 sampleとし、timestampから1 sample欠落と一意に判断できる場合はControl tickを未来sample待ちで停止しない。欠落tickでは直前rateを1 ms積分し、次のvalid tickではそのrateを1 ms積分することで2 ms全体として前後sampleの台形積分と等価になる構成を使用できる。

許容連続欠落数1は飛行用確定値ではないため`TODO(SIMULATION)`とする。補間を使用した場合もICM data loss eventをtelemetry/logへ残す。

許容数を超える欠落、欠落数不明のtimestamp gap、FIFO format fault、gyro sample invalid、gyro saturation、timestamp不整合等では姿勢をinvalidとし、その飛行中のControl再移行を禁止する。

## 4. Controlへの移行

Control移行判定は、離床時刻から8秒以上となる**最初のaccepted coordinator tickで一度だけ**行う。`control_gate_evaluated`と`control_reentry_inhibited`を別latchとして保持し、判定後に条件が回復しても再評価してControlへ入らない。airspeed entry debounceは+8秒より前から更新してよいが、+8秒のone-shot tickではその時点までに連続条件が成立済みでなければならない。

Controlへ入るためには以下をすべて満たす。

- `fin_control_disabled == false`
- motor-side観測角に対する動翼0度保持がelectrically valid
- `EncoderPipelineState == Ready`
- 有効な対気速度が60 m/sを上回る
- 姿勢推定がvalid/fresh
- LPS25HBがControl用としてavailable/fresh
- SSCDRRN005PD2A5がControl用としてavailable/fresh
- gyro biasがvalid
- SSC zero offsetがvalid

条件成立tickではMission/Control coordinatorがMissionStateをControlへ更新する前後のrising edgeを一意に検出し、Control roll reference captureを完了してから同じtickの最初のRoll Controller演算を行う。encoder consumerはそのtickまでのlatest complete blockだけを取得し、新blockが無い場合にfuture sampleをblocking待ちしない。

離床時刻から8秒経過した最初の判定時点で、上記gateのいずれか一つでも満たせない場合は、`control_gate_evaluated=true`かつ`control_reentry_inhibited=true`とし、その飛行中のControl再移行を禁止する。

LPS25HBまたはSSCがControlに必要な時点でUnavailableの場合も、その飛行ではControlへ入らず、Control再移行を禁止する。復旧後もControlへは戻さない。

一発のtransport errorのみで即Unavailableにする必要はない。最後の正常値がfreshness範囲内でHealth上も使用可能なら、その値を使用できる。availability predicate、freshness、60 m/s entry/stop debounceは`TODO(SIMULATION)` / `TODO(HW_TEST)`を残して最終決定する。

初期候補はICM freshness 3 ms、AS5047D 3 ms、SSC 20 ms、LPS 120 ms、entry `>60 m/s` 50 ms連続、stop `<=60 m/s` 20 ms連続とする。これらはconfig値とし、`TODO(SIMULATION)`を維持する。1 sample欠落を補間できる場合もsource timestampとageでfreshnessを一意に判断し、補間をfresh sampleの生成として扱わない。

## 5. Control中の停止と再移行

Control中に以下が成立した場合はEngineBurnへ戻り、その飛行中のControl再移行を禁止する。

- 有効な対気速度が60 m/s以下の停止debounce成立
- 姿勢推定を継続できない
- 動翼角/動翼制御系を利用できない
- LPS25HBまたはSSCがControl用としてUnavailable
- `DisableFinControl`を受理

LPS/SSCが後で復旧してもtelemetry、logging、頂点検知へは利用できるがControlへ再entryしない。

Control停止後、`fin_control_disabled=false`かつ動翼角/ZeroHoldがvalidならZeroHoldへ切り替える。動翼状態を利用できない、または`fin_control_disabled=true`ならBrakeとする。

Control停止時はintegrator、trim correction、disturbance observer等の候補controller stateをdrive出力から切り離し、再entryへ持ち越さない。新flight epoch/reset/`CancelSequence`/`LiftoffDetectionEmergencyStop`ではこれらをclearする。Control停止後も`control_reentry_inhibited=true`を維持する。

## 6. DisableFinControl

`DisableFinControl`はgeneric commandとし、LiftoffDetection、EngineBurn、Controlで受理する。

受理後は`fin_control_disabled=true`をそのflight中latchedし、ZeroHold/RollControlを禁止してBrakeとする。

- LiftoffDetection: state維持、ZeroHold停止、Brake
- EngineBurn: state維持、ZeroHold停止、Brake
- Control: RollControl停止、EngineBurnへ戻り、Brake

受理後はそのflightでControlへ再移行しない。`LiftoffDetectionEmergencyStop`ではclearせず、`CancelSequence`または次の新しいSequence Startでclearする。

## 7. 減速機構作動条件

以下のいずれかを満たした場合に減速機構を作動しDescentへ遷移する。

- 離床時刻から10秒以上経過し、LPS25HB 25 Hzの5 sample算術平均が前回平均より高い状態が1秒間連続
- 離床時刻から17秒経過

LPS25HB故障時は気圧による頂点検知を行わず、経過時間+17秒条件を使用する。

Controlへ移行できない場合や`DisableFinControl`後も、EngineBurnのまま減速機構作動条件を監視する。

## 8. Descentへの移行

減速機構作動条件成立時、`fin_control_disabled=false`かつ動翼角/ZeroHoldがvalidなら動翼目標角を0度とする。動翼を利用できない、または`fin_control_disabled=true`ならBrakeを維持する。

動翼が実際に0度へ到達したかに関係なく、パラシュートOpen処理を直ちに開始する。動翼0度到達をOpenの前提条件にしない。

Descent移行後もfinが利用可能なら離床+25秒までZeroHoldを継続し、離床+25秒でBrakeへ移行する。Recovery Deep Sleep直前にはStop/Hi-Zへ安全化する。

## 9. パラシュートOpen処理

Descentへ移行した場合は、Start/ForceStart時にfreezeしたflight snapshotだけを参照する。CommandReceiveのactive NVS configを飛行中に再参照しない。

flight snapshotにOpenが存在する場合、各Open指令またはretryの直前にSTS3215からfreshな現在角を取得し、`shortestParachuteDisplacement(current, open)`を計算する。exact half-turn（2048 count）は方向を任意選択せず動かさず、`ambiguous_half_turn`として一度記録する。retryでも同じsnapshot Openを使い、fresh currentから変位を再計算する。

Openがmissing/corruptでsnapshot=`nullopt`の場合もMissionStateはDescentへ遷移するが、Open moveは発行しない。`open_not_configured`を一度記録し、fresh currentを取得できるならその位置をHoldする。Closeはdeploymentの必須条件ではない。

Openが存在してもfresh currentを取得できない場合はtargetから方向を推測せずmoveを発行しない。STS power-on要求、bounded再初期化、fresh angle取得を継続し、Open retry deadline内に取得できればOpenを試す。取得不能のままdeadlineを迎えた場合は`current_angle_unavailable`/`retry_exhausted`を記録してrequested Holdへ戻す。

Open開始0.5秒後に開始位置からの進行量が初期候補2 deg未満ならretryする。一度動き始めた後もtarget未到達で直近0.5秒の進行量が2 deg未満ならstallとしてretryする。2 deg/0.5 sは`TODO(HW_TEST)`とする。

全体Open retry deadlineは最初のOpen要求から約5秒とし、retryで延長しない。5秒は新規Open move/retryを終了する期限であり、電源遮断期限ではない。Open成功後はOpen位置Hold、Open失敗/retry exhausted後は取得できた現在位置Holdを継続し、STS電源は離床+25秒まで基本的にONとする。絶対電源遮断は状態にかかわらず離床+25秒でのみ行う。

パラシュート開放条件監視、Open処理、および離床+25秒絶対電源遮断はControlより高い安全優先度で実装する。

## 10. 開放確認用telemetry

少なくとも以下を区別する。

- `ServoOpenConfirmed`: servoがOpen目標角まで正常に動いたことを確認
- `DeploymentShockConfirmed`: Open後にICM42688で大きな衝撃を確認

両者は地上局通知用であり、MissionState遷移、Open retry、電源遮断条件には使用しない。

ServoOpen到達許容値、DeploymentShock閾値は初期値を置いて実装してよいが`TODO(HW_TEST)`を残す。

## 11. 絶対電源遮断期限

離床時刻から25秒経過した時点で、Open処理、ServoOpenConfirmed、DeploymentShockConfirmed等の状態にかかわらず、パラシュートサーボおよび差圧系基板への電源供給を無条件で遮断する。

この処理はSTS UART task等がhangしていても実行可能な独立Safety処理とする。

## 12. 飛行中Reset後

飛行中reset後はroll turn count、Control roll reference、および減速機構後の動翼絶対角を正確に復元できるとはみなさずControlへ復帰しない。wrapped orientationと最後のreferenceだけからturn countを復元せず、`control_roll_reference_valid=false`としてfinはBrakeを使用する。

Power-on reset以外ではRTC系時刻基準と保持状態から離床後経過時間を復元し、減速機構作動条件、Open処理、+25秒絶対遮断を継続する。

完全なPower-on resetでは保存済み離床絶対時刻と、GNSSまたは地上局から得た現在絶対時刻との差から経過時間を復元する。

離床時に絶対時刻が未取得でも、その後flight中に絶対時刻を取得できた場合は現在絶対時刻とelapsedから離床絶対時刻を逆算してcheckpointを更新する。完全電源断までにこれを保存できず、POR後にもelapsedを復元できない場合はパラシュートOpenを開始または再開しない。

NVS/checkpoint I/Oはbest effortであり、flight critical処理を待たせない。

## 13. RecoveryBeacon移行とRecovery Deep Sleep

RecoveryBeaconへの**移行判断はMission Boardが行う**。RecoveryBeaconはMissionStateではないため、RecoveryBeacon中もMissionStateはDescentのままとし、Mission側ではRecovery移行済みlatch/RTC markerをMissionStateとは別に保持する。通信基板は離床後経過時間、最後に受信したMissionState、Mission通信断等からRecoveryBeacon移行を推測してはならない。

自動移行の初期条件は、Mission BoardがDescent中であり、離床時刻から120秒以上経過したこととする。120秒はRecovery battery life、通信要求、回収運用を含む実機確認で最終調整してよいが、条件評価主体は常にMission Boardとする。

地上局から早期Recovery移行を要求する場合は`EnterRecovery` generic commandを使用する。Mission BoardはDescentかつ`DeploymentPowerCutoffDone=true`の場合だけ受理し、それ以外では`InvalidState`または`SafetyInterlock`で拒否する。Ground/通信基板が直接RecoveryBeaconへ切り替えるcommandは設けない。

Mission BoardがRecovery移行を決定した場合は、次の順序を基本とする。

1. finをStop/Hi-Z相当へ安全化し、パラシュートサーボおよび差圧系基板の電源遮断済みであることを確認する。
2. Mission microSD/Internal Flashのflushをbounded best-effortで要求し、無期限には待たない。
3. RTC Recovery markerを設定する。
4. `RecoveryModeCommand::EnterRecoveryBeacon 0x014`を通信基板へ送る。CAN送信成功まで短時間retryしてよいが、初期上限は1秒とし、Recovery移行を無期限に待たせない。
5. Mission BoardはDeep Sleepへ入る。

`RecoveryModeCommand`を1回も正常送信できなかった場合、Mission Boardは通信基板がRecoveryBeaconへ入ったと仮定しない。10秒periodic wake時に再度`EnterRecoveryBeacon`を送信し、通信基板との接続が復旧した時点で収束させる。通信基板はMission Boardから有効な`EnterRecoveryBeacon`を受信するまで`MissionLinkFallback`等の現在communication modeを維持する。

Deep SleepからのwakeではRTC Recovery markerとwake causeを確認してRecovery専用boot pathへ入り、通常flight bootへ戻らない。

初期候補として10秒periodic wakeを使用し、ADC/CAN/Recovery statusを更新して短時間commandを待った後、要求がなければ再びDeep Sleepへ入る。wakeごとに`EnterRecoveryBeacon`を再送してよい。wake周期、command window、CAN再initializationは`TODO(HW_TEST)`とする。

RecoveryBeacon中の標準remote dumpは内部Flash backupを対象とする。Mission microSD full-rate logはoffset/length指定の部分dumpとする。可能ならrequested rangeをCANで通信基板microSDへ先にspoolし、Mission Boardは再びDeep Sleepへ戻して通信基板だけでLoRa送信を継続する。
