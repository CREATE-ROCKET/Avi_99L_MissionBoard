# 99L Mission Board 初期実装・検証仕様

> **2026-08-16更新:** パラシュートのOpen/Close、STS3215 Hold、NVS、readiness、廃止commandについては[[08e_20260816_パラシュート簡素化|08e パラシュート簡素化仕様]]を優先する。本書に残る絶対角endpoint、NVS、Free、Open retryの旧記述は当該範囲では廃止。


## 1. 本文書の位置付け

本書は、Mission Board本実装へ着手する直前の初期実装値、実機検証順序、bring-up完了条件をまとめる。

00〜05は本書で決定した内容を反映し、00〜07を一体の仕様として扱う。本書はbring-upと検証手順、`TODO(SIMULATION)` / `TODO(HW_TEST)`の具体運用を補足する。

初期実装の第一目的は本番シーケンスを完成させることではなく、`CREATE-ROCKET/Avi_ESP_Libs`の`refactor` branchで今回使用するAPIが実基板上で正しく動作することを確認し、制御・推定・filter等の未確定係数を決めるための実測データを取得することである。

## 2. 現在の実機検証構成

- Mission Boardは実基板をPCへUSB接続して試験する。
- ESP32-S3は`/dev/ttyACM<N>`として認識されるものを使用し、番号をhardcodeしない。
- 差圧系以外は接続した状態で試験する。
- 差圧系未接続はbring-up failureとは扱わず、AirData実機試験のみskip可能とする。
- 動翼DC motorには現在動翼を取り付けていない。
- 現在の動翼駆動系には機械stopperがなく、360度以上連続回転可能である。
- bring-up段階では飛行時software limitを適用せず、test専用duty/speed/time limitで安全化する。
- 動翼motorのstep、PRBS、coast、Brake等のsystem identificationを実施してよい。ただし低duty・短時間から段階的に上げる。

fin装着actuator characterizationとfinなしmotor/gear rigの1/2 kHz characterizationは別途作成中である。本preworkはその値を推測して埋めず、dynamic freeplayの未同定parameterは`status=unidentified`としてcanonical評価をblockする。

## 3. Avi_ESP_Libsの利用方法

`CREATE-ROCKET/Avi_99L_MissionBoard`では`CREATE-ROCKET/Avi_ESP_Libs`を`lib/Avi_ESP_Libs`のGit submoduleとして使用する。

- 対象branch: `refactor`
- 実際の利用revisionはsubmodule commit SHAで固定
- remote `lib_deps`で毎build時に取得しない
- submoduleとPlatformIO/ESP-IDF toolchain取得済みならoffline build可能

Mission本実装より先に以下を実基板で個別検証する。

- `SPICREATE`
- `ICM42688`
- `AS5047D`
- `CANCREATE`
- `I2CCREATE`
- `LPS25HB`
- `SSCDRRN005PD2A5`

library側の問題をMission Board側workaroundで隠さず、共通driver/APIの責務に属する不具合はsubmodule側を修正し、library build/testとMission実機試験を再実施する。

## 5. MotorProfileと実機characterization

動翼motorには予備個体があり、使用個体により抵抗、摩擦、dead-zone、駆動応答等が変わる可能性がある。motor依存値をcontrollerやTorqueMapperへ直接埋め込まない。

現在のfin/stopper未装着状態で最低限以下を取得する。

### 5.1. 静置

- ICM raw accel/gyro 1 kHzを5分以上
- ICM sensor timestamp/FIFO status
- AS5047D raw compensated angleを1/2/5/10 kHzで取得
- 各1 kHz record内の最大10 subsample raw値、timestamp offset、valid mask、sample count
- capture interval、release delay、block group delay、deadline miss/coalescing
- logic/motor voltage
- queue drop/SD latency

static logでは1/2/5/10 kHzのlast sample、non-overlapping block arithmetic mean、block median、direct high-rate estimator without retuneを比較し、必要な場合のみsliding meanを追加する。1 kHz consumerに対するblock sizeは1/2/5/10 sampleとし、`block_arithmetic_mean_n1/n2/n5/n10`のように一般名を使用する。raw `uint14`をwrapしたまま平均せず、raw compensated angleをsampleごとにunwrapしてからblock statisticを求め、最後にtotal ratioへ変換する。

現characterization task構成で得た静止output cadenceのsanityは、1 kHz約999.997 Hz、5 kHz約994.619 Hz、10 kHz約984.749 Hzである。これはsensor limitではなく現在task構成の測定値として扱う。

static sanityの基準値は以下とする。

| sampling | last sigma [count] | arithmetic mean sigma [count] | median sigma [count] | Quad N3 last→mean [deg/s] | alpha-beta .40/.35 last→mean [deg/s] |
|---:|---:|---:|---:|---:|---:|
| 1 kHz | 1.5541 | 1.5541 | 1.5541 | 0.5016→0.5016 | 0.0924→0.0924 |
| 5 kHz | 1.4885 | 0.6967 | 0.9063 | 0.4725→0.2393 | 0.0859→0.0374 |
| 10 kHz | 1.3915 | 0.6331 | 0.7484 | 0.4387→0.2161 | 0.0805→0.0346 |

5 kHz算術平均がmedianより低noiseであること、および10 kHzの5 kHz比改善が約8〜10 %に留まることを確認する。10 kHz dynamic logは未取得であり、dynamic production候補の根拠にしない。

2 kHzの必須入力は`static_2k.bin`、`auto_ident_2k_safe.bin`、`auto_ident_2k_full.bin`とする。存在する場合は実fileからSHA-256、byte count、record数、durationを算出し、header `acquisition_hz` / `samples_per_log`が2 kHz / 2 sampleであることを照合する。filenameだけでsampling rateを信用しない。存在しなければ不足の3 fileを明示し、2 kHz canonical artifactを生成せずPhase 6/7 revision 3を`COMPLETE`としない。

static比較ではangle noise sigma [count]、fin-equivalent angle noise、Quadratic N3/alpha-beta rate RMS、group delay、block cadence、steady-state raw capture miss rate、startup warm-up duration、CPU/task load proxy、timestamp offset saturationをrateごとに保存する。dynamic auto-identではbreakaway/sustained threshold、direction asymmetry、pulse velocity RMSE、acceleration RMSE、Coast/Brake、estimator active proxy、chatter、run-to-run variation、Vbusをrate/runごとに保存する。

### 5.2. motor step

正負方向について5%、10%、15%程度の短時間stepを段階的に実施する。最初は5%から行い、異常な高回転・発熱・異音があれば中止する。

### 5.3. PRBS

fixed seedのPRBSを100 Hz程度で与え、sensor/encoderは1 kHzでlogする。最初は±5%、問題なければ±10%、必要性を確認した場合のみ±15%へ進む。

### 5.4. coast / Brake

一定速度まで回した後にHi-Z coastとShort Brakeを別々に実施し、速度減衰、停止時間、停止角、振動を比較する。

### 5.5. 得るparameter

この実測から最低限以下を求める。

- motor polarity
- duty/Vbus→steady speed
- dead-zone
- command→motion delay
- step/PRBS dynamic response
- equivalent drivetrain inertia候補
- Coulomb/viscous friction候補
- coast/Brake response
- encoder jitter/noise
- motor駆動時ICM noise/vibration
- Vbus sag
- scheduler/SD logging jitter

個体ごとの結果をMotorProfile候補として保存し、予備motorでも同じ試験を再利用できる構造にする。

auto-identは利用可能なstrict-validまたはwarm-up-discarded-validな1/2/5 kHz safe/fullのrunを、sampling rateとsafe/fullごとの独立unitとして管理する。run ID、encoder observation pipeline、Vbus、direction、startup policy/除外量を保持する。30 kHz PWMでの暫定range sanityはpositive breakaway 15〜21 %、negative breakaway 15〜20 %、positive sustained 18〜21 %、negative sustained 20〜26 %とし、単一点の真値へ潰さない。

leave-one-complete-run-outで学習と検証を分け、同一runをtrainingとvalidationへ同時使用しない。sampling rateを無視してpulseを混ぜず、1/2/5 kHzは別motor plantではなく独立repeatとobservation pipeline差として扱う。旧V2約10.9 V runと新V4約9.76〜10.01 V runを別conditionとして保存する。

actuator Candidate A/B/Cを全runで再比較し、per-run/per-rate fit error、held-out run error、threshold range、Vbus range、run-to-run variance、model selection confidenceを出力する。従来のCandidate Bはhistorical carry-forwardとし、自動採用しない。証拠不足な場合は`selectable=false`を維持する。actual torque/current/inertia/efficiencyは未同定のままとし、duty/Vbus/方向別観測から確定したと表現しない。

### 5.6. V2/V4 binary log contract

Spica importerはV2とV4をmagic/version/header/record sizeから判別し、backward compatibilityを維持する。V4はmagic `99LMCV4\0`、header 128 byte、record 160 byteで、record先頭112 byteはV2 compatible prefixとする。

V4 writer sourceで確定したextensionは、`encoder_burst_raw[10]` u16 LE at byte 112、`encoder_burst_dt_us[10]` i16 LE at byte 132、`encoder_burst_valid_mask` u16 LE at byte 152、`encoder_burst_count` u8 at byte 154、`encoder_burst_missed_ticks` u8 at byte 155、`burst_reserved` u32 LE at byte 156である。byte 155を一般的なstatus/flagsと推測して改名しない。

malformed header、unknown version、partial record、sample count > 10、count外のvalid bit、countに対して不足するvalid sample、valid raw timestampの非単調増加をstrict importerでrejectする。sequence、queue drop、encoder error、ICM error、FIFO lost、host tick missedはbinaryから集計し、期待値をhardcodeしない。

revision 3 importerは`StartupPolicy="strict"`をdefaultとし、追加の`StartupPolicy="discard_pre_baseline_warmup"`を明示指定できる。後者が不正timestampをanalysis対象外にできるのは、以下をすべて満たす有限なprefixだけとする。

- 最初の`baseline_pre`より前
- `test_phase` がidle相当
- motor commandが0
- motor modeがCoastまたはStopの安全状態
- actuator identification開始前
- 最初のanalysis-eligible strict complete block（`baseline_pre`先頭）より前
- prefix record数と経過時間が有限

このprefix内のlong startup gap、int16 timestamp offset saturation、incomplete producer warm-upは事実を記録した上でanalysis対象外にできる。任意の中間corruptionをstartupとして破棄せず、最初のanalysis-eligible record以降は現在と同じstrict validationを維持する。steady-state、baseline、またはmotor試験中に同じ異常があればrunをrejectする。

importerはraw recordを物理的に削除せず、recordごとの`analysis_eligible`、`startup_warmup`、quality/statusを返す。artifactに`startup_warmup_record_count`、`startup_warmup_duration_us`、`startup_invalid_burst_count`、`startup_offset_saturation_count`、`first_analysis_eligible_sequence`、`first_analysis_eligible_timestamp`を保存する。model fit、noise解析、steady-state timing評価は`analysis_eligible=true`のrecordだけを使用する。

`auto_ident_5k_full.bin`はrevision 2のstrict rejectionをhistoricalに保持し、revision 3では上記prefix条件をbinaryから検証する。異常が真にstartup prefixだけで、その後がstrict-validな場合に限りrun-level validationへ再利用できる。条件不成立またはsteady-state異常をsalvageしない。

V4のsubsample timestampは現writerではSPI transaction begin/endの中点であり、actual completion timestampではない。last midpointをrelease proxyとして保存する場合は`release_timestamp_status=proxy_last_subsample_midpoint`を明示し、deadline証明済みと扱わない。production loggerでは最後のsubsample完了時刻を記録するか、別のdeadline証拠を取得する。

次のproduction相当logにはraw capture requested timestamp、SPI transaction start/completion timestamp、block completion/release timestamp、1 kHz consumer timestamp、consumer deadline miss、repeated block count、coalesced notification count、raw capture missed tick count、timestamp offset saturation count、pipeline ready timestampを追加する。startup warm-upが許容できても、現V4でcompletion/release timestampが無い限り`production_timing_proven=false`を維持する。

入力binaryはSpica repository外のpathから明示指定し、raw binaryをrepositoryへcommitしない。artifactにはbasename、SHA-256、format version、writer source contractを保存する。

## 6. 構造系審査書から既に使える実測値

以下は新たにmotor-only試験で求める必要はなく、構造系審査書の実機評価値を初期Spica modelへ使用できる。

- backlash全幅: **0.344 deg = 0.00600 rad**
- 回転方向支持剛性: **269.43 N·m/rad**
- 対称play operator half-width: **0.172 deg = 0.00300 rad**
- 安全評価用直進残留角: **±0.344 deg = ±0.00600 rad**
- 構造上の必要支持剛性: **152.71 N·m/rad**
- 危険符号の静的発散防止必要剛性: **15.91 N·m/rad**
- 0.344 deg残留時の追加法線力: **1.301 N / fin**（比0.01903、合格基準0.10以下）
- hardware angle limit: **±15 deg**
- stopper構造評価torque: **7.10328 N·m**
- stopper静的proof: **10.65 N·m / 30 s**
- 通常制御時に必要と評価された保持torque: **2.66526 N·m**（構造上の最大許容torqueではない）
- 通常保持の構造試験比較値: **9.10 N·m**
- stopperなし駆動系構造評価torque: **1.21208 N·m**

backlashを対称dead-zoneとしてmodel化する場合は全幅/半幅の定義を明示する。安全評価の直進位置残留角には0.344 degを保守値として使用する。

269.43 N·m/radは予荷重でbacklashを一方向へ取り切った後の今回測定方向の割線剛性である。freeplay内復元剛性、歯面衝突/stopper/dynamic impact stiffnessではない。`measurement_direction_coverage`、`source_status`、`requires_bidirectional_revalidation`をmetadataに保存する。

### 6.1. fin assembly system-identification handoff

dynamic two-fin canonical評価には、少なくとも次のfieldを入力する。

- `left_fin_inertia_kg_m2` / `right_fin_inertia_kg_m2`
- `left_fin_viscous_damping_Nm_s_rad` / `right_fin_viscous_damping_Nm_s_rad`
- `left_fin_coulomb_friction_Nm` / `right_fin_coulomb_friction_Nm`
- `engaged_stiffness_positive_Nm_rad` / `engaged_stiffness_negative_Nm_rad`
- `contact_damping_positive_Nm_s_rad` / `contact_damping_negative_Nm_s_rad`
- `backlash_full_width_positive_rad` / `backlash_full_width_negative_rad`
- `left_right_zero_offset_rad`
- `motor_current_measurement` / `Vbus`

## 7. Stopper衝突試験の位置付け

stopperへmotorで意図的に衝突させる実機試験は、Phase 6開始条件にはしない。

構造系審査書の10.65 N·m / 30 s確認は静的保持試験であり、高速衝突時の運動energy許容値を直接保証しない。

SpicaでHigh-authority candidateがstopper dynamic contactを必要とする場合にのみ、simulationが要求する最大接触速度を基準として段階的なqualification testを計画する。

試験する場合は低速から開始し、各段階でbacklash、歯車異音/損傷、AS5047D基準、stopper変形、作動後のガタを再確認する。GP22Aを破損させる条件まで上げない。

## 8. PreflightCalibration

CommandReceiveで`RunPreflightCalibration`を何度でも実行可能にする。

1回のattemptでは利用可能なデバイスについて以下を同時に評価する。

- ICM42688 gyro bias
- gravity vector
- launcher tilt
- SSCDRRN005PD2A5差圧zero offset

最新attemptのみ使用し、失敗項目を古い成功値へrollbackしない。

bring-up用初期calibration時間は3秒としてよいが`TODO(HW_TEST)`を残す。

差圧zeroはLiftoffDetection中にrolling更新せずPreflightCalibration中に求めてfreezeする。

Calibration中はFin/Para駆動command、motor試験、`StartSequence`を`Busy`で拒否する。

Fin zero configurationはPreflightCalibrationと別transactionとし、positive single approach、negative single approach、bidirectional midpointをground fixture / fin-side angle計測で比較できるようにする。`FinZeroConfigured`はelectrical configuration成功のみを表し、physical zero verificationの代用にしない。

## 9. ICM42688欠落sampleの初期方針

初期実装では連続欠落許容数を1 sampleとし`TODO(SIMULATION)`とする。

1 sample欠落tickで未来sampleを待たず直前rateを1 ms積分し、次valid tickでそのrateを1 ms積分することで2 ms全体を前後sample台形積分と等価にする。

許容数を超える欠落、timestamp gap不明、FIFO format fault、gyro invalid/saturation、timestamp不整合では姿勢をinvalidにする。

### 9.1. Control roll reference検証

姿勢推定の離床時原点とControl referenceを別stateとして実装し、少なくとも以下を自動testで確認する。

- Control entry前はreference invalid
- EngineBurn→Control entry tickで一度だけ、最初のControl演算より前にcapture
- captureと最初の演算は同じlatest-complete sampleを使用し、角度偏差0 rad
- entry時のroll rateが非零なら最初のtickからrate項torqueが出る
- absolute rollへ任意定数を加えてもControl出力不変
- reference=0、current=+380 degで`roll_deviation_unwrapped_rad=+380 deg`、角度feedback torqueはnegative
- reference=0、current=-380 degでdeviation=-380 deg、角度feedback torqueはpositive
- reference=+720 deg、current=+1100 degでdeviation=+380 deg
- referenceとcurrentの両方に同じ`2*pi*N`を加えてもdeviation不変
- currentだけに`+2*pi`を加えるとdeviationは`+2*pi`増え、同値姿勢としてwrapしない
- `+pi/-pi`、`+2*pi/+4*pi/-2*pi/-4*pi`通過でestimate/deviationにjumpがない
- Control中に再captureしない
- invalid/stale attitudeではcaptureしない
- reset、新epoch、`CancelSequence`、`LiftoffDetectionEmergencyStop`、rollbackでinvalid
- estimator sample timestampがcapture timestamp以下

旧`wrapPreservesPositiveAndNegativePiTies`等のshortest-path wrap testは現runtime要件から削除するか、historical testとして現runtime gateから分離する。

### 9.2. Constant disturbance / coordinator / AirData test

system-ID非依存のpreworkでは次を自動testする。

- `Cl0=0`でnominal trim要求0、Cl0正負でtrim符号反転、true/assumed mismatchを相殺しない
- BaselineLQRのconstant disturbance定常偏差を記録し、trim/LQI/trim+bounded-integralがnominal誤差を低減するか比較
- saturation、invalid input、fin/stopper/motor/gear limit、Control inactive/no-reentry中のanti-windup freeze/back-calculationと、Control exit/new epoch/reset/Emergency時clear
- +8秒one-shot gate、entry/stop debounce、freshness、LPS/SSC loss、`DisableFinControl`、Control停止後ZeroHold/Brake、再entry禁止
- gain lookup 59.9 / 60 / 60.1 / 179.9 / 180 / 180.1 / 200 / 220 m/sでendpoint clamp、raw/lookup値とlow/high flag、table外非extrapolation
- `K=0.92`を`K^2*q_c/P_s`のpressure correction coefficientとして使用し、Pitot true/assumedを分離
- pressure-domain filter後変換と、変換後airspeed-domain filterを同一inputで比較し、Mission/Spicaのfilter domain/timestamp/freshness contractを一致
- Control OFFは同じinitial state、plant、sensor/scheduler replay、seed、disturbance/profileでrequested torqueだけ0

## 10. Fin Velocity Estimator

Spica Phase 5の現評価ではquadratic regression N=3がactive motionのRMSE/peak/phase delayでalpha-betaより優位なsimulation candidateとなっている。

## 11. Fin software limit

bring-up時点のmotorは360度連続回転可能であり、動翼・stopperは未装着である。

飛行時software angle limitは`FinSoftwareLimits`等の単一configから参照する構造だけを用意し、最終値はfin/stopper組付後のBrake停止角、encoder error、backlash、latencyを測って決定する。

hardware limit **±15 deg**は絶対条件である。

## 12. AirData異常時のControl

LPS25HBまたはSSCDRRN005PD2A5がControlに必要な時点でUnavailableとなった場合、復旧後のControl再移行は行わない。

一回のtransport errorだけで即Unavailableにせず、最後の正常値がfreshness内でvalidなら利用できる。availability/freshness/debounceは`TODO(SIMULATION)` / `TODO(HW_TEST)`とする。

LPS25HB internal averagingはdriver default任せにせず、初期候補pressure/temperatureとも8 samplesとする。

## 13. Flash backup / memory freeze

internal Flash backupは初期50 Hz程度としてよいが`TODO(HW_TEST)`を残す。

flight backup用Flash領域はCommandReceive中に事前eraseし、飛行中はpre-erased領域へのappend writeのみとする。飛行中にeraseしない。

`CommandReceive -> LiftoffDetection`をmemory freeze境界とし、LiftoffDetection移行前までに全Task/stack、queue、driver、SD mount、flight log open、ring/buffer、timer、ADC calibration、Flash buffer等を確保する。

LiftoffDetection以降はapplication codeからdynamic heap allocation、container growth、新規Task/queue生成、filesystem mount、未準備file open、大規模local stack確保を行わない。

## 14. Recovery

Recoveryは**Deep Sleepのみ対応**する。Light Sleep fallbackは持たない。

初期候補として10秒periodic wakeを使用し、Recovery専用boot pathでADC/CAN/Recovery statusを更新し、短時間commandを待って再sleepする。`TODO(HW_TEST)`。

標準remote log dumpはInternal Flash backup。Mission microSD full-rate logはoffset/length指定の部分dumpとする。

可能ならrequested dataをCANで通信基板microSDへ先にspoolし、Mission Boardは再Deep Sleepして通信基板だけでLoRa送信を継続する。
