# 99L 実装仮定・検証待ち一覧

## 1. 目的

本書は、00〜07および04aだけでは一意に決定できなかった実装上の選択を、正式仕様と混同せず追跡するための台帳である。

- `ASSUMPTION`: 仕様不足を補うための仮定
- `TEMPORARY_IMPLEMENTATION`: 最終方式決定前の仮実装
- `TODO_SIMULATION`: simulationでの確定待ち
- `TODO_HW_TEST`: 実機試験での確定待ち
- `NEEDS_HW_VALIDATION`: 動的または安全上の実機確認待ち
- `UNVERIFIED_HARDWARE`: Codex環境から対象hardwareを検証できていない
- `SPEC_CONFLICT`: 仕様内、または仕様と既存実装の矛盾

本書に記載した値を、飛行用の確定値として扱ってはならない。

## 2. Wire protocol

### PROTOCOL-001: split後CAN telemetryのbyte layout

- 分類: `ASSUMPTION`
- repository: `Avi_99L_MissionBoard`, `99L_comboard`
- file: `src/protocol/can_protocol.*`, `src/can/protocol.rs`
- symbol: `ControlTelemetry`, `DescentCoreTelemetry`, `AttitudeTiltTelemetry`, `LpsTelemetry`, `AirspeedTelemetry`
- 採用した仮定: 0x101は4 byte、0x104は4 byte、0x107は3 byte、0x108は4 byte、0x109は2 byteとし、sequenceを先頭、multi-byte値をlittle-endianで配置する。未使用上位bitは0とする。
- 採用理由: 現行04はsensor周期ごとの分離後のfieldを規定するが、全frameのbyte表を規定していない。過去Vaultの配置原則と現行fieldを矛盾なく組み合わせた。
- 影響範囲: Mission CAN送信、ComBoard CAN受信/cache、共通golden vector。
- fail-safe挙動: DLC、standard ID、reserved bitが一致しないframeを破棄し、cacheを更新しない。
- 最終決定に必要な情報: 各CAN IDの正式byte/DLC表。
- simulation / hardware test方法: 3実装のgolden vector一致を確認後、CAN analyzerでID、DLC、byte列、周期を測定する。

### PROTOCOL-002: LoRa A0/A6/B0/B1のpacket layout

- 分類: `ASSUMPTION`
- repository: `99L_comboard`, `Avi_tenkatenn_board`
- file: `src/payload.rs`, `src/protocol.*`
- symbol: `CommandReceiveTelemetry`, `RecoveryLogData`, `CommandResultPacket`, `GroundTimeRequest`
- 採用した仮定: A0=22 byte、A6=24 byte、B0=10 byte、B1=3 byteのapplication packetとする。A6は16 byte dataを持ち、B0 detailはu32 little-endianとする。headerからpaddingまでをXORし、E220固定送信prefixと追加RSSIはchecksum対象外とする。
- 採用理由: 現行04はpacketの責務を規定するが、これら4種の完全なfield順、bit幅、packet長を規定していない。
- 影響範囲: LoRa framing、即時command result/time request、Recovery dump、Ground表示。
- fail-safe挙動: header別の固定長とXORが一致しないpacketを破棄する。A6のtransfer ID/offsetが不連続なら自動結合しない。
- 最終決定に必要な情報: 4種の正式bit table、A6 fragment/EOF規則。
- simulation / hardware test方法: bit境界を跨ぐgolden vectorを3実装で比較し、E220 loopbackでprefix/RSSIを含むstream再同期を確認する。

### PROTOCOL-003: A0 status 24 bit割当

- 分類: `SPEC_CONFLICT`, `ASSUMPTION`
- repository: `99L_comboard`, `Avi_tenkatenn_board`
- file: `src/payload.rs`, `src/protocol.*`
- symbol: `CommandReceiveTelemetry::status`
- 採用した仮定: bit 0から順に ICM/LPS/SSC/AS5047D/STS health、Fin zero、Para open/close、logic/motor battery、Mission/Com SD、CAN、persistence、Fin/Para busy、gyro bias、gravity reference、SSC zero、Flash data/health、profile valid、Fin disabled、calibration busyを割り当てる。
- 採用理由: 過去の23項目と現行文書で追加されたgravity reference/calibration busyを24 bitへ収める必要がある。`Preflight calibration valid`はgyro bias/gravity/SSC zeroと重複するため独立bitを割り当てなかった。
- 影響範囲: A0生成、Groundのpreflight status表示。
- fail-safe挙動: Groundは未知bitをraw hexでも表示し、未知bitをhealth=trueと解釈しない。
- 最終決定に必要な情報: 正式なstatus bit表と、Preflight calibration validの独立性。
- simulation / hardware test方法: 各flagを1 bitずつ立てたvectorでCom encode/Ground decodeを確認する。

### PROTOCOL-005: ComBoard local command code

- 分類: `ASSUMPTION`, `SPEC_CONFLICT`
- repository: `99L_comboard`, `Avi_tenkatenn_board`
- file: `src/lora_uplink.rs`, Ground `src/protocol.*`, `src/main.cpp`
- symbol: `ComBoardLocalCommand`
- 採用した仮定: 既存operator入力との互換性のためlogging/GNSSはASCII `l/m/g/h`をcodeとして維持し、Recovery wake/internal dump/Mission SD dump/stopは`w/f/s/x`を割り当てる。旧`r=ForceRecoveryBeacon`は**通信基板単独でRecoveryへ入るため廃止**し、受信時は`NotSupported`とする。手動Recovery移行はMissionGeneric `EnterRecovery 0x33`をMission Boardへ送り、Mission Boardが受理した場合に`RecoveryModeCommand 0x014`で通信基板へ指示する。
- 採用理由: fixed 11-byte uplinkはlocal commandを規定するがcommand code表が未確定である一方、RecoveryBeacon移行責務は04でMission Boardへ正式に固定したため、旧local `r`は責務違反となる。
- 影響範囲: Ground CLI/GUI、ComBoard local dispatch、Recovery entry。
- fail-safe挙動: `r`および未知codeを副作用なしでRejected/NotSupportedとして扱う。RecoveryBeaconへは有効なMission→Com `RecoveryModeCommand`なしで遷移しない。
- 最終決定に必要な情報: logging/GNSS/wake/dump系ComBoard local commandの正式code/argument表。Recovery entry ownershipは確定済み。
- simulation / hardware test方法: 各codeのencode/decode、`r`/unknown code拒否、MissionGeneric `EnterRecovery`→Mission判定→0x014→A5のend-to-endをtestする。

### COM-001: CAN cache freshness

- 分類: `ASSUMPTION`, `TODO_HW_TEST`
- repository: `99L_comboard`
- file: `src/can/cache.rs`, `src/constants.rs`
- symbol: `freshness_limit_ms`, `TelemetryCache::snapshot`

- 採用理由: 送信周期は規定済みだが、ComBoard cacheのstale判定時間は未規定。数回のpacket lossを許容しつつ更新停止を検出する値を選んだ。

- 最終決定に必要な情報: 実測CAN jitter、task latency、意図するpacket loss許容数。
- simulation / hardware test方法: CAN frameを1〜N周期dropし、閾値前後のsnapshotとLoRa rawを確認する。

### GROUND-001: E220 fixed prefixとRSSI framing

- 分類: `NEEDS_HW_VALIDATION`
- repository: `Avi_tenkatenn_board`
- file: `src/decode.cpp`, `src/config.h`
- symbol: LoRa stream parser
- 採用した仮定: Ground側UARTにはE220固定送信prefix 3 byteが渡らずapplication headerから始まり、設定済みのappend-RSSI byteがpacket末尾に1 byte付く。
- 採用理由: 2026-08-14の3基板試験で、Ground E220のread-only設定応答`C1 00 08 00 00 EC 81 04 C3 00 00`が基準byteと一致した。Ground parserはA0/B0/B1を受信し、全203 packetにappend-RSSIがあり、XOR decode errorは発生しなかった。ただし現行USB pretty-printはUART raw byteを保存しないため、fixed prefixのUART境界自体は未確定である。
- 影響範囲: variable-length parser、checksum範囲、RSSI表示、再同期。
- fail-safe挙動: header/length/XOR不一致を破棄し、次の既知headerへ再同期する。RSSI値だけを理由にvalid application packetを実行系へ渡さないことはしない。
- 最終決定に必要な情報: E220の正確なmodule型番と一次資料によるfield解釈、fixed prefixを含むraw UART capture、RSSI欠落、壊れたpacket、A1〜A6の受信。
- simulation / hardware test方法: 未実施のheaderとprefix、RSSI欠落、連結・破損packetを含むUART captureでparserを再生し、LoRa loopbackで比較する。

### MISSION-005: Recovery entry / Deep Sleep周期

- 分類: `TEMPORARY_IMPLEMENTATION`, `TODO_HW_TEST`
- repository: `Avi_99L_MissionBoard`, `99L_comboard`
- file: Mission recovery/runtime module、ComBoard communication-mode module
- symbol: Recovery entry coordinator、Recovery boot path、`RecoveryModeCommand`
- 採用した仮定: RecoveryBeaconへの移行判断はMission Boardが所有する。自動移行の初期条件はDescentかつ離床後120秒、手動要求はMissionGeneric `EnterRecovery`をDescentかつ`DeploymentPowerCutoffDone`後だけ受理する。Missionは安全化/flush/RTC marker後に`RecoveryModeCommand 0x014`を送信し、最大1秒のbounded retry後にDeep Sleepへ入る。Recovery中は10秒periodic wake、短時間CAN command window、要求がなければ再Deep Sleepとし、wakeごとに0x014を再送してよい。
- 採用理由: MissionStateと飛行elapsed、安全outputを正として判断できるのはMission Boardであり、ComBoardが独自timerでRecoveryBeaconへ入ると責務が分離する。wake時間、CAN再初期化、120秒条件の最終marginは未確定。
- 影響範囲: Recovery entry ownership、Recovery battery life、beacon/status/dump latency、Mission link fallback。
- fail-safe挙動: ComBoardは有効な0x014を受信するまでRecoveryBeaconへ自律移行しない。Mission→Com送信に失敗してもMission safety/Deep Sleepを無期限に待たせず、次回wakeで再送する。Recovery marker/wake causeが不正なら通常flightへ復帰せず、安全outputのままRecovery errorを保持する。Light Sleepへfallbackしない。
- 最終決定に必要な情報: wake current、CAN initialization時間、0x014到達率、必要battery life、120秒entry timingの運用確認。
- simulation / hardware test方法: Normal→Recovery、Mission link loss前後、0x014 drop、ComBoard reset、連続Deep Sleep/wake、CAN command、storage dump、brownout/resetを反復し、ComBoardがMission指示なしにA5へ入らないこととeventual convergenceを確認する。
