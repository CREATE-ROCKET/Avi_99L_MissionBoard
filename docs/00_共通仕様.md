# 99L Mission Board 共通仕様

> **2026-08-16更新:** パラシュートのOpen/Close、STS3215 Hold、NVS、readiness、廃止commandについては[[08e_20260816_パラシュート簡素化|08e パラシュート簡素化仕様]]を優先する。本書に残る絶対角endpoint、NVS、Free、Open retryの旧記述は当該範囲では廃止。


## 1. 目的

99Lロケットのミッション基板は、離床検知、エンジン燃焼終了後の機体ロール角を一定に保つための動翼制御、頂点付近での減速機構開放を自律的に実行する。ロール制御は実装上、エンジン燃焼終了後であることを十分保証できる離床+8秒以降の最初のControl開始時に保持目標をcaptureし、その後は連続・unwrappedなロール角でその目標からの偏差を評価する。

通信基板側にはMission Board用のミッション状態機械を持たせない。通信基板はCANとLoRa間の通信、GNSS、通信基板microSD、RecoveryBeaconの送信処理等の通信基板固有機能を担当し、ミッション状態の管理はMission Boardのみが行う。RecoveryBeaconはMissionStateではないが、その**移行判断もMission Boardが所有する**。通信基板はMission Boardから明示的なRecoveryBeacon移行指示を受信した場合にのみRecoveryBeaconへ移行し、経過時間やMission通信断を根拠に自律移行しない。

## 2. 実装環境と共通データ表現

Mission BoardのファームウェアはPlatformIO + ESP-IDF上のC++17で実装する。

共通ハードウェアライブラリには`CREATE-ROCKET/Avi_ESP_Libs`の`refactor` branchを使用し、Mission Board repositoryでは`lib/Avi_ESP_Libs`のGit submoduleとしてcommit SHAを固定する。submoduleとPlatformIO/ESP-IDF toolchainが取得済みであれば通常buildをofflineで完結できる構成とする。

制御系内部の物理量はSI単位を基本とする。

- 角度: rad
- 角速度: rad/s
- トルク: N·m
- 圧力: Pa
- 電圧: V
- 電流: A
- 時間: sまたは明示されたtimestamp単位

地上局表示、設定値入力、ログ表示等で必要な場合は境界でdegree等へ変換してよい。

取得できない値を表す場合はC++17の`std::optional`を使用できる構成とする。`std::nullopt`はその時点で利用可能な値が存在しないことのみを表し、通信timeout、デバイス故障、データ鮮度切れ、Health状態、semantic errorは別に保持する。

シミュレーションで最終決定する値へ暫定値を置く場合は、コードおよび仕様に`TODO(SIMULATION)`を残す。実機試験で最終決定する値には`TODO(HW_TEST)`を残し、暫定値を飛行用最終値として扱わない。

## 3. 通信故障時の基本動作

CAN通信ができなくなった場合や、通信基板側がLoRaを介して地上局と通信できなくなった場合でも、離床検知および飛行中の自律動作を継続する。

CANがbus-off等になった場合はCAN recoveryを行い、通信の復旧を試みる。通信やloggingの異常だけを理由にMission Board全体を再起動しない。

Mission Board由来CAN telemetryが途絶した場合、通信基板は`MissionLinkFallback` telemetryへ移行してGNSS、LoRa、通信基板microSD等の通信基板自身が保持する情報を継続送信してよい。ただし通信基板はMissionStateを推測せず、最後に正常受信したMissionStateをlast-known情報としてのみ保持する。Mission通信断中もRecoveryBeaconへ自動移行しない。

## 4. 共通デバイス状態とControl再移行

すべてのミッション状態において、少なくとも以下のデバイスのHealthを保持し、地上局から確認できるようにする。

- ICM42688
- LPS25HB
- SSCDRRN005PD2A5
- AS5047D
- STS3215

動翼encoder pipelineは次の`EncoderPipelineState`を持つ。

- `Uninitialized`: producer/driver開始前
- `WarmingUp`: capture開始後だがcomplete blockまたはestimator historyが不足
- `Ready`: 必要sample数のcomplete block、strict monotonic timestamp、validなfiltered angle、estimatorの必要history、freshnessをすべて満たす
- `Faulted`: startup prefix終了後のtransport/timestamp/pipeline fault等により安全に利用できない

AS5047D producerはCommandReceive中から開始でき、有限なstartup warm-upは許容する。`StartSequence`またはControl entry時に`Ready`でなければfuture sampleをblocking待ちせず、Control input unavailableとして扱う。startup warm-upと、`Ready`後のsteady-state capture deadline miss/stale/faultは別のqualityとして記録・判定する。

値の有無、Health、freshnessは別概念として管理する。一時的なtransport errorが1回発生しただけで即座に値をUnavailableへしない。最後の正常値がfreshness範囲内で、Health上も利用可能である場合はその値を利用できる。

Control再移行可否はHealthそのものとは別に`control_reentry_inhibited`相当の状態として保持する。

以下が成立した場合はその飛行中のControl再移行を禁止する。

- 姿勢推定を継続できなくなった
- 動翼角または動翼制御に必要な状態を失った
- 有効な対気速度が60 m/s以下になった
- LPS25HBまたはSSCDRRN005PD2A5がControlに必要な時点でUnavailableになった
- 地上局から`DisableFinControl`を受理した

LPS25HB/SSCのdriver復旧処理は続けてよく、復旧後の値をtelemetry、logging、頂点検知等に使用してよいが、一度Control再移行禁止となった飛行でControlへ戻すためには使用しない。

各Health/freshnessの具体的閾値には、必要に応じて`TODO(SIMULATION)`または`TODO(HW_TEST)`を残す。

## 5. 設定値・校正値・MotorProfileの保持

動翼0度設定はresetをまたいで有効とはみなさない。

- `FinZeroConfigured`は、motor側AS5047Dのencoder zero referenceが設定され、そのconfiguration transactionが成功したことだけを表すRAM上の飛行準備状態とする。Mission Boardがresetした場合は未設定へ戻す。
- `FinZeroConfigured`はphysical finが厳密に0 degであること、左右finが一致すること、backlash gap中央にあること、air load下の空力中立、またはthermal / creep後の中立を保証しない。
- AS5047Dは減速機構よりmotor側にあるため、reset後にsingle-turn角度だけから減速機構後の動翼絶対角または0度基準を一意に復元しない。

`FinZeroConfiguration`相当のmetadataには、少なくとも`encoder_zero_count`、`configured_timestamp`、`approach_direction`、`calibration_method`、`ground_verification_status`、`measured_bidirectional_span`、`flight_epoch_id`を保持する。比較対象は`ideal_true_zero`、`single_approach_positive`、`single_approach_negative`、`bidirectional_midpoint`とする。`bidirectional_midpoint`は正負からapproachしたmotor-side zero候補をunwrapして中点を求めるbacklash中心推定候補であり、自動的に飛行用最終方式とはしない。

motor-sideの観測角とfin側の物理角は別状態とする。

- `theta_measured_rad = motor_drive_true_rad - configured_encoder_zero_rad`
- `theta_left_true_rad` / `theta_right_true_rad`: 左右それぞれのfreeplay後の実際角に、機械的中立offsetと安全評価用残留角を加えた物理値

ZeroHoldは`theta_measured_rad`を0へ制御する。したがってelectrical ZeroHold validでもphysical finが空力0度とは限らない。motor-side AS5047Dだけでは左右fin側の角度を飛行中に直接観測できないため、physical zero errorはsimulation / ground verification metricとし、観測不能な値をMission runtimeのvalid条件へ混ぜない。

パラシュートのOpen/Close設定は永続化する。

- `ParachuteOpenConfigured`は1回転内のOpen絶対角endpointが有効な場合のみtrueとする。
- `ParachuteCloseConfigured`は1回転内のClose絶対角endpointが有効な場合のみtrueとする。
- Open/Closeは互いに独立した`std::optional`として保持し、回転方向は永続化しない。実移動時にfreshな現在角とtargetからshortest pathを都度計算する。
- NVS key missing、およびCRC/schema/size/endpoint/reserved/count範囲等が不正なblobはendpoint=`nullopt`として扱う。corrupt理由はHealth/MissionEvent/internal logへ残し、剰余・clamp・既定角で補正しない。
- Open/Close設定はFlash/NVSへ保存し、resetおよび完全な電源断後も復元する。ForceStartでもmissing/corrupt endpointをvalidへ偽装しない。

動翼motorは予備個体へ交換できるため、motor依存値はprofile IDごとの`MotorProfile`へまとめる。ただしactive MotorProfileはruntime設定ではなく**build時固定値**とする。

- build systemから`AVI_99L_MOTOR_PROFILE_ID`を必ずcompile definitionとして指定する。
- macro未指定は`#error`でbuild失敗とする。
- 未知のprofile IDは`#error`でbuild失敗とする。
- MotorProfile IDをNVS/Flashへ保存してruntime選択・復元しない。
- 地上局/CAN/LoRaからactive MotorProfileを変更しない。
- profile変更はfirmware再build・再書込みでのみ行う。
- `MotorProfileValid`はcompile-time選択profileのparameters/qualification validityを表す。

未qualification profileを明示的にbuild対象へ選択した場合は`MotorProfileValid=false`のままとし、通常`StartSequence`は`NotConfigured`で拒否する。`ForceStartSequence`は7項目gateのうちこの項目だけをbypassできるが、profileをvalidへ偽装しない。メーカー公称値以外の個体依存値には`TODO(HW_TEST)`を残す。

CommandReceiveでは`RunPreflightCalibration`を何度でも実行可能とし、利用可能な範囲でgyro bias、重力vector、launcher tilt、SSC差圧zero offsetを同時に求める。各校正量は最新attemptの結果だけを使用し、最新attemptで失敗した項目について古い成功値へ自動rollbackしない。重力vectorはtilt確認に使用するが、重力軸まわりのroll zeroを決めるためには使用しない。

姿勢推定のroll原点とRoll Controllerの保持目標は別に管理する。`roll_estimate_liftoff_relative_unwrapped_rad`は離床時刻を0 radとするgyro積分の連続・unwrapped姿勢推定値であり、EngineBurn中も積分を継続し、Control開始時にresetしない。EngineBurnからControlへ初めて遷移するaccepted tickでは、最初のControl演算より前に最新のvalid/freshかつlatest-completeなunwrapped姿勢sampleを一度だけ`control_roll_reference_unwrapped_rad`へcaptureする。Roll Controllerへ渡す第1状態は`roll_deviation_unwrapped_rad = roll_estimate_liftoff_relative_unwrapped_rad - control_roll_reference_unwrapped_rad`とする。

Control pathでこの差を`wrapToPi`、`atan2(sin(d), cos(d))`、`mod(..., 2*pi)`、その他`[-pi,+pi]`へのnormalizationに通さない。Control開始後に+380 deg回転した場合は`roll_deviation_unwrapped_rad=+380 deg`、表示用の`corrective_roll_error_unwrapped_rad=-380 deg`とし、-20 degの最短路として扱わない。reference=+720 deg、current=+1100 degの場合もdeviationは+380 degである。Quaternion由来のwrapped orientationは表示やsimulation truth比較に限り、Control入力と分離する。

`control_roll_reference_valid`、captureしたMission tick、使用したestimator timestampを別々に保持する。同じlatest-complete sampleをcaptureと最初のControl演算の両方へ使用し、reference未captureでRoll Controllerを実行しない。Control中は再captureしない。reset、新しいflight epoch、`CancelSequence`、`LiftoffDetectionEmergencyStop`、rollbackでreferenceをinvalidにする。

固定finの0.5 deg misalignment仮定に由来する`Cl0_nominal=0.00536`は、ランチャー0へ戻すためのreference offsetではなく、Control entryでcaptureしたunwrapped referenceに対してControl中も継続するconstant roll disturbanceである。reference訂正だけではentry時roll rate、継続roll moment、trim fin angle、holding torque、saturation、定常偏差は消えない。積分状態、disturbance observer、trim feed-forwardを持たない4-state BaselineLQRがconstant disturbance下で偏差0を保証すると主張しない。

`RunPreflightCalibration` commandの実行履歴そのものではなく、`GyroBiasValid`、`GravityReferenceValid`、`SscZeroValid`の3 validityを通常`StartSequence`の必須条件とする。これらがinvalidなら通常Startは`NotConfigured`で拒否する。Forceで開始してもinvalid値をvalidへ偽装しない。

`RunPreflightCalibration`中は静置条件を守るため、Fin/Para駆動command、bring-up motor試験、`StartSequence`および`ForceStartSequence`を`Busy`で拒否する。逆にFin/Para駆動またはmotor試験中もCalibrationを`Busy`で拒否する。

## 6. Reset後の復帰

起動直後にESP32-S3のreset reasonを確認する。

飛行中resetから復帰した場合は、reset前のロールturn count、Control roll reference、および動翼絶対角を正確に復元できるとはみなさず、Controlへは復帰しない。single-turn姿勢やtelemetryのwrapped orientationからturn countを復元してはならない。Reset直後は`control_roll_reference_valid=false`とし、動翼はBrakeとしてロール制御や0度保持へ復帰させない。

Resetをまたいで保持・復元する情報は、少なくとも以下を対象とする。

- sequence開始済みか
- 離床検知済みか
- 離床時刻または離床後経過時間を復元するための情報
- パラシュートOpen処理を開始済みか
- パラシュートサーボおよび差圧系基板の電源遮断済みか
- Control復帰禁止情報

飛行中reset後は、連続ロール角、Control reference、動翼絶対角を正確に復元できるとはみなさないため、Controlへは復帰しない。

リセット時点が離床前のCommandReceiveまたはLiftoffDetectionであれば通常のCommandReceiveへ戻り、必要な設定・校正をやり直す。

離床検知後にresetした場合は、復元できる範囲でEngineBurnまたはDescentへ戻すが、動翼はBrake、`control_reentry_inhibited=true`としてControlを禁止する。離床済みなのにLiftoffDetectionへ戻って再離床検知を要求してはならない。

パラシュートOpen開始済みであればOpenを再開し、電源遮断済みであれば再投入しない。

離床後経過時間の復元は以下の優先順位とする。

1. validな離床絶対時刻と現在時刻から再計算
2. 単調増加相当のcheckpoint済みelapsedを復元
3. どちらも不可能なら安全側へ倒す

完全なPower-on resetまでに有効な離床絶対時刻を保存できず、再起動後も経過時間を復元できない場合は、その飛行ではパラシュートOpenを開始または再開しない。時刻不明のまま気圧条件だけでOpenへ移行することもしない。

## 7. NVS checkpointと内部Flash backup log

NVS checkpointはreset recoveryの成功率を上げる補助系であり、飛行critical pathのtransaction journalとは扱わない。

飛行中の重要eventでは、まずRAM/RTC上のstateとMission動作を即時更新し、NVS保存はbounded queueへnon-blockingで要求する。

対象eventは少なくとも以下とする。

- シーケンス開始受理
- 離床検知
- パラシュートOpen処理開始
- パラシュートサーボおよび差圧系基板の電源遮断完了

NVS queue full、write failure、CRC failure等があっても離床検知、Control、パラシュートOpen、+25秒cutoffを待たせない。失敗時は`persistence_healthy=false`とし、event/logへ残してMissionを継続する。

CommandReceive中のパラシュートOpen/Close設定のように永続化そのものがcommand目的である操作は、保存成功後にactive configを更新してよい。MotorProfileはNVS設定対象ではなくbuild-time固定である。

NVS recordはversion、record sequence、payload、CRCを持ち、raw C++ structのpaddingへ依存しない明示serializationを使用する。二重slot等により最新のvalid recordを選べる構成とする。

`LiftoffDetectionEmergencyStop`はEngineBurnでのみ受理し、LiftoffDetectionへ巻き戻す。巻き戻し時は前回の離床時刻および離床checkpointを無効化し、次の離床検知で新しいflight epoch/checkpointを作成する。旧epochに属する遅延Safety eventを現在flightへ適用しない。

NVS checkpointとは別に、Mission microSDのbackupとして内部Flashへ飛行中の重要データを低rateで保存する専用partitionを設ける。初期rateは50 Hz程度としてよいが、`TODO(HW_TEST)`を残す。

internal Flash backup領域はCommandReceive中に必要範囲を事前eraseし、LiftoffDetection以降はpre-erased領域へのappend writeのみとする。飛行中にeraseしない。Flash write/eraseを1 kHz realtime taskから直接行わない。

CommandReceiveでは`ExportFlashLogToSdAndErase`を実行可能とし、Flash logをmicroSDへ書き出し、flush・再読出し・CRC等で完全な保存を確認した場合だけFlash backup partitionをeraseする。途中で失敗した場合はFlashを消去しない。

## 8. microSDと冗長logging

Mission Board microSDは主flight logを保存し、内部Flashは重要値のbackup、通信基板microSDはMission Boardから受信したCAN telemetryの冗長backupとして使用する。

Mission Board microSD初期化に失敗した場合は1秒ごとにretryしてよい。microSD異常を理由にMission sequence全体を停止しない。

通信基板はMission BoardからCANで受信した量子化済みtelemetryをLoRa送信周期へ間引く前に保存し、少なくとも通信基板側受信時刻、CAN ID、DLC、payloadを失わない形式で記録する。Mission Board由来値を通信基板側で再量子化しない。

## 9. 通信基板とのプロトコルとRecovery

Mission Boardから通信基板への周期telemetryは100 Hz程度を基本とし、実機でCAN/処理/logging上の問題が確認された場合は設定値を10 Hz程度へ変更してよい。runtimeで自動的に100 Hzと10 Hzを行き来する仕様にはしない。LoRaのFlightTelemetry / DescentTelemetry約0.5秒周期とは独立とする。

Emergency以外のMission Board向け通常コマンドはgeneric command request/resultとして扱う。Emergencyは以下の2種類を別messageとする。

- `ActuatorEmergencyStop`: CommandReceiveのみで受理
- `LiftoffDetectionEmergencyStop`: **EngineBurnのみ**で受理し、LiftoffDetectionへ巻き戻す

飛行中に地上局から動翼制御だけを禁止する`DisableFinControl`をgeneric commandとして受理できるようにする。LiftoffDetection、EngineBurn、Controlで受理し、受理後はそのflight中`fin_control_disabled`を保持してBrakeとし、Controlへ再移行しない。

LiftoffDetectionからCommandReceiveへ戻す`CancelSequence`をgeneric commandとして用意する。

RecoveryBeaconへの移行判断はMission Boardが行う。Mission BoardはDescent中のRecovery条件を評価し、必要なSD/Flash flushと安全化、RTC Recovery marker設定後に`RecoveryModeCommand`を通信基板へ送る。通信基板はMission Boardから明示的なRecoveryBeacon移行指示を受信した場合にのみRecoveryBeaconへ移行し、独自のelapsed timerやMission通信断を理由に自律移行しない。MissionStateはRecoveryBeacon中もDescentのままとする。

Mission BoardはRecovery移行決定後、**Deep Sleepのみ**を使用するRecoveryへ入る。Light Sleep fallbackは実装しない。`RecoveryModeCommand`を送信できない場合でもMission safety処理を無期限に待たせず、次回Recovery wakeで再送する。通信基板は指示を受信するまで`MissionLinkFallback`等の現在communication modeを維持する。

Deep Sleepからの復帰は通常flight boot pathと分離し、RTC memoryのRecovery markerとwake causeを確認してRecovery専用boot pathへ入る。初期候補として10秒periodic wakeを使用し、ADC/CAN/Recovery status更新と短時間command受付後に再びDeep Sleepへ戻る。wake時にはRecoveryBeacon移行指示を再送してよい。wake周期、command window、CAN再initializationは`TODO(HW_TEST)`とする。

RecoveryBeacon中でも地上局から要求された場合はMission Boardをwakeし、内部Flash backup logを標準sourceとして通信基板へ転送する。Mission microSD full-rate logはoffset/length指定の部分dumpを基本とする。Mission→通信基板は可能ならCANで通信基板microSDへ先にspoolし、その後Mission BoardをDeep Sleepへ戻して通信基板だけでLoRa送信を継続する。

## 10. 実装・検証上のTask ownership

本番Mission実装より先に、`Avi_ESP_Libs/refactor`で今回使用するAPIが実Mission Board上で正しく動くことを個別検証する。ライブラリ責務の不具合をMission Board側のad-hoc workaroundで隠さず、必要ならsubmodule側を修正して再検証する。

安全優先度は**deployment条件監視・絶対電源遮断 > パラシュートOpen/UART > 1 kHz Mission/Control > AirData > CAN > persistence/logging**とする。

Taskの基本責務は以下とする。

- `SafetyTask`: deployment条件、+17/+25監視、絶対power cutoff latch。UART/SD/Flash等の長時間blocking I/Oは禁止
- `ParachuteTask`: STS3215通信、Open/progress/retry。STS UARTの唯一owner
- `MissionRealtimeTask`: 1 kHz FSM、ICM、AS5047D、fin controller。`MissionState`の唯一writer
- `AirDataTask`: SSC/LPS、filter、airspeed。I2Cの唯一owner
- `CanTask`: CAN RX/TX、bus-off/recovery
- `CommandWorkerTask`: command dispatch、Calibration、長時間command管理。deviceを直接所有しない
- `HousekeepingTask`: ADC、LED、低rate Health/時刻処理
- `InternalFlashTask`: NVS + internal Flash backup
- `SdLogTask`: Mission microSD

`SafetyTask`はMissionStateを書き換えずdeployment request/latchのみを更新し、`MissionRealtimeTask`が次の1 ms tickでDescentへ遷移する。

GPIO40/GPIO44等のpower enableは単一power arbiterを通し、`deployment_power_cutoff_latched=true`後は他TaskのON要求で再投入できない構造とする。

## 11. 動翼構造・simulationの共通前提

飛行時hardware angle limitは±15 degである。mechanical stopperへの接触自体を直ちにFAILとはしないが、`|theta| > 15 deg`は絶対FAILとする。

一次資料は「構造系審査書_CREATE_第3版」第5.2.3節「可動機構のガタ・支持剛性に関する補足評価」（PDF pp.79–87、PDF SHA-256 `341aaede7f89f26f5c4644d851e00aeb9cd1cd3256ed2a9e0de4bc461a4ba6c0`）とする。この一次資料でsource-fixed / measuredまたはderivedと確認できる値を以下の基準とする。

- 実測backlash全幅: **0.344 deg = 0.00600 rad**
- 回転方向支持剛性: **269.43 N·m/rad**
- 対称freeplay operatorのderived half width: **0.172 deg = 0.00300 rad**
- 直進位置残留角の保守的安全評価値: **±0.344 deg = ±0.00600 rad**
- 269.43 N·m/radは予荷重でbacklashを一方向へ取り切った後の最大測定点割線剛性
- 構造上の必要支持剛性: **152.71 N·m/rad**
- 危険符号での静的発散防止必要剛性: **15.91 N·m/rad**
- 0.344 deg残留時の追加法線力: **1.301 N / fin**
- 設計荷重に対する追加法線力比: **0.01903**（合格基準0.10以下）
- stopper構造評価torque: **7.10328 N·m**
- stopper FM相当静的確認: **10.65 N·mを30 s保持**
- 通常制御時に必要と評価された保持torque: **2.66526 N·m**（構造上の最大許容torqueではない）
- 通常保持の構造試験比較値: **9.10 N·m**
- stopperなし駆動系構造評価torque: **1.21208 N·m**

269.43 N·m/radは今回測定した方向の組立支持剛性であり、freeplay内の復元剛性、歯面衝突の局所contact stiffness、stopper contact stiffness、dynamic impact stiffnessではない。構造試験は左右・正負全方向が完全に同一とは証明しない。parameter metadataに`measurement_direction_coverage`、`source_status`、`requires_bidirectional_revalidation`を必須とする。

構造系審査書はfreeplay内のfin単独振動、backlashを跨ぐLCO、歯面の反復衝突、dynamic contact damping / stiffness、impact許容energy、左右fin個別のinertia / damping、fin搭載時の最終摩擦、current / thermal / creepを最終保証しない。sourceがないparameterは`status=unidentified`および`TODO(HW_TEST)`とし、synthetic unit test値をcanonical flight artifactへ混ぜない。

stopperの10.65 N·m試験は静的保持試験であり、高速衝突時の運動energy許容値を直接保証しない。Spicaではstop contact時の`theta_dot`、接触回数、接触継続時間、static contact torqueを記録し、未実機確認のdynamic impactを`NEEDS_HW_VALIDATION`として区別する。

制御候補は少なくとも以下の2系統を比較可能にする。

- Gentle candidate: output torque上限初期候補 **1.21208 N·m**
- High-authority candidate: software current 2 A相当を基準とする約**3.0 N·m級**の初期候補

Gentleで十分な制御性能を得られる場合はGentleを優先する。High-authorityでなければ要求性能を満たせずstopperへのdynamic contactが発生する場合は、simulationが要求する最大接触速度まで段階的に実機qualification testを行ってから採用可否を判断する。stopper衝突試験はPhase 6開始条件にはしない。

`3.0 N·m > 2.66526 N·m`だけを理由にHigh-authorityを構造FAILにしない。3.0 N·m candidateはactual motor current、GP22A continuous/intermittent条件と6000 rpm超過時間、motor speed、gearbox speed、thermal、stopper、duty、repeated load、およびflight authority承認を個別に評価する。current / thermal / drivetrain efficiencyが未同定の間はflight-readyとしない。

## 12. 未定義・要検証事項

コード構造を止める未定義事項ではなく、以下をsimulationまたは実機試験で最終決定する。

- 各デバイスHealth/freshnessの最終閾値
- 動翼相対移動時の最終torque、stall条件
- MotorProfileの個体実測値、駆動系効率、motor polarity
- 動翼・stopper取付後のfin software limit
- ZeroHold、LQR、Fin Velocity Estimator、AirData filter等の飛行用最終係数
- Brake時の電流、温度、機械負荷
- battery present threshold/debounce
- STS3215 speed/torque、ServoOpenConfirmed、DeploymentShockConfirmedの最終値
- 基板X/Y軸と機体X/Y軸の最終対応
- dynamic stopper impact許容速度/energy
- 左右fin inertia/damping/friction、歯面dynamic contact stiffness/damping、impact energy許容値
- physical fin zeroの正負approach repeatability、左右差、thermal / creep後残留角
- LED表示仕様
