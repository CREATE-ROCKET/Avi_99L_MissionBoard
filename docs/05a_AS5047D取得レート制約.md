# 99L Mission Board AS5047D取得レート制約

## 1. 優先順位

本仕様は2026-08-16時点のAS5047D取得レート決定である。

`05_実装仕様.md`その他の99L文書に残る旧取得レート記述と矛盾する場合、本仕様を優先する。

**新規のAS5047D acquisitionはcharacterization / productionとも1000 Hzだけとする。**

2000 Hz / 5000 Hz / 10000 Hzで新規実機captureを行わない。

## 2. 判断根拠

PRECHECK8.4の1000 Hz rate-checkでは10秒・10000 epochについて次を確認した。

- valid 10000 / 10000
- repeated 0
- skipped 0
- invalid 0
- steady-state incomplete 0
- raw queue overflow 0
- writer queue overflow 0
- encoder transport/status error 0
- command deadline miss 0
- V5 records written 10000

同じ条件の2000 Hzではrepeated 3、skipped 3、steady-state incomplete 6が発生した。production controlおよびmotor system identificationは1000 Hzで構成できるため、2000 Hzの追加qualificationを継続しない。

## 3. Production

MissionRealtimeTaskは1 ms周期とし、各周期でAS5047D `readPipelined()`を1回実行する。

AS5047D angle、fin velocity estimator、Roll Controlへ渡すencoder updateは1000 Hzとする。

飛行中はpipelined angle readを優先し、diagnostic目的でpipelineを周期停止しない。詳細status/ERRFL確認はCommandReceiveまたはbring-upで行う。

## 4. Motor system identification

新規characterization campaignのrate-check/full captureは1000 Hzだけとする。

各stageの完了条件は次だけである。

1. 1000 Hz motor-ID rate-check normal
2. 1000 Hz full capture normal

2000 Hz / 5000 Hzのcampaign slotはV5旧ログdecode互換のため型として残してよいが、新規campaignでは最初からunsupported扱いとし、operatorへ実行を要求しない。

## 5. Motor-ID用realtime契約

motor system identificationとflight realtime qualificationを分離する。

productionの100 us realtime requirementは変更しない。一方、motor-ID full captureでは100 usをcommand applyの診断targetとする。必要なcommand applyが100 usを超えても、actual timestampとepoch順序を保持できる限りrunを継続する。

command applyが予定epoch内で完了する場合、actual `command_apply_timestamp_us`をそのepochのcommand evidenceとして保存する。

command apply開始または完了が予定epoch終端を越え、かつ次epoch終端より前である場合、すなわち`epoch_start_us + 1000 us <= command_apply_timestamp_us < epoch_start_us + 2000 us`では、1 epoch command slipとして診断継続する。この場合、既に終了した予定epochのrecordへ遅れて適用されたcommandを帰属させてはならない。予定epochのrecordには適用前command evidenceを保持し、遅れて適用されたcommandはactual apply timestampに従って次epoch側の実入力として扱う。

これにより、encoder blockと実際にそのblockへ作用したmotor inputの因果関係を保つ。offline解析はprofile上の予定command時刻ではなく、V5のactual `command_apply_timestamp_us`をplant入力の正本とする。

command apply開始時点で`>= epoch_start_us + 2000 us`の場合は遅れたDrive/Brakeを出さずCoastへ倒す。apply開始は2 ms未満でも、適用完了時刻が`>= epoch_start_us + 2000 us`へ達した場合は直ちにCoastへ倒して`AbortReason::Deadline`でrunを停止する。

100 us超過や1 epoch slipを、flight realtime requirementを満たした扱いにしてはならない。production timing qualificationは別試験とする。

consumer releaseがepoch終端から100 usを超えた場合でも、次の全条件を満たせばmotor-IDのtimestamp診断として継続できる。

- notificationがexactly 1
- release遅延が1 epoch未満
- raw sampleのactual capture timestampが正しいepoch内
- repeated/skipped/invalid/steady-state incompleteがない

release-only遅延は`consumer_lateness_us`とUART timing diagnosticへ残す。新規motor-ID V5 recordではrelease-only遅延をfatalな`EpochDeadline`へ昇格しない。

次は従来どおりfatalとする。

- command applyが2 epoch目へ達する、またはcommand generation/epoch順序の因果関係を保持できない
- notification coalescing
- 1 epoch以上のconsumer release遅延
- encoder invalid / transport / status error
- repeated / skipped / steady-state incomplete
- raw/writer queue overflow
- Vbus invalid
- position guard / overshoot / hard abort
- motor apply error
- SD write/sync/close error

このmotor-ID用緩和は、production MissionRealtimeTaskの100 us realtime requirementを満たしたことを意味しない。

### 5.1. TB67H standby復帰時間

`command_apply_timestamp_us`はMCUがTB67H入力へcommandを適用した時刻として扱い、TB67H内部でstandby解除後にOUTが有効になるまでの最大30 usは含めない。

長いCoast後のDriveではstandby復帰遅延が生じ得るため、motor-ID解析では`command_apply_timestamp_us`以後のplant-side latency uncertaintyとして扱う。最大30 usを固定値としてtimestampへ加算してはならない。

## 6. V5旧ログ互換

V5 schema、320 byte record、`EncoderRate::Hz2000` / `Hz5000`の数値、5 raw-sample slotは過去ログdecode互換のため残す。

旧V5 captureでrelease遅延に`EpochDeadline`が付いている形式も引き続きdecode可能とする。旧契約で100 us超過commandに`EpochDeadline`と`AbortReason::Deadline`が記録されているfull captureもdecode可能とする。

新しいmotor-ID full captureでは、予定epoch内の100 us超過command applyについて`EpochDeadline`やabortを要求しない。1 epochだけslipしたcommandは終了済みepochのrecordへ誤帰属させず、actual timestampに従って次epoch側の実入力として扱う。2 epoch目へ達したcommandだけ`EpochDeadline`と`AbortReason::Deadline`を必須とする。

MissionBoardの`tools/verify_characterization.py`をV5 timing契約の正本validatorとし、`tools/verify_motor_id_characterization.py`は同じvalidatorを呼び出す互換entry pointとする。

## 7. Storageとpackage

V5 1000 Hzは320 byte/ms、すなわち320 kB/sを連続生成する。

run前のstorage契約は次を維持する。

- planned file全体を`esp_vfs_fat_create_contiguous_file(..., alloc_now=true)`で確保する
- `esp_vfs_fat_test_contiguous_file()`で連続性を確認できない場合はcaptureを開始しない
- header/record/footerはstdio bufferingを介さずPOSIX file descriptorへshort-write/EINTR対応で書く
- 終了時にactual footer終端へtruncateし、`fsync`してcloseする

2026-08-16のcontiguous allocation後の実機試験では、同一構成で次の両方を観測した。

- 10秒10000 recordを正常完走し、`write-bps`約392 kB/s、`fwrite-max-us`約61 msとなるrun
- `fwrite-max-us=2322287`の単発stallが発生し、577 record時点で512-record writer queueがoverflowするrun

後者は`preallocate-us=41590`、`contiguous=1`で発生しており、FAT cluster allocationではなくSD/FAT write pathのtail latencyとして扱う。512 recordは0.512秒分しかないため、2秒級stallをDRAM queueだけで吸収しない。

### 7.1. 4 MiB PSRAM staging

characterization writerは次の二段buffer構成とする。

```text
char_runtime
  -> 512-record internal-DRAM ingress queue
  -> char_log_stage: strict validation + V5 encode
  -> 4 MiB PSRAM SPSC wire-record ring
  -> char_writer: internal-DRAM batchへ最大64 record copy
  -> SDMMC/FATFS
```

要件は次のとおり。

- PSRAM staging領域は**4 MiB固定**とし、run中ではなくwriter初期化時に`MALLOC_CAP_SPIRAM | MALLOC_CAP_8BIT`で確保する
- PSRAMには320-byte V5 wire recordとsequence metadataを保存する
- 実装容量は約12787 record、1000 Hzで約12.8秒分とする
- SDMMCへPSRAMを直接DMA sourceとして渡さず、最大64 recordをinternal DRAM batchへcopyしてからwriteする
- `char_log_stage`とSD I/O taskを分離し、SD `write()`が数秒blockしてもDRAM ingressをPSRAMへ退避できるようにする
- Core 1 task priorityは`char_encoder=23`、`char_log_stage=12`、`char_writer=10`とし、encoder captureを最優先する
- PSRAM ringが満杯の場合はold recordを上書きしない。`ESP_ERR_NO_MEM` / writer queue overflowとしてfail-safe停止する
- SD write/sync/close failureは従来どおりfatalとする

footerの`writer_queue_overflows`はDRAM ingress overflowとPSRAM staging overflowの合計を表す。

`CHAR_WRITER_TIMING`には次を表示する。

- `queue-depth`
- `queue-high-water`
- `psram-bytes`
- `psram-capacity-records`
- `psram-high-water`
- `psram-overflow`
- `batch-capacity`
- `max-batch-records`
- `contiguous`
- `write-bps`
- 既存のvalidate/encode/fwrite timing

4 MiB staging変更後はまず1000 Hz・10秒rate-checkで次を確認する。

- `contiguous=1`
- `valid=10000 total=10000`
- `writer-queue-overflow=0`
- `psram-overflow=0`
- repeated/skipped/invalid/steady-incompleteが0
- SD stall発生時もDRAM `queue-high-water`が512へ張り付かない

`psram-high-water`が増えること自体はfailureではない。SD stallを吸収して最終的に全recordが保存されれば正常とする。

Spica引渡しpackageで各stageに要求する新規captureは次だけとする。

- 1000 Hz rate-check normal
- 1000 Hz full normal

FV / FH+ / FH- / M0について2000 Hz evidenceを要求しない。
