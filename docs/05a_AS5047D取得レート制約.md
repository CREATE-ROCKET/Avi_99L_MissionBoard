# 99L Mission Board AS5047D取得レート制約

## 1. 優先順位

本仕様は2026-08-16時点のAS5047D取得レート決定である。

`05_実装仕様.md`その他の99L文書に残る5 kHz / 10 kHz取得記述と矛盾する場合は本仕様を優先する。

AS5047Dの最大更新レートは2.5 kHzであるため、99Lでは上限ぎりぎりを使用せず、新規取得を次の2レートだけに限定する。

- 1000 Hz
- 2000 Hz

5000 Hz / 10000 Hzで新規AS5047D captureを行わない。

## 2. Characterization

characterizationのrate-checkおよびfull captureでAS5047D samplerを開始できるのは1000 Hz / 2000 Hzだけとする。

1000 Hzは必須レートとする。2000 Hzはrate-check結果に基づいてaccepted / unsupportedを決定する。2000 Hzがunsupportedでも1000 Hz fullが正常であればcampaignは継続可能とする。

Stage完了条件に5 kHz rate-checkを含めない。

V5の旧ログ互換のため、firmware内部の旧`EncoderRate::Hz5000`数値や5-sample wire slotを当面残してよい。ただし新規実機取得を許可する意味ではない。

## 3. Production

productionのAS5047D capture候補は2000 Hzのみとする。Mission/Control estimator updateは従来どおり1000 Hzとし、2 kHz captureからcomplete blockを渡す。

5 kHz captureをproduction候補から除外する。

飛行中はpipelined angle readを優先し、diagnostic目的でpipelineを周期停止しない方針は維持する。

## 4. 検証

実機rate-checkは1000 Hz、2000 Hzだけを実施する。

1000 Hzは欠落・repeated・deadline・queue overflow・encoder errorがないことを必須とする。2000 Hzは同じ基準でqualificationし、成立しない場合はunsupportedとして1000 Hzへfallbackする。

## 5. Characterization realtime契約

PRECHECK7.5では1 kHzのraw captureはcompleteだった一方、consumerが前epoch処理を終える前に次の1 ms alarmへ到達しrelease deadlineを落とした。したがってAS5047D producer queueのconsumerは、queueが空になるまでproducerを追い続けてはならない。

consumerはdrain開始時点のSPSC ring producer headをsnapshotし、その時点でpublish済みだった有限個のsampleだけを処理する。snapshot後にpublishされたsampleは次consumer cycleへ残す。future sampleを現在epochへ借りず、epoch/slot所属はactual capture timestampによる半開区間判定を維持する。

V5 recordのfull wire validationは1 kHz `char_runtime`から外し、immutable recordをwriter queueへ値copyした後、`char_writer`がencode直前にstrict validationを1回だけ行う。motor safety、position guard、100 us command/release deadline、queue overflow、encoder transport/status errorの監視はrealtime側に残す。writer validation failureは既存failure notificationを通して安全停止へ伝播させる。native/offline validatorはstrictのままとする。

### 5.1. 2 kHz trigger phase

1 kHz triggerはepoch内500 usを維持する。

PRECHECK7.5では2 kHzのscheduled→actual capture最大347 usが観測され、250/750 us triggerでは500 us slot境界を越えた。qualification再試験ではprovisionalに120/620 usでtriggerする。120 usは100 us command deadlineより後に置き、command apply deadline中へencoder taskを直接重ねない。

120/620 usはflight採用済み定数ではない。actual captureが各half-open slot内へ入り、repeated/skipped/deadlineが0になる場合だけ2 kHzをacceptedとする。成立しなければ2 kHzはunsupportedとし、deadlineやslot境界を緩和しない。

### 5.2. Task affinityとwriter throughput

PRECHECK7.8では`char_runtime`をCore 0へ分離したことで、1 kHzの`consumer-work-max-us`は644 us、`consumer-wait-late-max-us`は0まで改善し、2 kHzでもraw epochはcompleteになった。一方、1000/2000 Hzとも約233 recordでwriter queueがoverflowした。

characterizationではtask affinityを次のように固定する。

- Core 0: `char_runtime` priority 21、`char_vbus` priority 12、`char_console` priority 5
- Core 1: `char_encoder` priority 23、`char_writer` priority 10

`char_encoder`は同Coreのwriterより常に優先し、AS5047D captureをSD書込みより優先する。

PRECHECK7.9では1 kHzが10秒・10000 recordを`writer-queue-overflow=0`で完走し、queue high-waterは56だった。2 kHz raw captureもcompleteだったが、Core 1上で2 kHz encoder taskにpreemptされるwriterがqueue depth 128を使い切り、1615 record時点でoverflowした。

SD/FATの数十ms級の瞬間stallをcharacterizationのRAM bufferで吸収することは許可する。このためwriter queue depthを512 recordsへ拡張する。ただし`queue-high-water`を必ず記録し、10秒run中に512へ単調に近づく場合は平均writer throughput不足として不合格とする。queue拡張を持続速度不足の隠蔽に使用してはならない。

SDMMC mountは`char_runtime`から行わず、Core 1へpinした`char_writer` task自身のstartupで実施する。storage初期化成否はstartup semaphoreで`LogWriterV5::initialize()`へ返し、失敗時はcaptureを開始しない。これによりstorage driverの初期化・interrupt allocationをrealtime consumer側Core 0から分離する。

rate-check終了時にwriter側の次のdiagnosticを記録する。

```text
queue-depth
queue-high-water
batch-capacity
max-batch-records
batch-count
preallocate-us
planned-bytes
validate-max-us
validate-total-us
validate-avg-us
encode-max-us
encode-total-us
encode-avg-us
fwrite-max-us
fwrite-total-us
fwrite-avg-us
records-written
```

`fwrite-max-us`はSD/FATの瞬間stall、`fwrite-avg-us`とqueue high-waterの推移は持続throughputの判定に使用する。encoder raw rateが2 kHzでもconsumer record生成は1000 Hz、1 record/msのままとする。

### 5.3. PRECHECK8後のstorage契約

PRECHECK8ではqueue depth 512でも、1 kHzで`fwrite-max-us=951768`、2 kHzで`fwrite-max-us=532719`の長時間stallが観測された。1 kHzは9328 record、2 kHzは535 recordでqueue high-waterが512へ到達してwriter queue overflowとなった。一方、停止までのraw encoderは両rateとも`repeated=0`、`skipped=0`、`steady-incomplete=0`であった。

この結果からqueueを512よりさらに増やすだけの対策は採用しない。queue depthは512のまま維持し、writer batch上限を16から64 recordsへ増やして、backlog時は最大20 KiB級の連続V5 recordを一度の`fwrite`へまとめる。

各rate-check/full runではmotor、AS5047D sampler、consumer GPTimerの開始前にplanned file sizeを`V5 header + expected epochs * V5 record + V5 footer`として`ftruncate()`で確保し、`fsync()`まで完了させる。ESP-IDF FatFs VFSのfile拡張は不足領域をzero writeしてclusterを確保するため、FAT cluster allocationをmotor run前へ移す。preallocation完了後に`epoch_zero`を新しく決め、characterization run start leadは1.5 sとする。

abort等でplanned record数より短く終了した場合は、footer書込み後のactual file positionへ`ftruncate()`してzero tailを除去し、`fsync()`後にcloseする。V5 file layoutは常に`header + actual records + footer`を維持する。

V5 CRC32はpolynomial `0xEDB88320`、initial/final XOR、`previous_crc` chainingを変更せず、256-entry table lookupへ高速化する。file CRCはwriter batchの連結bytesを一度にchained CRCへ渡す。既存golden fixtureとbyte-for-byte互換であることを必須とし、schema、record size、Spica importerを変更しない。

storage改善のために100 us command/release deadline、half-open epoch/slot境界、queue overflow時のfail-safeは緩和しない。preallocation/batch/CRC改善後もdeadline missが残る場合、GPTimer interrupt priority/affinityは別の変更として評価する。

## 6. Characterization compiler最適化

characterization firmwareはtiming qualification専用buildとして、ESP-IDF framework componentには公式のperformance optimization `-O2`を使用する。framework全体へPlatformIO `build_flags`で`-O3`を注入してはならない。

MissionBoard自前の`src` componentだけは、characterization用CMake option `AVI_99L_CHARACTERIZATION_BUILD=ON`のとき`-O3`を追加する。これによりrealtime/characterization処理を強く最適化しつつ、ESP-IDF UART/FreeRTOS/SDMMC等はEspressifが想定する`-O2`でbuildする。

ESP-IDF framework全体のcompile-time/link-time LTOは使用しない。LTOによるframework task stack使用量やdriverコード生成の変化をcharacterization timing qualificationへ混入させないためである。

`-Ofast`およびfast-math系optionも使用しない。finite/NaN/Inf、浮動小数点比較等の安全判定の意味論を維持するためである。

2026-08-16の全component `-O3`試行ではESP-IDF `esp_driver_uart/src/uart.c`がGCCの`-Warray-bounds`を発生させ、frameworkの`-Werror`でbuild停止した。このためcomponent-local `-O3`をcharacterization build方針とする。

最適化変更後のbinaryは別firmware SHAとして扱い、1/2 kHz rate-check、full 1 kHz、writer throughput、position guard、安全停止を再qualificationする。deadlineやacceptance基準を最適化のために緩和しない。

## 7. V5 characterization validator semantics

V5 characterization logでは、前epochで適用済みのcommand generationを現在epochでも継続して使用できる。したがって同一generationについて`command_apply_us < epoch_start_us`であることだけをinvalidとしない。stable commandのapply timestampは過去の適用時刻を保持してよい。

一方、新しい`command_generation`へ進んだrecordでは、そのgenerationの`command_apply_us`が直前generationより単調増加し、かつ当該current epochの`epoch_start_us`以上でなければならない。新generationを前epochのapply timestampで表現してはならない。`command_apply_us > release_us`等の既存timestamp ordering違反も引き続きinvalidとする。

startup warm-upとsteady-state qualityを分離する。起動直後のepochで発生したrepeated/skippedは`startup_incomplete`等のstartup指標で追跡し、それだけを理由にcompleted capture全体をFAILへしない。Ready後の欠落は`steady_incomplete`で評価し、正常qualificationでは`steady_incomplete=0`を要求する。

`trigger_coalesced`、`pre_epoch`、invalid/late、raw/writer queue overflow、encoder transport/status error、Vbus invalid等の既存fatal条件は緩和しない。startup warm-upの許容をsteady-state欠落やqueue overflowの隠蔽に使用しない。

MissionBoard側V5 writer/validatorとSpicaの`load_99l_motor_characterization` / `validate_99l_characterization_capture`はこの判定を一致させる。schema、record size、CRC chainおよび既存golden fixtureのbyte互換性は変更しない。
